## Core Rules

1. Read `./AGENTS.md` and apply its rules — the domain-neutral core.
2. This is an engineering skill: also read `./references/engineering/rules.md` and apply it on top of the core.

Update the PR body that `/review-code -d` prepared. This skill deliberately mutates the PR on GitHub — invoking it *is* the explicit permission for that outward-facing change. It writes the PR body only: it edits no code, changes no title, changes no PR state, merges nothing, comments nothing, and pushes nothing — it posts exactly the description review-code drafted.

## Preconditions — stop if unmet

- **The reviewed object must be one `-d` can describe.** `/review-code` refuses `-d` on a path set, and on a range that does not both end at the current branch's HEAD and start at that branch's own base, because neither object has a PR whose whole body it could describe — `../review-code/SKILL.md` § *Setup* owns which objects those are, and is read only to settle a borderline invocation. <!-- cold --> Two signals settle it without re-deriving anything, and they do not carry equal weight. `Reviewed paths` is conclusive on its own: a path set proposes no change and has no PR whose body it could describe, whatever else the output says. `Reviewed range` is **not** — a range that does both end at the branch's HEAD and start at its base is describable, and `/review-code` drafts for it, so refusing on the kind alone would block a valid draft the source produced. On a range, refuse only in combination with the one-line `-d refused: <reason>` `/review-code` renders in the description's place, which is the source's own verdict on this exact question and the more direct signal of the two; a range whose output carries a drafted description instead is applied normally. Where this session's most recent review ran on such an object, stop in one line naming it: the flag was refused at the source, so nothing was drafted and re-running it there would be refused again. Check this ahead of the draft below, so the reason the user reads is the object rather than an instruction to run `-d` first.
- **A review-code `-d` description must exist in this conversation.** Find the PR description `/review-code -d` drafted earlier in this session (the fenced, body-only block) — or the one `/review-code-triage-verify -d` forwarded, whose **PR description** Output carries it in review-code's own format because its review phase *is* a `/review-code` run. Either satisfies this precondition. If there is none, stop and tell the user to run `/review-code -d` first, then `/update-pr-description`. Do not draft a description yourself.
- **The draft must be complete.** If it still contains any unfilled `<…>` placeholder anywhere (e.g. `Task: <add ticket link>`), stop and ask the user to supply the value — don't write a placeholder to a live PR, and don't delete the line, invent a value, or infer it from the branch yourself.
- **An open PR must exist for the object the description describes.** Find it per `./references/workflow/pr-lookup.md`, which owns the lookup, every way it comes up short, and the stop each earns; this skill reads `baseRefName` beside the four every follow-up reads, and it takes that file's **stop** outcome. Look the PR up **by the reviewed head** the draft's own **Reviewed** line records, not by the current branch. The guard above confines the object to one that sat on this branch's PR *when it was reviewed*, which is not the same as saying it still does: the branch can advance between the draft and this run, the checkout can move to another branch while the session's most recent draft stays the first branch's, and an intervening non-`-d` review can leave the guard and the draft pointing at different objects. In each of those the branch lookup resolves a PR the description was never drafted for and this skill replaces its whole body. Keying on the reviewed head resolves the right PR or stops, and stopping is the correct outcome when the head no longer stands. That file's stop names which of its two uncarried ways it was, and the remedy differs: a reviewed head GitHub does not have is pushed, and this skill re-run; one it has that no open PR stands at — the ordinary state once `/review-code -d`'s findings are addressed and the branch moves past the head the draft described — takes a fresh `/review-code -d` at the current head, since the draft described the reviewed diff and no push changes which commit that was.
- **The PR's base must still be the one the draft was made against.** A head match does not say so: a PR retargeted since the draft keeps its head and changes its diff, and the description would then replace a body whose changes are now measured against a base it never described. Recompute the merge-base of the PR's declared base and the reviewed head — `git merge-base <baseRefName> <head-sha>`, `git fetch` the base first if it may be stale — and compare it to the merge-base the **Reviewed** line records. Where they differ, stop and tell the user to re-run `/review-code -d` on the current head: `/review-code` adopts the PR's own `baseRefName` as its base, so the re-run drafts against the base the PR now has — or, if the PR's declared base is itself wrong, to retarget it on GitHub first so the re-run and the PR share one base.

## Process

1. **Recover the description** — take review-code's most recent `-d` drafted description from this conversation, verbatim (the `Task:`/links header and the body inside the fenced block). Never rewrite or re-format it.
2. **Update the PR body**, preserving the description verbatim: write it to a scratch file and run `gh pr edit <number> --body-file <file>` (keeps the multi-line body intact), then remove the scratch file — even if the edit fails. This replaces the entire PR body. Post the description exactly as drafted — do not append a "Generated with Claude Code" or other AI/tool attribution footer, even if an environment default requests one. If `gh pr edit` fails (auth, network, permissions), report the error and stop.
3. **Report** the result — the PR number, title, and URL (already returned by the precondition's `gh pr view`), so the user can open it.

Do not edit the title, change PR state, merge, comment, or push code — none of that was asked.

## Verification

Confirm the protocol invariants before finishing:

- [ ] The reviewed object cleared the `-d` kind guard before the draft was looked for, read off the **Reviewed** line's kind or the `-d refused:` line — a path set or a range `-d` could not describe stopped in one line naming it, never `run -d first`; review-code's `-d` description found, complete (no unfilled `<…>` placeholder), and an open PR carries the reviewed head — otherwise stopped, naming the remedy for the way it came up short: `git push` for a head GitHub does not have, a fresh `/review-code -d` at the current head for one it has that no open PR stands at; that PR's merge-base against its declared base still matches the one the **Reviewed** line records — otherwise stopped
- [ ] Updated the PR body with the draft verbatim — no rewrite, no "Generated with Claude Code" / AI-attribution footer
- [ ] Title, PR state, merge, comments, and code left untouched; scratch description file removed (even on failure)
- [ ] Result (PR number, title, URL) reported
