## Core Rules

1. Read `./AGENTS.md` and apply its rules — the domain-neutral core.
2. This is an engineering skill: also read `./references/engineering/rules.md` and apply it on top of the core.

One command for the full review pipeline: review the object (`review-code`) — the current branch against its base with no argument, or the commit range or path set the invocation names — batch the findings by concern (`triage-findings`), then verify each batch in an isolated read-only probe running the `verify-issue` protocol — cold eyes per batch, uncolored by the session that wrote the findings. The final display is the triage frame with one verdict per finding.

`./references/workflow/verify-pipeline.md` owns the mechanics this pipeline shares with the kit's other verify composite — the pipeline-wide overrides every phase runs under among them. Read it; the sections below carry only what is specific to this one.

**CRITICAL**: The whole pipeline reads and displays. No phase edits code, posts to the PR, or writes to any source — the guarantee `triage-findings` and `verify-issue` each carry individually, held end to end.

## Flags

`-n N` (independent reviewers) passes through to the review phase, and its per-return machinery survives the suppressed settle: the two intake checks and the drop rule in `./references/workflow/reviewer-contract.md` § *The settle* run per return, and the standing returns pool by location inside phase 1 — deduped by distinct claim within each location group — so phase 2 batches one candidate per distinct claim carrying its `cited by k/N` marker. Only the adopt, spot-check, and final-verdict steps are suppressed — the ones phase 3 would pay for a second time. Pooling before the batches is what keeps N reviewers from costing N verdicts on one location.

`-x` (cross-vendor second review) and `-d` (draft PR description) pass through to the review phase — see `../review-code/SKILL.md` — with one suppression: under this composite the review phase does not verify the `-x` probe's novel candidates on its own read (`./references/workflow/agent-fanout.md` § *Merge contract*), since phase 3 verifies every finding the review hands forward, probe-sourced ones included, and settling one twice pays twice for the same verdict. The suppression is unconditional: a finding phase 3 later scopes out of probe range takes `Unverified (out of probe scope — candidate never settled)`, so a suppressed settle is never read as a probe-budget call. Those candidates still merge as candidates and reach the batches like any other finding. The per-batch verify probes verify batches after the review rather than reviewing the diff during it. `./references/workflow/verify-pipeline.md` § *Flags through the review phase* covers what these flags carry into the pipeline beyond that suppression.

## Setup

Resolve the object per `../review-code/SKILL.md`'s Setup — its grammar, its kinds, and the identity it records — and hand it to phase 1 so it isn't resolved twice; the check below needs the object and its kind both.

Then confirm the working tree carries no uncommitted change — staged, unstaged, or untracked — at a reviewed path: no path of the reviewed set appears in the working-tree change set, the union of `git diff HEAD --name-only` (every tracked change, either side of the index) and `git ls-files --others --exclude-standard --full-name` (untracked files, including a reviewed path deleted on the branch but re-created untracked in the tree). The reviewed set is `git diff --name-only <merge-base>...<head>` on a `pr` object, whichever of the two forms Setup resolved it from, and the `git ls-files --full-name --error-unmatch -- <paths>` listing on a `paths` object. Every command here runs at the effective root and every listing is root-relative, `--full-name` being what makes the two `ls-files` calls so: `git diff --name-only` already prints root-relative paths while `git ls-files` prints cwd-relative ones, so unpinned the union compares two path forms and a run started from a subdirectory matches nothing — the precondition then passes on a tree that diverges at a reviewed path, which is the one thing it exists to catch. The phase-3 probes read the live tree, so an uncommitted edit — or an untracked re-creation — at a reviewed path means they verify content the reviewed object never carried. A range object needs one condition more: where the reviewed head `b` is not `HEAD`, a commit between `b` and `HEAD` that touches a reviewed path puts content at that path the object never carried, and neither `git diff HEAD` nor the untracked listing sees it, the change being committed rather than sitting in the tree. So on a range, confirm `b` is an ancestor of `HEAD` and that no commit in `b..HEAD` touches a reviewed path; a commit that does fails this precondition exactly as an uncommitted edit does, and needs the object re-resolved against the current head before the pipeline runs. A range on another branch fails the ancestry condition too, though nothing moved under it — standalone `/review-code` reviews such a range and this composite does not, because its phase-3 probes read the live tree, and only a `b` in `HEAD`'s history lets the ancestry check say that tree carries the range's reviewed paths as `b` had them. Reviewing it needs that branch checked out, or the standalone skill.

That is this composite's instance of the shared tree-agreement precondition, whose standing and whose relation to a standalone `/review-code` run are `./references/workflow/verify-pipeline.md` § *The tree-agreement precondition*. Under `-x`, a phase-3 catch would waste a cross-vendor probe along with the review. The diverging paths named on a failure here need committing or stashing first.

## Phase 1 — Review

Run it per `./references/workflow/verify-pipeline.md` § *The review phase*, which owns the delegated pass and its fallback, the suppressed standalone settle — its two intake checks per `./references/workflow/reviewer-contract.md` § *The settle* still run first, the same trade the Flags section makes for the `-x` probe's candidates — the pooling that stands in for the suppressed steps under `-n N`, and the no-findings shortcut. The review skill is `../review-code/SKILL.md`, executed end to end against the object Setup already resolved. Three lines print as the phase completes: its **Summary**, its **Reviewed** provenance line in whichever form its kind takes, and its **Review pass** line, which carries every `reviewer <i> dropped` entry the phase recorded.

## Phase 2 — Triage

The whole phase is `./references/workflow/verify-pipeline.md` § *The triage phase*, run over the findings phase 1 held.

## Phase 3 — Verify

First re-confirm the reviewed identity in the form its kind takes. On a `branch` object — the no-argument `pr` form — the object's own head expression still resolves to the reviewed head (`git rev-parse HEAD`), and the merge-base recomputed against Setup's own base still matches the reviewed merge-base: Setup's base, never the PR's `baseRefName`, which `publish-pr-review` recomputes from on a `branch` object and compares against the recorded base on a `range` one, because it holds no Setup of its own to ask. A `range` object's recorded identity is constant by construction — Setup resolved `b` to a SHA once and took the base as `merge-base(a, b)` over two immutable commits — so `git rev-parse --verify <b>` and a recomputed merge-base each hand back the recorded value whatever moved under the pipeline, and comparing either proves nothing. Setup's ancestry condition is what re-runs for a range instead: `b` is still an ancestor of `HEAD`, and no commit in `b..HEAD` touches a reviewed path. That is the range's whole identity re-check, because a commit landing on `HEAD` mid-pipeline is the one way content the object never held reaches a reviewed path without Setup's working-tree check seeing it — the change is committed rather than sitting in the tree — and a comparison of constants would not see it either. It guards the reviewed paths, as the working-tree half does on every kind, and not the rest of the tree the probes may read past them. On a `paths` object: `git rev-parse HEAD` still matches the reviewed head, and the digest recomputed over Setup's own pathspecs still matches the reviewed digest, since a directory or glob pathspec can gain or lose a tracked file under a HEAD that never moved. Setup's working-tree check still passes on every kind. All of it held when the review started, so a mismatch now is genuine drift — something moved under the pipeline. Any → stop and report: probes read the live tree, verdicts against a moved tree describe code the review didn't see, and a moved merge-base or digest, or a commit landed over the range, means the reviewed object is no longer the one on disk.

This skill fans out under `./references/workflow/agent-fanout.md`, `./references/workflow/probe-engines.md`, and `./references/workflow/probe-shape-verify.md`. Fan out, merge, and degrade per `./references/workflow/verify-pipeline.md`, handing every probe prompt the **review object** its kind names — the reviewed diff, Setup's resolved base to the reviewed head, for a `pr` object, and the reviewed paths at the reviewed head SHA for a `paths` one, each as `./references/workflow/probe-shape-verify.md` shapes it. Two additions to the merge: a **Withdrawn** finding is out of scope for `publish-pr-review`, and an adopted probe candidate enters the publishable list its own severity names — **Findings** at Major/Critical, **Minor findings** at Minor — besides **Batches** and the **Verified** count.

## Output

Lists, never tables.

- **Summary** — what changed, intent, and the overall assessment restated after verification — verdicts are evidence and may move it; the session owns the final call. The assessment is the approve / request changes / needs discussion call on a `pr` object and the health verdict `../review-code/SKILL.md`'s Output fixes on a `paths` one.
- **Batches** and **Verified** — as `./references/workflow/verify-pipeline.md` § *Output: Batches and the Verified line* specs them, `Batches` here taking the whole reviewed object as its no-anchor locator and carrying one entry per distinct claim — a location that drew two different defects keeps both — each with the `cited by k/N` marker phase 1 pooled it under where N reviewers ran; the Verified line counts those pooled candidates, not one per return. An out-of-probe-scope verdict carries the annotation the Flags section fixes.
- **Findings** — the publishable list, in `review-code`'s Findings format: every surviving Major/Critical finding — verdict Confirmed, Inconclusive, or Unverified — with its severity, `file:line`, and original text verbatim. A verdict other than Confirmed rides along as a closing note on the entry — `(Inconclusive: <what's missing>)` / `(Unverified: <reason>)` — and counts as part of the finding's text downstream, so `/publish-pr-review` posts the caveat with the claim instead of giving an unsettled finding a confirmed one's authority. Withdrawn findings are excluded here; their evidence lives in Batches. `/publish-pr-review` consumes this section and **Minor findings** below, one severity tier each; write `none` when nothing survives — a `none` here is what lets the follow-up approve rather than request changes.
- **Minor findings** — the same publishable list at Minor severity, in `review-code`'s Findings format and under the Findings rules above: every surviving Minor — verdict Confirmed, Inconclusive, or Unverified — with its severity, `file:line`, and original text verbatim, a non-Confirmed verdict riding along as the same closing note (`(Inconclusive: <what's missing>)` / `(Unverified: <reason>)`) and counting as part of the finding's text downstream for the same reason. `(Unverified: out of probe scope)` is that note where a large set had the probes scoped to Major/Critical, and it travels like any other. Withdrawn findings are excluded here too; their evidence lives in Batches. Minors are listed individually and never capped, exactly as `review-code` carries them — a collapsed block is a tier the follow-up cannot count. Write `none` when no Minor survives.
- **Cross-check** (only with `-x`), **Improvements**, **Inaccessible context** (only if any), **PR description** (only with `-d`) — forwarded from the review phase as `review-code` specs them. Improvements are non-blocking suggestions, not findings — they pass through unverified.
- **Reviewed** — the provenance line exactly as `review-code` specs it, in the form its kind takes: `Reviewed <kind> at <head-sha> (merge-base <base-sha>) by <model>` on a `pr` object, `<kind>` being `branch` or `range`, and the `paths` digest-and-file-count form on a `paths` one, the model carrying its `×N` where a fleet produced the pass. `/publish-pr-review` reads that line to anchor, and reads the kind off it to pick which base its currency check compares against.
- **Review pass** and **Divergence** — forwarded from the review phase exactly as `review-code` specs each, on the terms `./references/workflow/verify-pipeline.md` § *Output: Batches and the Verified line* adds.

**Next:** on a `pr` object, `/publish-pr-review` offers the **Findings** and **Minor findings** lists above, and **Improvements**, as severity tiers and posts the one you select — Withdrawn are already excluded from both lists, and with nothing in any of them it posts a short approval instead of asking — a clean `range` object posting that as a comment naming what the range covered, since an approval would speak for the whole PR; a `paths` object sits on no PR, so publishing does not arise on it and its findings go to `/fix-findings` below instead. With `-d`, `/update-pr-description` applies the drafted **PR description** to the PR. Or address the batches with `/implement-task` or `/fix-findings`, then `/commit`; the PR's next review pass certifies them.
