## Core Rules

1. Read `./AGENTS.md` and apply its rules — the domain-neutral core.
2. This is an engineering skill: also read `./references/engineering/rules.md` and apply it on top of the core.

Review the object Setup resolves — the current branch's diff against its base with no argument, or the commit range or path set the invocation names — for correctness, unintended impact, and adherence to project patterns.

## Flags

- `-n N` — Launch N independent reviewers over the identical review object rather than one, and pool their returns into a single findings list before verdicts are assigned. Default 1; the count is the user's and carries no ceiling, but its form is fixed — N is a positive whole integer, and a `-n` carrying anything else (a zero, a negative, a fraction, a nonnumeric token, or no value at all) stops the review with a question rather than guessing a count, since a run with no reviewer 1 runs none of the project's verification scripts and matches no branch below. Only reviewer 1 runs the project's verification scripts, so a review runs them once whatever N is; the links Setup extracted are not deduplicated the same way, so N reviewers fetch each of them once apiece — the packets are identical by design, and varying that to save the fetches would put the reviewers on different context and make their agreement meaningless. Everything N above 1 adds — the pooling marker, the completed/requested coverage record, the per-return drop rule — is absent at N = 1, where the pass is the single-reviewer pass the rest of this file describes. A count large enough to read as a stray digit rather than an intent is confirmed before launching, the same question the malformed value above earns and for the same reason — that is the one check on the count, not a ceiling on it. Independent reviewers over the identical object corroborate by agreement, where partitioning one pass across per-lens probes left no claim cited twice.
- `-x` — Cross-check: launch one independent cold review of the same object on the cross-vendor engine and merge it before findings are finalized, per `./references/workflow/probe-cross-check.md` on the cold-review shape in `./references/workflow/probe-shape-cold-review.md`, under the shared contract in `./references/workflow/agent-fanout.md`, with the engine and its launch recipe in `./references/workflow/probe-engines-cross-vendor.md`. Off by default. The probe is read-only; its outcome is recorded on the output's `Cross-check:` line. <!-- cold -->
- `-d` — Draft a ready-to-paste PR description (body only) in addition to the review, per the "PR description" section. The session drafts it on either pass; the reviewer returns none and is never told the flag is set. Off by default. Where that section refuses the draft, the refusal is one line — `-d refused: <reason>`, the reason naming the object's kind or the range endpoint that earned it, its head or its start above the base — rendered where Output's **PR description** item would have gone, with the rest of the review unchanged.

## Setup

**Resolve the object.** Flags and `-n`'s value are consumed from the argument list before the object is read, and `--` terminates the object's own tokens rather than the whole argument list — so `-- <path>… -n 3` names one path set and a count, not three pathspecs. What remains after that is the object. With no argument the object is the current branch's diff against its base: run **Determine base branch** below and take `<base>...HEAD`.

With an argument, **select the form before applying it.** Probe what remains bare and positional both ways — as pathspecs (`git ls-files --error-unmatch -- <tokens>`), and as a rev or range by splitting the token on `...` or `..` and running `git rev-parse --verify <endpoint>^{commit}` on each side (a bare token being a single endpoint) — and read the two answers together, because each probe's failure is only evidence about its own form. `--verify` takes exactly one parameter and refuses anything resolving to more than one revision, so handing it `a..b` whole fails on every range and would leave the range form unreachable; the `^{commit}` peel rejects a blob outright and resolves an annotated tag to the commit the head anchor downstream compares against. **A token that resolves both ways — a branch and a directory sharing a name — stops and asks instead of guessing**, and the answer settles that one invocation; git itself refuses the same token (`fatal: ambiguous argument … Use '--' to separate paths from revisions`) rather than picking a side. `--` is what selects the path form outright where the question is not wanted. Everything after a `--` is a path set whatever it looks like, and no other probe runs. Only once a form is selected does its own failure stop the review; a probe that fails while the other resolves has merely ruled its form out, and an argument no form claims stops with a question — what was meant is cheap to ask and expensive to guess.

The selected form is one of:

- **A path set** — arguments naming tracked paths under the repository root, and everything after a `--`. The object is the tracked files the index lists under those paths, from `git ls-files --error-unmatch -- <paths>`. That listing is the index's, not HEAD's, while every read of the object downstream — the packet at the head SHA, the reviewer's spot-check, the `-x` probe — is pinned to the head commit, and nothing downstream compares the two anchors, so Setup does: `git diff --cached --name-status --no-renames HEAD -- <paths>` names every reviewed path where the index and the head commit differ, and each state it reports reads from one anchor and is recorded from it. A staged addition (`A`) is in the listing and the digest but has no content at the head SHA, so there is nothing at that path for a spot-check or a probe to read: record it under **Divergence** as staged-only with no content at the head, and settle a Critical or Major finding there by the verify route `./references/workflow/agent-fanout.md` fixes rather than by a spot-check with nothing to read. A `git rm --cached` path (`D`) is the reverse: the head commit carries it, the listing does not, and nothing else in the pipeline would say so — record it under **Divergence** as dropped from the index though in the head commit, so the file count Output renders reads against that record rather than as the whole of what the head commit holds under those paths. A staged edit (`M`) is in both and reads from the head SHA like any other reviewed path, its on-disk divergence the reviewer's to record. An unmerged path is listed once per stage and counts once per stage in the digest below. Once this form is selected, exit 1 stops the review before anything is launched, naming every pathspec that matched nothing: one that exists on disk but is untracked is committed first, and one that is absent is a typo or a glob that matched nothing. Any other non-zero exit is reported as the git error it is.
- **A range** — `<a>..<b>` or `<a>...<b>`, or a single rev standing for `<rev>..HEAD`, a rev being whatever `git rev-parse --verify <rev>^{commit}` accepts, which resolves an annotated tag to the commit it points at and rejects a blob outright. Either range form reviews the diff from `merge-base(a, b)` to `b`, so the two-dot and three-dot spellings name one object here — a redefinition of Git's own `a..b`, so echo the resolved object back before reviewing (`reviewing <merge-base>...<b>`) rather than leaving the user to discover it in the output. The single-rev form is also how a base is named by hand — `main` reviews the diff the no-argument object would resolve against that base — and what it costs is the kind: the object is a `range`, which `/publish-pr-review` posts as `COMMENT` whatever it covered, so a review meant to approve the branch runs with no argument and lets **Determine base branch** find the base instead. **Resolve `b` to a SHA here, once** — `git rev-parse --verify <b>^{commit}` — and use that SHA everywhere `b` is afterwards recorded or compared: the identity below, the PR lookup, the packet, and the provenance line. A symbolic `b` compares equal to no SHA, so leaving it unresolved silently loses the PR context and hands `publish-pr-review` and the verify composite a head they cannot match; the peel is what keeps that recorded SHA a commit, since an annotated tag's own object SHA is what all four would carry and it matches nothing in the head-keyed lookup and reaches `publish-pr-review` as a `commit_id` no head can equal. That merge-base is the base, so **Determine base branch** does not run — except under `-d`, whose guard has no other source for the branch's own base: there it runs for that comparison alone and its answer is never adopted as the review base, which stays the merge-base. `-d` is allowed on a range only where `b` is the current branch's HEAD **and `merge-base(a, b)` is that branch's own base**: the description it drafts replaces the whole PR body, so a range starting above the base covers less than the PR does and would silently drop the rest of it. A range failing either condition takes the `-d` refusal the flag entry fixes.

The effective root is the tree the object lives on, and every git command in this Setup runs there — the digest below is not the only cwd-sensitive one, and a Setup that resolves the object from one directory and reports it from another has no single object. **Resolve the review object's identity** below records the identity. The no-argument and range objects make a `pr`-kind packet; a path set makes a `paths`-kind one.

**Determine base branch** (for the no-argument object, and on a range only for the `-d` guard above): if the current branch has an open GitHub PR, adopt its declared base — `gh pr view --json state,baseRefName` (requires `gh`; targets the current branch's PR), taking `baseRefName` only when `state` is `OPEN`. `gh pr view` returns the branch's PR whatever its state, so a merged or closed PR with no open successor would otherwise hand back a stale base — check `state` and treat anything but `OPEN` as no PR (the same guard `/publish-pr-review` applies). That declared base is the exact one `/publish-pr-review` re-checks against (it recomputes `git merge-base <baseRefName> HEAD`), so adopting it keeps the review and the publish step from resolving different bases and looping. Only with no open PR — `gh` missing, no GitHub remote, or no PR in `OPEN` state — fall back to local heuristics: check common ancestors with `main`, `master`, `develop`, or `release/*`, and verify the commit count is reasonable.

**Resolve the review object's identity:** record the object's **kind** — `branch`, `range`, or `paths` — and both the reviewed head commit (`git rev-parse HEAD`, or the SHA `b` resolved to on a range) and its merge-base with the base (`git merge-base <base> HEAD`, or `git merge-base <a> <b>`). The kind is recorded rather than inferred because a range and a branch diff are both `pr`-kind packets and render alike downstream: a consumer that has to tell them apart — `publish-pr-review`'s currency check, `update-pr-description`'s `-d` guard — cannot do it from a head and a merge-base alone, and guessing swaps the object for the checkout's. This stays in-session on every pass — it is the identity the review packet carries and the reviewer echoes back, and the anchor the `publish-pr-review` follow-up depends on: it anchors its posted review to the head and re-checks the merge-base so it never publishes against a retargeted or moved diff. A path set has no merge-base, so its identity is the head SHA and a digest of the reviewed list: `git ls-files --full-name --error-unmatch -- <paths> | LC_ALL=C sort | git hash-object --stdin`, the sorted newline-terminated listing hashed as it stands, computed at the effective root. Both pins are load-bearing, and for one reason: three separate processes recompute this digest — Setup, the reviewer, and a composite's drift re-check — of which only the reviewer's is pinned to a root by its own contract, so anything cwd- or environment-dependent in the pipeline digests the identical object two ways and the identity check stops a review that never moved. What each pin guards is `./references/workflow/reviewer-contract.md` § *Launch packet*, which carries the command to the reviewer. The digest names the exact set reviewed, so the same commit reviewed over different paths is a different object and says so.

**Launch the cross-vendor probe** (only with `-x`): as soon as the object is resolved, start one background probe per `./references/workflow/probe-cross-check.md` on the cold-review shape in `./references/workflow/probe-shape-cold-review.md`, on the engine and launch recipe in `./references/workflow/probe-engines-cross-vendor.md` — a cold second review of that same object at the effective root, demanding findings with severity and `file:line` evidence. Continue the setup while it runs; the probe is read-only, so it may overlap the delegated review pass. Collect and merge it in the Settle, per the contract, before finalizing Findings. <!-- cold -->

**Gather context:**

- Read the commit messages of the object's own commits — the branch's on a no-argument object, and `merge-base(a, b)..b` on a range. A range may end on another branch or a detached commit, where the checkout's history is somebody else's intent and the range's own is what the review needs
- On the no-argument object, and on a range whose `b` is the current branch's HEAD, check for an open PR on GitHub for this branch with `gh pr view --json number,title,body,state,url,comments,reviews,baseRefName` (requires `gh` CLI), taking the result only when `state` is `OPEN` — `gh pr view` returns the branch's PR whatever its state, so a merged or closed PR's title, body, and threads would otherwise enter the review context as live intent, the same guard **Determine base branch** above applies to the same call. It runs on no other range, where the checkout's PR is not the range's and its title, body, and threads would enter the context as the reviewed object's intent. This branch-keyed lookup and that one are one of `pr-lookup.md`'s recorded exceptions to its no-second-copy rule, for the reason it states there: the branch under review routinely has a local HEAD ahead of the pushed PR head, where a head-keyed lookup finds no PR and costs the review both its context and its declared base. If the command fails because `gh` is missing or the repo has no GitHub remote, note that and skip the PR lookup. `baseRefName` is the PR's declared base — the one already adopted in **Determine base branch**; carrying it in the context confirms the review ran against the PR's own base.
- On a range, the PR to find is the one whose head is the SHA `b` resolved to, not the current branch's. Where `b` is the current branch's HEAD the lookup above already finds it; otherwise find it per `./references/workflow/pr-lookup.md`, which owns the lookup, reading the fields listed above. This skill is that file's **no-stop consumer**: coming up short is not an error here — no match, no `gh`, or no GitHub remote means no PR context, and the range reviews on its commits alone. <!-- cold -->
- If a PR exists:
    - Read the PR title, description, and any review comments / discussion threads — these often contain the _why_ behind the change and prior reviewer concerns
    - Extract every URL from the PR body and comments (issue trackers, design docs, Slack threads, RFCs, related PRs, dashboards). Extraction is where the session's link work ends: the URLs travel to the reviewer, which fetches them — the session fetches them itself only on the inline fallback
- If no PR exists, proceed with just the branch commits and any context the user provided
- A path set has neither a PR nor a branch's commits to read: skip both lookups, and its context is whatever the user gave with the invocation

## Review pass

**Launch.** Launch and hand over per `./references/workflow/reviewer-contract.md` § *The launch*, with a packet of the kind Setup resolved, the **Inline fallback** below standing where that section names one. The session puts in the packet:

- the review object named concretely — the `<base>...HEAD` diff, `<merge-base>...<b>` on a range with `<b>` the SHA Setup resolved rather than the symbolic rev the user typed, or the path set as its own paths at the head SHA, never pasted diff or file text — with the identity Setup resolved: the head and merge-base SHAs, or the head SHA and the path-list digest
- the absolute effective working root: the tree that object lives on, which is the worktree when the run is in one rather than the main checkout
- the kind, `pr` or `paths`
- the PR context Setup gathered — title, body, review comments and discussion threads — and every URL extracted from them, as URLs for the reviewer to fetch, or an explicit `none` where Setup found no PR or the object had none to look for; a packet is never launched short, so the absence is stated rather than left out
- the absolute installed paths of the install home's `references/engineering/review.md` (`~/.claude/` on Claude, `~/.codex/` on Codex), the per-surface checklist directory beside it, the engineering overlay `references/engineering/rules.md` in that same directory, and the install home's `CORE_RULES.md`
- any context and constraints the user gave with the invocation — the why behind the change, a focus to take, a constraint to honour — verbatim, or `none`: the session holds them and the reviewer sees no session context, and with no PR they are the whole of the intent Setup gathered
- this skill's § *Review Focus*, verbatim — the review pack does not carry it
- the instruction that the reviewer builds the change map and the blast-radius search itself, and runs the project's verification scripts over the reviewed set — that second half in the per-reviewer form `./references/workflow/reviewer-contract.md` § *Launch packet* fixes once `-n N` puts more than one reviewer on the object

A packet with a missing or ambiguous item is completed by reading or asking, never launched short.

With `-n N`, send the N packets in one message — one turn, N launches, on the primitive `./references/workflow/delegated-waiting.md` § *Per-host primitives* names for this host. They carry the same items, differing on the verification-scripts instruction alone; varying anything else would put the reviewers on different objects and make their agreement meaningless. Announce the fleet as `launched: reviewer ×N (<model>, <effort>)`, both pins read from the installed adapter as `./references/workflow/reviewer-contract.md` § *Adapter defaults* says.

**Wait.** While the reviewer is in flight the session runs no command against the tree — no reads of the diff, no verification scripts, no scratch runs; the reviewer is executing on that same tree. Wait on the harness's completion signal per `./references/workflow/delegated-waiting.md` § *How to wait*, reporting where the launch stands at each check-in. Under `-n N` the ban on touching the tree holds until the last of the N is in, the check-in gives one line per launch, and nothing settles until every launch has returned or failed. The `-x` probe is read-only and may overlap the wait.

**Settle.** The return is evidence, not a verdict — this skill assigns the verdicts, per `./references/workflow/reviewer-contract.md` § *The settle*, read cold at this point. First classify an explicit signal that a safety denial prevented a usable pass under that contract's § *Safety blocks*; it is not a malformed return and takes the **Blocked output** below rather than an inline retry. A complete report that records a denied validation still goes through normal intake with that limit visible. For a returned report, the two intake checks run first, in order, before any settle step: the `Identity` echo against the head and merge-base SHAs Setup resolved, or on a `paths` object against the head SHA and the path-list digest — a mismatch means the reviewer resolved a different object: stop and report, settle nothing, launch nothing — then every return heading present, a malformed return taking the inline fallback below with reason `reviewer failed`. Then adopt, spot-check, and assign the final verdicts as that section orders — `Summary` and `Improvements` pass through uncited, as evidence for Output — and merge the `-x` probe.

Under `-n N`, classify safety-block signals first, run both intake checks per returned report in their existing order, and drop each unavailable reviewer instead of ending a pass that still has a usable return. Record each on `Review pass:` as `reviewer <i> dropped (<reason>)`: `identity mismatch`, `malformed return`, `no return`, `reviewer failed: <error>` for an ordinary returned error, or `safety blocked: <error>`, preserving only the available error code and message in `<error>`. A launch with no return remains `no return`; do not guess that it was safety blocked. Settle on the returns still standing and render their coverage as `completed <completed>/<requested>`. Only once none stands does the pass take a terminal path: any `identity mismatch` among the drops stops the review and reports, settling nothing and launching nothing; otherwise any `safety blocked` drop takes the **Blocked output** below; a set containing only `reviewer failed`, `malformed return`, and `no return` falls to the inline fallback with reason `reviewer failed`.

Losing reviewer 1 ordinarily costs the review its verification scripts as well as its reading, the others having been told to skip them: run the scripts in-session before Output and record `scripts: session (reviewer 1 <reason>)` on that same line. If reviewer 1 was safety blocked, preserve any completed script outcomes and do not repeat the denied operation. Run only checks the available signal shows are independent and already authorized, recording `scripts: session independent checks only (reviewer 1 safety blocked: <error>)`; if the signal does not distinguish the denied operation, record `scripts: unavailable (reviewer 1 safety blocked: <error>)`. That is script handling, never a replacement review — the standing returns still produced the pass with reduced independent coverage.

With `-n N` above 1, the standing returns' findings pool by location before anything is adopted, per `./references/workflow/agent-fanout.md` § *Merge contract*, which owns the grouping and the walk of the sibling branches that follows it. Mark each pooled entry `cited by k/N` — `k` the number of returns making *that entry's claim*, not merely citing its location, and `N` the count `-n` named — and count reviewer returns only in both: a dropped return is one that cited nothing, and an `-x` probe's agreement at a pooled spot belongs to the `Cross-check:` line rather than to `k`. Adoption and the Critical and Major spot-check then run once per pooled group instead of once per return, and the assessment restated in `Summary` is the session's read across the standing returns, their `Improvements` merged. The three remaining return headings take their own rule rather than the singular one Output states for a single pass: `Change map` is reviewer 1's — the one return whose packet differs from the rest, so naming it keeps the `-d` draft reading one map instead of an arbitrary one — and where reviewer 1 is among the dropped, the lowest-numbered standing return's, which keeps that property by naming a successor rather than leaving the draft's only source unspecified in the one case where it is missing; while `Divergence` is the union across the standing returns — plus Setup's own index-versus-head record on a `paths` object, as at N = 1 — and `Inaccessible context` the union across them, since a path only one reviewer found diverging still diverges and a link only one could not reach is still unread. <!-- cold -->

A composite driving this skill stops this settle after the intake checks, per `./references/workflow/verify-pipeline.md` § *The review phase*. <!-- cold --> The `-d` draft is not one of those steps: it is Output's, drafted from the return's `Change map` whatever settles the findings, so a composite forwards it unchanged. Findings adopted here render in the shape `./references/engineering/review.md` § *Findings output shape* defines, which Output already cites.

**Blocked output.** When `./references/workflow/reviewer-contract.md` § *Safety blocks* makes the primary review terminally blocked, stop with `Review pass: blocked (completed 0/<requested>; reviewer <i> safety blocked: <error>; …)`, including every unavailable reviewer's recorded reason and preserving only an explicit safety signal's available code and message. That line — and with `-x` the `Cross-check:` line — is the whole output: no Summary, Findings, **Reviewed** provenance, Divergence, Improvements, Inaccessible context, PR description, or **Next** pointer, since none came from a usable primary pass, and an empty Findings list would be publishable as a clean review. With `-x`, the `Cross-check:` line takes the `unattached (<n> findings; primary pass blocked)` outcome `./references/workflow/probe-cross-check.md` defines where the probe completed, or `skipped (<reason>)` where it did not; never adopt it as the pass or use it to continue into a composite.

**Inline fallback.** Where the reviewer cannot launch or a launched one failed — the reasons `./references/workflow/reviewer-contract.md` § *Degrade rule* closes — announce which it was and run the pass in-session, recording the reason on the output's `Review pass:` line. Only the runner changes: nothing about the review object, the base, or what the output owes moves with it.

Build the change map:

- Get the full diff against the base branch (its identity is already recorded in Setup)
- Exclude generated files (lockfiles, build artifacts, snapshots) unless manually edited
- Group changes by intent: new feature, bug fix, refactor, configuration, tests
- For each modified export or shared component — search all usages to understand blast radius
- If the diff exceeds ~1000 non-generated lines and isn't a single logically cohesive change, the first finding is "split this PR" — large diffs hide bugs and exceed reviewer working memory
- If the diff bundles refactoring with feature work or bug fixes, flag "separate the refactor" — mixed-purpose PRs are harder to review, harder to revert, and dilute commit history. Exception: refactors required _to enable_ the feature, which should be called out in the PR description.
- On a `paths` object the map is the reviewed files grouped by concern instead, with the blast-radius search over their exports unchanged; the two split findings above do not arise, since nothing was proposed to split

Read the links Setup extracted:

- Fetch every extracted link concurrently — parallel fetch calls in one batch (WebFetch for public URLs, `gh issue view` / `gh pr view` for GitHub references), or one native probe batching the retrieval per `./references/workflow/agent-fanout.md` — read it when taking the probe route — and merge what comes back into the review context <!-- cold -->
- If a link can't be accessed (auth-walled, private workspace, 404, tool unavailable), record it in the output under **Inaccessible context** with the URL and reason. Do not fabricate what's behind it — flag the gap so the user can decide whether to paste the content in or proceed without it

Launch verification scripts per "Verification Scripts" in `./references/engineering/review.md` — always: as soon as the reviewed set is determined, launch the project's lint/typecheck/test scripts over it and review while they run; their failures and warnings land as findings before output. `./references/workflow/agent-fanout.md` fixes the route a candidate raised there settles by, that section's reproduction bar and all. <!-- cold -->

Then apply **Review Focus** below and render the output.

## Review Focus

The reviewer applies this focus on a delegated pass; the session applies it on the inline fallback.

**On a `pr` object, examine tests first.** Test diffs reveal intent and expected behavior. Read them before the implementation so you evaluate the code against what it's supposed to do, not what it appears to do.

**On a `paths` object, read the tests for the behavior they intend** rather than examining them first — no diff dates them, so a test file is one more reviewed file, and what it says the code should do is worth more than the order it is read in. Spend the effort where a whole-file read pays: first the exports the rest of the project consumes, then the security surfaces, then the complexity and the dead code that collect where nothing has changed in a while.

Apply the full review process from `./references/engineering/review.md` — its "What to Look For", "What NOT to Flag", "Calibrate Severity", "Approval Bar", "Prioritize Review Effort", and "Don't Rationalize" sections apply to a diff and a path set alike, with § *Reviewing a path set* saying where the second reads differently.

## Output

- **Summary** — What changed, intent, overall assessment (approve / request changes / needs discussion); on a delegated pass restated from the return's `Summary`, its assessment re-read against the settled verdicts. On a `paths` object the assessment is instead a health verdict from the closed set `./references/engineering/review.md` § *Reviewing a path set* fixes — `sound`, `needs work`, `needs discussion` — since nothing was proposed to approve
- **Findings** — in the shape `./references/engineering/review.md` § *Findings output shape* defines: one entry per issue with its severity, `file:line`, recommendation, and impact, Minors in that same shape and the list never capped. That shape is not the publish step's selection rule: `/publish-pr-review` offers the Critical/Major findings, the Minor ones, and **Improvements** as severity tiers and posts whichever you select. With `-n N` above 1 each entry additionally carries the `cited by k/N` corroboration marker the settle assigned it.
- **Reviewed** — a provenance line recording the object's kind, the reviewed head commit and its merge-base (the kind, the `git rev-parse HEAD` or the SHA `b` resolved to on a range, and the `git merge-base` beside it, all from Setup) and the model that produced this review: `Reviewed <kind> at <head-sha> (merge-base <base-sha>) by <model>`, `<kind>` being `branch` or `range`; and on a `paths` object the digest and file count in the merge-base's place: `Reviewed paths <paths-digest> at <head-sha> (<n> files) by <model>`. The kind is on the line because it is the only signal a follow-up has for telling a range from a branch diff — both render the same head-and-merge-base form, and `publish-pr-review` and `update-pr-description` each guard on the difference. The model carries `×<completed>` — `by <model> ×<completed>` — where a fleet request produced that many usable reviewer passes; dropped reviewers are excluded from it, while the Review pass line preserves the requested count and `cited by k/N` keeps N as that requested count. That `<model>` is the reviewer adapter's pinned model on a delegated pass and this session's own on the inline fallback — the same one the `Review pass:` line names. `/publish-pr-review` reads it to anchor the posted review to the head commit, re-check the diff hasn't moved, and attribute it — so attribution survives the model changing between review and publish. A blocked pass emits no **Reviewed** line.
- **Review pass** — mandatory, per `./references/workflow/reviewer-contract.md` § *Degrade rule* and that contract's § *Safety blocks*: `Review pass: delegated (<model>)` when one requested reviewer produced the pass, `Review pass: inline (<reason>)` when the session did, and the **Blocked output** form when no usable primary pass remains after a safety block. With `-n N` above 1, the delegated form reads `delegated (<model> ×<completed>; completed <completed>/<requested>)`, every dropped return is named as `reviewer <i> dropped (<reason>)`, and the script run is named — `scripts: reviewer 1`, the ordinary `scripts: session (reviewer 1 <reason>)` fallback, or the safety-blocked independent/unavailable form above. `<model>` is read as the contract's § *Adapter defaults* says; an inline reason comes from § *Degrade rule*'s closed set. A denied check that a standing return recorded under `Verification scripts` — or that the session's own run met on the inline fallback — is named on this line at every N, so a pass whose always-run guarantee went partly unmet never renders as the clean form: `scripts: reviewer 1 (<check> denied: <error>)` in the fleet form, and at N = 1 the same clause appended to the otherwise unextended line — `delegated (<model>; scripts: <check> denied: <error>)` or `inline (<reason>; scripts: <check> denied: <error>)` — preserving only the error code and message the host supplied. At N = 1 with no denied check, a usable pass keeps the contract's unextended delegated or inline form.
- **Divergence** — the diverging reviewed paths the runner recorded per "Verification Scripts" in `./references/engineering/review.md` — the return's `Divergence` heading on a delegated pass, the session's own record on the inline fallback, and on a `paths` object the index-versus-head record Setup's **A path set** bullet took beside either — each with the context reported at it; `None` when the tree and the index both carry the object
- **Cross-check** (only with `-x`) — the probe's `Cross-check:` outcome line per `./references/workflow/agent-fanout.md` <!-- cold -->
- **Improvements** (optional) — Non-blocking suggestions; on a delegated pass the return's `Improvements`, passed through
- **Inaccessible context** (only if any) — Links from the PR that couldn't be fetched, with URL and reason (auth required, private, 404, tool unavailable). Note which findings might shift if that context were available.
- **PR description** (only with `-d`) — A ready-to-paste description (body only); drafted per the **PR description** section below.

**Next:** on a `pr` object, run `/publish-pr-review` to post this review to the PR — it offers this review's Critical/Major findings, its Minor ones, and its **Improvements** as severity tiers and posts the one you select as inline comments, or a short approval if all three are empty — a clean `range` object posting that as a comment naming what the range covered, since an approval would speak for the whole PR; a `paths` object sits on no PR, so publishing does not arise on it and its findings go to `/fix-findings` instead.

## PR description

Only when `-d` is passed, and only where the object has a PR of its own to carry the description: the current branch's diff, or a range whose `b` is that branch's HEAD **and whose `merge-base(a, b)` is that branch's own base** (Setup's **A range** bullet says why each condition is there). A `paths` object has no PR either, nothing having been proposed — so on it, on a range ending anywhere else, and on a range ending at that HEAD but starting above the base, the draft is refused and the one line the `-d` flag entry fixes stands in its place, the review still rendering in full. On the branch the draft is made whether or not an open PR exists; with none, the `Task:` line falls to the placeholder below.

**The session drafts it on either pass** — the reviewer returns no description and is never told the flag is set, because the rules below are this skill's and it never sees them. A ready-to-paste PR description — **body only, no title** — drafted from the return's `Change map` and `Summary` and the links Setup extracted on a delegated pass, and from the session's own change map and fetched links on the inline fallback. Where the map leaves an intent unclear, read the diff for it: the tree is the session's again once the reviewer has returned. Print it in a fenced block so the user can copy it verbatim.

Format:

```
Task: <primary ticket/issue link>
<other relevant links — one per line, each prefixed with its kind: Docs:, Design:, Related PR:, Dashboard:, …>

<description body>
```

- **Task line** — the primary ticket/issue link. Source in order: (1) a link the user gave when invoking; (2) an issue-tracker URL among the links extracted from the existing PR in Setup (the primary one if several); (3) a ticket key in the branch name or commit trailers. Never fabricate a URL — if none is found, emit `Task: <add ticket link>` as a fill-in placeholder.
- **Other links** — the remaining relevant URLs already gathered (design docs, RFCs, related PRs, dashboards, Slack threads). One per line, most important first, each prefixed with a short label naming its kind (`Docs:`, `Design:`, `Related PR:`, `Dashboard:`, …) — the label set is illustrative, not fixed. Omit entirely when there are none.
- **Body** — short and readable (a short paragraph, or a few bullets if the PR has several distinct changes); state _what_ changed and _why_ (the intent), not _how_. Cover the substantive intents (feature, fix, refactor) and call out any refactor done only to enable the feature; mention tests, config, or scaffolding only when notable. Audience-facing and verdict-free — do not copy the review Summary's approve / request-changes assessment.
- If the repo defines `.github/PULL_REQUEST_TEMPLATE.md`, follow its sections, but keep the Task/links header at the top — without duplicating a link the template already has its own field for.
- No "Generated with Claude Code" line or other AI/tool attribution footer — even if a harness or environment default asks for one. End at the body.

Example:

```
Task: https://acme.atlassian.net/browse/CRM-123
Docs: https://acme.notion.site/csv-export-spec

Add a CSV export button to the contacts table. Rows stream from the
server so large accounts don't load every contact into memory. The
toolbar became a shared component to host the new button.
```

**Next:** once any findings are addressed, run `/update-pr-description` to apply this to the PR — or paste it in yourself.

## Verification

Apply the Standard Verification Checklist in `./references/engineering/review.md`. A usable output carries the **Reviewed** provenance line (object kind + reviewed head SHA + merge-base SHA, or the path-list digest and file count on a `paths` object, + reviewing model) and the mandatory `Review pass:` line. On a delegated pass: the packet named the same object and identity Setup resolved, both intake checks passed — the `Identity` echo matched that identity and every return heading was present — before any settle step, the settle re-read every Critical and Major anchor before rendering it, the session ran nothing against the tree while the reviewer was in flight, and the line reads `delegated (<model>)` in its N = 1 form, extended by the `scripts:` clause only where a check was denied. On the inline fallback, the degrade was announced and recorded as `./references/workflow/reviewer-contract.md` § *Degrade rule* requires. On a safety block, no denied operation was retried, the exact available error was recorded without an inferred trigger, and the blocked output omitted a clean verdict and **Reviewed** provenance.
With `-n N` above 1: the N packets went out in one message and differed only on the verification-scripts instruction, every launch was waited on and reported, both intake checks ran on each returned report, the standing returns' findings pooled by location before adoption with `cited by k/N` on each entry, the line names completed/requested coverage and the scripts' runner or unavailability, every dropped return is named on that line, and every standing return heading resolved by its own rule — findings pooled, `Summary` read across the returns, `Improvements` merged, `Change map` taken from reviewer 1 or, where that return was dropped, from the lowest-numbered standing one, `Divergence` and `Inaccessible context` unioned. If no return stood, identity mismatch retained priority; otherwise any safety block stopped without inline fallback, while ordinary failures still degraded inline.
With `-x`: on a usable pass the probe was merged per `./references/workflow/agent-fanout.md` and the output carries its `Cross-check:` line; on a blocked pass any completed outcome remained unattached evidence and did not replace the primary review. <!-- cold -->
With `-d`: where a usable pass covered an object with a PR of its own to carry the description — the current branch's diff, or a range whose `b` is that branch's HEAD and whose `merge-base(a, b)` is that branch's own base — the session drafted it itself on either runner, to the Format above: the `Task:`/links header, and a body short and readable, stating what changed and why rather than how; body-only and verdict-free, sourcing its links only from those already gathered — a `Task: <add ticket link>` placeholder rather than a fabricated URL — and carrying no AI-attribution footer. Where the **PR description** section refused — a `paths` object, a range ending anywhere else, or a range ending at that HEAD but starting above the base — no draft was made and the one line `-d refused: <reason>` stands where Output's **PR description** item would have gone, its reason naming the object's kind or the range endpoint that earned it, its head or its start above the base. A blocked pass emitted no draft under **Blocked output**.
