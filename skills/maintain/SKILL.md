## Core Rules

1. Read `./AGENTS.md` and apply its rules — the domain-neutral core.

The monthly maintenance ritual: one command that keeps the kit and its task store from drifting between audits — the R6 recommendation of the July 2026 workflow audit, "maintenance has no owner; give it one." It runs these operations in order — a format-conformance sweep of the kit's task folders, a health sweep across the registered roots, the two install homes, and the task worktrees beside the kit checkout, a listing of the active tasks for handoff, and a misbehavior triage of the Claude and Codex sessions written since the last run — then reports what it found and hands the fixes back to you. It operates on the task-folder **envelope**, its lifecycle bookkeeping, store artifacts, and the host session logs, not on any task's domain *content*, so it resolves no `**Domain:**` pack, delegates to no skill, and reconciles nothing: the docs→reality reconcile of a task's own content is `resume-task-reconcile`'s job, handed off in **Next** rather than run here.

Every phase runs inline against the reference contracts it names. Two overrides apply pipeline-wide:

- **Chat display** — the final **Output** owns the consolidated report; each phase prints only a one-line progress note plus any inline confirmation gate it requires (a gate is a mutation control, not display to suppress — it must reach you).
- **Next pointers** — the Output owns the single **Next**.

Past these two, a phase departs from the contract it names only where its own section below says so — never by improvisation.

**CRITICAL**:

- **Report-first; gate every mutation but one.** Exactly one change applies without a prompt: the `.maintain-last-run` marker rewrite, because it is this skill's own derived run metadata — the date it last swept the session logs — rather than task content, and a run that reports without moving it leaves the next run re-reading the same window. Everything else — format fixes, the archive batch move, the `setup.ts` rerun, the worktree-husk removals, the session-findings file, folder removals — is previewed and applied only on its own confirmation, or handed off in **Next**. Never auto-apply a doc edit, never auto-delete. Every health check and every session read is **detection-only**: finding drift or misbehavior authorizes reporting it, never repairing it outside a gate.
- **Never commit; one gated removal and the fetch its predicate runs are the only git writes.** No add, commit, push, or checkout in any repo, and the dirty paths `git status --porcelain` names are **reported only**, never staged, committed, stashed, or reverted. The gated write is Phase 2's worktree-husk sweep removing a spent task worktree and its branch, or that branch alone where no worktree survives: the task branch-and-worktree lifecycle, sanctioned for a skill whose CRITICAL block names it among its writes — as this bullet does — scoped to that lifecycle alone and fired only on the per-item confirmation that gate requires. That sweep's **merged** predicate also runs the branch-scoped `git fetch origin <default-branch>` that lifecycle carries as its one exception, moving the default branch's remote-tracking ref and no other; it establishes what the gate is asked about, so it precedes the confirmation rather than following it. Everything else stays working-tree only; you review with `git diff` and commit yourself.
- **Coverage is partial by design.** Of R6's six operations this ritual runs three — the format sweep, the deploy-drift check (Phase 2's install probe), and the worktree-husk sweep (Phase 2's husk probe and its gate). One — memory GC — has no backing procedure yet and is **not run**; name it in the Output (see **Deferred**) rather than skipping silently. The fifth, the docs→reality reconcile, is wired but deliberately not run here: it is handed to `resume-task-reconcile` in **Next**. The sixth, the store-index refresh, is **retired** — a store keeps no standing listing artifact, so there is nothing to regenerate (`./references/workflow/task-store.md` § *Store-level artifacts*).

## Setup — resolve targets

Resolve this run's targets before any phase, and print them as the one setup line. Both come from the **root registry** — `./references/workflow/task-store.md` § *The root registry*, the single home for this machine's paths — and an argument overrides.

- **Kit root** — resolved per `./references/workflow/task-store.md` § *Resolving `<kit-root>`* <!-- cold -->, which owns that rule, with one addition this ritual needs: an argument naming a path that holds `setup.ts` overrides the config, per the paragraph below. Pointing the ritual at an install home rather than the checkout would have Phase 2 compare the source against itself, which is the sharpest form of the mistake that section forbids. This is the source that redeploys — **not** the deployed copy this skill is running out of.
- **Task roots** — every entry in the config's `taskRoots`, each carrying its label. This ritual's own two files — the `.maintain-last-run` marker and any session-findings file — live in `~/.local/state/agents-kit/`, never in a task root and never beside the config: they are per-machine run *state* the ritual derives, not content belonging to any store and not configuration anyone authors. A registered path absent on this machine is skipped and named in one line per that section's rule; the run continues on the roots that resolved.

An argument overrides the config for the target it names: a path holding `setup.ts` is the kit root, any other path is a task root added to the set. With **no config**, say the registry is absent and name `~/.config/agents-kit/config.json` as where roots are declared and `/init-config` as what writes it — then run anyway on the kit's own canonical root, which is derivable from the kit root with no configuration at all and is the fallback every discovery rule already names (`./references/workflow/task-layout.md` § *One task, one flat folder*). Only with **no kit root either** — no `kitRoot`, no `setup.ts` argument — is there nothing to maintain: say so and stop. Guessing a *task* root is still not an option: a hardcoded default that silently resolves to a directory nobody uses is the failure the registry exists to remove, and the kit root is not a guess.

The two **install homes** — `~/.claude` and `~/.codex` — are fixed targets of Phase 2's drift check, never arguments and never asked about: they are where `setup.ts` deploys, so the pair is a property of the kit rather than of this run. A home that doesn't exist is an uninstalled host, reported as such rather than treated as a missing default.

## Phase 1 — Format-conformance sweep (kit)

Bring the kit's own task folders under `<kit-root>/.agents/tasks/` into conformance with the **current** format. The format evolves, so folders written under an older convention drift out of shape; this phase finds that drift, previews it, and repairs only what can be repaired without judgment.

**Derive the format — never restate it.** Read the envelope contracts under `./references/workflow/` at run time and treat them as the only source of truth: `task-layout.md` (folder shape, the role-file set with its exact spelling and casing, link-header targets, discovery) with its satellites — `task-goals.md`, `task-diagram.md`, `task-observations.md`, `doc-task-files.md`, `task-siblings.md` for multi-part siblings, `task-archiving.md` and `task-backlog.md` for the archive and backlog containers — and `task-lifecycle.md` (the `**Status:**` vocabulary, which differs *per file* — check each file against its own column) with its satellite `task-authorship.md` (the `## Current state` liveness rule). When classifying a file whose internal shape another workflow doc owns, read that doc too (`context-schema.md`, `ticket-format.md`, `acceptance-criteria.md`). This skill deliberately carries **no** copy of the format: read each value out of the docs every run rather than against a remembered shape. The one carve-out is recognizing the *legacy* names the docs no longer define — undocumentable by construction, so the transforms below enumerate them; the **current** format still comes only from the docs. If you believe a rule holds but can find no home for it in the docs, surface that gap in the preview and do not enforce it.

**Classify** every directory directly under `.agents/tasks/`, excluding the archive and backlog containers themselves — each is a container, not a task, and each is matched case-insensitively, per `task-archiving.md` and `task-backlog.md`. Assign each exactly one label:

- **conformant** — matches the derived format. An optional file's absence is conformance, not a deviation.
- **structurally-fixable** — deviates *only* in ways a **lossless, content-free** transform repairs: renaming a file to its role name, normalizing a name's case, repointing a link at its `./`-relative role name, or normalizing a container's own case — the archive's when no canonical `Archive/` sits beside it, the backlog's when no canonical `Backlog/` does (`task-backlog.md`). Nothing else qualifies. A file **renames onto a role name** when its role suffix identifies it (`*.plan.md`, `*.result.md`, `*.ticket.md` — match the suffix, never assume the stem is the folder's slug), when only its case is wrong, or when it carries the legacy goals name (`spec.md` / `*.spec.md`) *and* is already goal-shaped; a legacy goals file that isn't is needs-judgment, not a rename. A link **repoints** when it names a file this sweep renames, or when it reaches **this folder's own** role file by anything other than its `./`-relative role name — the `**Header:**` lines *and* the in-body links alike, including a plan step's `([result](./<stem>.result.md#…))`; a rename that leaves either behind strands a dead link. A link reaching *out* of the folder is never repointed: `./` role-name targets are a within-folder convention (`task-layout.md`), so rewriting a cross-task citation retargets it rather than repairing it. The legacy `**Spec:**` header additionally takes the `**Goals:**` label, retired together with the file name it points at — the one label change that qualifies.
- **needs-judgment** — anything that would derive, remap, or delete content: assigning goal IDs, extracting criteria out of a plan, remapping an out-of-vocabulary status, stripping a header that shouldn't be there, writing a missing `## Current state` block, resolving a collision where a *distinct* file already holds a destination role name (a case-only difference is not one — see below), or collapsing an older *grouping* layout (a `PROJECT.md` and/or nested task subdirectories) whose shared context has to be redistributed into each task by hand. Also anything you can't confidently match to the derived format — describe what you saw rather than guessing a transform. The same at root level: two containers of one kind (`archive/` *and* `Archive/`, or `backlog/` *and* `Backlog/` — possible only on a case-sensitive filesystem) are a judgment call, never a rename — flag it and leave both untouched.
- **stray** — a directory holding **no task content at all**: no role file, no file that renames onto one (see **structurally-fixable**), and nothing task-shaped nested inside. Every discovery rule ignores it and `resume-task` never surfaces it. Not a task; flag it for removal and **never auto-delete**.

**Precedence:** any judgment issue makes the whole folder needs-judgment even when structural issues also exist, and the folder is left **entirely** untouched — applying its structural fixes in isolation is the half-migration that strands content. Resolving the judgment issue by hand and re-running picks the structural fixes up safely.

If `.agents/tasks/` doesn't exist, or no folder has a planned operation and no container rename is pending — every folder conformant, or the deviations are all needs-judgment or stray — say so and move to Phase 2, carrying the judgment and stray folders into the Output; don't raise a confirmation gate for zero fixes. Otherwise preview every planned operation as a concrete `old → new` list and apply, on the phase's single confirmation, only what was previewed. Never delete content, never rewrite prose or a status value, never touch anything outside `.agents/tasks/`, and never touch git. A link-header that is still a prose placeholder rather than a link is conformant for its lifecycle state — leave it; linking it to a file that doesn't exist fabricates a dead link. Rewrite only a link's target, never the surrounding prose; the one `**Spec:**` → `**Goals:**` label named above is the sole exception. Carry any anchor over verbatim — it is heading-derived, not name-derived, so it survives the rename untouched. **A case-only difference is the rename to perform, not a collision**: on a case-insensitive filesystem (macOS's APFS) `Context.md` and `CONTEXT.md` resolve to the same path, so don't read the destination as occupied — rename via a temp name if the OS won't do a case-only rename directly. Every transform is idempotent, so a re-run over a conformant folder changes nothing.

Scope limit: this sweep is scoped to the kit's own canonical root, `<kit-root>/.agents/tasks/`, and applies its gated lossless transforms there and nowhere else. The other registered roots are **read** by Phase 2's detection-only probes but never swept: a registered root may be a personal vault or another team's repo, and a ritual that renames files across every root it can see writes far outside what it owns. A kit with no `.agents/tasks/` directory sweeps nothing — say so in the Output rather than reporting the absence as a clean sweep.

## Phase 2 — Health sweep (tasks, installs, git, worktrees)

Find the lifecycle and deployment drift the format sweep can't see: finished tasks never archived, tasks that stopped moving, broken step evidence, results grown past the compaction trigger, deployed copies that no longer match the source, work left uncommitted in either repo, and task worktrees still standing beside the kit checkout after their work landed. Every probe here is **read-only detection** — the only disk changes this phase can produce are its three gates, each previewed and confirmed on its own.

Run `scripts/health-check.ts` from the kit root. `<kit-root>/SCRIPTS.md` § *`scripts/health-check.ts`* owns the CLI forms, the emitted `check` values, and the stdout contract (read that section, not the whole file) — one JSON object with `findings`, `scanned`, `unreadable`, and `unreadablePaths`; task findings carry `{check,path,detail,root}`, while install findings carry `{check,path,detail}`. Warnings go to stderr and the exit status is always 0 so a partly unreadable store still parses. Read the findings out of that JSON rather than re-deriving anything the script already decided — and read `unreadablePaths` with them: an empty findings list over a store the run could not open is not a clean store, so `scanned` is a floor whenever `unreadable` is non-zero.

- **Tasks** — `node <kit-root>/scripts/health-check.ts --result-max-kb <KB> <kit-root>/.agents/tasks <every resolved task root>` — the script takes any number of roots, so pass them all in one run rather than once per root. The kit's own canonical root leads the list unconditionally: Phase 1 sweeps it and Phase 3 lists it, both derived from the kit root alone, so leaving its health to a registry entry would let a config that omits it hide the kit's own stale and unarchived tasks. Drop it from the list only when `taskRoots` already resolves to it — the script skips a root it has walked, but a duplicate argument is still noise in the setup line. With `<KB>` read **at run time** from the compaction trigger in `./references/workflow/reconciliation-compaction.md` § *Compaction (size trigger)*. That file owns the number; this skill carries no copy of it, and the script's own default is a bare-run fallback, not a value to lean on here. Pass no `--stale-days`: the script's default is the threshold this ritual wants. Treat each finding's absolute `root` as its authoritative task-root identity; `path` remains the compact display path prefixed by that root's basename, so never infer identity from that prefix when labeling a finding or deriving an archive move. Its ages come from each folder's `.md` mtimes, so a fresh clone or a bulk touch resets them — say that beside the ages rather than reading a young mtime as recent work.
- **Installs** — `node <kit-root>/scripts/health-check.ts --installs <kit-root> ~/.claude ~/.codex`. Compares the kit source against each deployed home over **marker-owned items, plus kit items with no path in the home at all** — a path that doesn't exist can't be yours, so a skill or agent the kit gained and `setup.ts` never deployed still reports; anything you installed yourself stays invisible either way, with `references/` and `CORE_RULES.md` the one exception — every kit skill resolves into those two, so an unmarked one is reported as the conflict `setup.ts` refuses the whole home over, and rerunning `setup.ts` will not clear it. A home carrying no markers at all is still one `never installed` line, not one per kit file; that line carries the conflict when there is one. This is R6's kit deploy-drift check, wired 2026-08 on this probe rather than on the `setup.ts --check` mode R4 declined.
- **Uncommitted work** — `git -C <root> status --porcelain` for the kit root, for each resolved task root that sits inside a git repository (a root that does not skips its own line; a root nested below a repo's top level still reports that repo), and for every linked worktree the husk probe's own `git worktree list --porcelain`, run from the kit root, names — one listing read once and used by both probes rather than the worktrees enumerated a second way, with a worktree that is itself one of the roots above reported once. A task's working changes land in that worktree rather than in the checkout (`./references/workflow/task-delivery.md` § *Branch and worktree creation*), so a probe skipping them misses exactly the uncommitted work it exists to catch. Report every linked worktree the listing names, the ones whose branch belongs to no kit task included: the husk probe discriminates because its gate removes a branch with each husk, and this probe removes nothing. The two ask different questions of the one list — here whether a worktree holds *dirty content*, there whether it is a spent *husk* to remove — so a live task worktree, out of that sweep's scope by design, is in this one's. Read-only: the paths it names go into the Output and the commit is handed to you in **Next**. The probe runs the status command off the listing alone and opens that contract only where a reader needs what put a task's changes in a worktree. <!-- cold -->
- **Worktree husks** — take the candidates from `git worktree list --porcelain` run from the kit root: every linked worktree it names, wherever that worktree sits. Reading the sibling directory instead would miss one the user moved, and deriving that directory from `<kit-root>` is wrong outright — an argument holding `setup.ts` is admitted as a kit root (§ *Setup*) and a linked worktree holds one too, so `<kit-root>.worktrees/` can resolve one level down inside a worktree, to a path that does not exist. The directory a created worktree lands in is `<main-checkout-path>.worktrees/`, and the main checkout path is that same listing's **first** entry (`./references/workflow/task-delivery.md` § *Branch and worktree creation*). **Then add a second source: the task branches this kit records that no longer have a worktree.** § *Removal*'s partial cleanup leaves exactly that pair — branch standing, worktree gone — and a candidate set keyed on the listing alone could never see one again. Take each folder under `<kit-root>/.agents/tasks/`, the archive container included, read the branch its result file's `**Pointers:**` line records (`./references/workflow/task-delivery.md` § *Branch and worktree creation*, the one home for that fact), and admit it where that branch still exists and no listed worktree carries it. Neither source naming a candidate → there is nothing to sweep, one line, never an error. Identify each entry by its **branch**: the slug that branch carries under the kit's declared pattern (`./references/workflow/task-delivery.md` § *Repo delivery declarations*), resolved to a folder under `<kit-root>/.agents/tasks/`, the archive container included since a finished task's folder is usually already inside it. An entry whose branch resolves to no task folder is **not this sweep's**: a worktree created by hand can stand in this same directory, and its branch is its author's rather than a delivered task's, so name the entry and leave it untouched. A branch-only candidate comes out of a kit task folder instead of being matched back to one, so it meets that same test by construction, and a branch no kit task records is never a candidate at all. Judge the rest against `./references/workflow/task-delivery-edges.md` § *Removal*, which owns both predicates — this skill restates neither, since a second copy is what let the sweep qualify entries the finalization run refuses. A branch-only candidate has no worktree path to preview and no tree for a predicate to run in; that section's resolution step already says what a missing worktree means for each predicate, and this skill copies it no more than it copies them. A husk failing either is reported **not removable** with the failing predicate named, and never reaches the gate below. **A task whose `plan.md` `**Status:**` is terminal but whose branch is not merged is exactly that case**: terminal status — read as Phase 3 reads a status, against the terminal set taken from `./references/workflow/status-transitions.md` at run time — puts an entry in the report and never in the gate. An entry that is neither merged nor terminal is live work and is not reported at all. Every contract this bullet cites is opened only once a candidate exists: with neither source naming one the sweep ends at that single line, and no delivery convention, branch pattern, removal predicate, or terminal set is read at all. <!-- cold -->

If `scripts/health-check.ts` is absent, or `node` is unavailable, skip the two script probes and say so with the reason — never silently, so a skipped probe is never read as a clean result. A root that is not a git repository skips its own status line the same way.

**Gate — archive the finished tasks.** Every `done-unarchived` finding is a finished task sitting outside an archive container, and relocating it is mechanical. Preview the batch as concrete `old → new` lines per the **location-relative** contract in `./references/workflow/task-archiving.md`: `<parent>/<slug>/ → <parent>/Archive/<slug>/`, where `<parent>` is whatever directory holds the folder today — not a canonical root, so a store task archives beside its own area instead of migrating into the kit. That section owns the contract; `archive-task` performs the identical move and a plain `mv` is equally valid per it, which is why doing it here delegates to nothing. Check `<parent>/Archive/<slug>/` for a collision before proposing a line — an occupied destination is a judgment call, so drop it from the batch and report it instead. Drop a kit folder Phase 1 classified **needs-judgment** the same way: that phase leaves such a folder entirely untouched, and archiving it would move work still awaiting a hand repair into a container every content check exempts. Drop a folder whose immediate parent is a backlog container the same way — matched case-insensitively per `./references/workflow/task-backlog.md` — because the mechanical line would nest it at `Backlog/Archive/<slug>/`; whether it activates first or archives out of the backlog is yours, so report it as a judgment item. On the gate's single confirmation move exactly the previewed folders and nothing else; declining leaves every folder where it is. Never edit a moved folder's contents: the move preserves its `./` links untouched, per the same section.

**Gate — rerun `setup.ts`.** Every `install-drift` finding means a deployed home no longer matches the kit source. Preview the drifted paths grouped by home, and warn before asking: `node <kit-root>/setup.ts` overwrites the installed skill and reference files **under any live session**, this one included, so a mid-conversation run can swap the file a running skill is reading. Run it only on confirmation, and only whole — there is no per-path mode. Declining leaves both homes exactly as they are, and the drift stays in the Output either way.

**Gate — remove the worktree husks.** Every removable husk the probe found is a delivered task's vehicle still standing. Preview them one per line — worktree path, branch, and the proof of merge that qualified it, a branch-only candidate carrying no path to name — then confirm **per item**, never as a batch: each removal takes a branch with it, and one answer over a list would carry away the entry you would have kept. A terminal-but-unmerged entry is in the report, not in this preview. Remove a confirmed husk exactly as `./references/workflow/task-delivery-edges.md` § *Removal* fixes it, at the path its resolution step returns, in that section's order and in neither command's forcing form — a branch-only candidate has no worktree to remove and so runs `git branch -d` alone; a command that refuses has caught what the predicates missed, so report the refusal and leave that husk standing. Where the refusal is `git branch -d`'s and this run's own `git worktree remove` had already succeeded, record the partial cleanup and name the surviving branch, as that section requires. Declining removes nothing, and every husk reaches the Output either way. With no removable husk there is no gate to raise and that section goes unread. <!-- cold -->

## Phase 3 — List the active tasks (no reconcile)

Name the folders under `<kit-root>/.agents/tasks/` whose `plan.md` `**Status:**` is non-terminal — reading the terminal set from `./references/workflow/status-transitions.md` **at run time** rather than against a remembered list, and excluding the `Archive/` and `Backlog/` containers (each matched case-insensitively, per `task-archiving.md` and `task-backlog.md`) — a backlogged task is parked by design, so it is not part of the active set. A folder with **no `plan.md`** — a young task holding only a `ticket.md`, `CONTEXT.md`, or a hand-authored `goals.md` (`task-layout.md` § *Discovery rules for skills*) — has no status to be terminal and counts as active: name it `no plan yet`. A list for the **Next** handoff, nothing more: this ritual reconciles no task content and reads no task's `**Domain:**`. Stray and needs-judgment folders are Phase 1's concern and are not repeated here.

## Phase 4 — Session analysis (Claude + Codex logs)

Read the agent's own recent history for the misbehavior no task artifact records: refused tool calls, sandbox and hook blocks, schema-rejected inputs, stuck retry loops, runs you had to interrupt. The two session corpora — `~/.claude/projects` and `~/.codex/sessions` — are fixed targets like the install homes, never arguments and never asked about: they are where the two hosts write their transcripts, so the pair is a property of the environment rather than of this run, and a corpus that doesn't exist is an uninstalled host, reported as such. Everything this phase reads is **detection-only**; the one file it can write is gated, and the marker it moves is metadata about the run itself.

**Window.** Read `~/.local/state/agents-kit/.maintain-last-run` — a single ISO `YYYY-MM-DD` line, this skill's own derived run metadata, written by the marker step below — and take that date as the window's start. Absent, empty, or unparseable → fall back to 30 days before today, and say in the Output which of the two the window came from. A first run has no marker by construction; that is the fallback working, not an error.

**Triage.** Run `node <kit-root>/scripts/session-triage.ts --since <window-start> ~/.claude/projects ~/.codex/sessions`. `<kit-root>/SCRIPTS.md` § *`scripts/session-triage.ts`* owns the CLI and the stdout contract (read that section, not the whole file) — one JSON object `{flagged, remainder, remainderPaths, scanned, sessions, skippedUnknownRecords, skippedUnrecognized, skippedUnrecognizedPaths, unreadable, unreadableDirs, unreadablePaths}`, warnings on stderr, exit status always 0 so an unreadable or unrecognized transcript still parses. Read the ranking out of that JSON rather than re-deriving anything: the script scores each session by its count of *distinct* signal classes and orders by that then recency, so `flagged` already **is** the ranked top slice. `sessions` groups the same in-window files by the `project` each ran in — compare every `project` against the kit root Setup resolved, `~` expanded: equal to it, or starting with it plus `/`, is a kit session, so a run out of a worktree under the checkout counts and one whose `cwd` is a scratchpad does not. A `project` under `<kit-root>.worktrees/` counts too: a worktree sits beside the checkout rather than inside it, and that is where every task the kit delivers on itself is worked (`./references/workflow/task-delivery.md` § *Branch and worktree creation*), so a prefix test alone would file the kit's work on itself as work done elsewhere — the one direction this line must not be wrong in, since it exists to catch the kit over-serving itself. Everything else — a `null` project included — ran elsewhere. Pass no `--top` — the script's default is the depth this ritual wants. If the script is absent, or `node` is unavailable, skip the phase and say so with the reason, never silently.

**Deep-read.** Launch one read-only probe per session in `flagged` — at most the list the script emitted, never a sweep this phase widens on its own — per the probe contract in `./references/workflow/agent-fanout.md`, which owns degrading and merging a probe, with the engine and its launch recipe in `./references/workflow/probe-engines.md`. Two bindings apply on top of that contract:

- **Native engine only; never a cross-vendor probe.** Session transcripts are personal data — your own prompts, pasted file contents, machine paths — and must not leave the machine's configured vendor. The cross-vendor hop is unavailable here on privacy grounds, not on capability.
- **Each prompt carries the session file's absolute path, its matched classes with their counts, and the demand for cited findings** — per finding: the misbehavior class, what the agent did wrong or what failed, a minimal evidence excerpt, and a suggested kit fix **when** the misbehavior traces to a kit skill, reference, or contract rather than to a one-off. Before returning, the probe replaces every credential, secret, token, PII value, proprietary payload, and sensitive path component in the excerpt with `[redacted]`; when redaction would erase the useful signal, it cites the record or line and paraphrases instead. The parent re-checks that sanitization before rendering or writing any probe result — raw transcript text never reaches chat or the findings file. A probe that finds nothing actionable answers `benign`, and its session is reported as triage-flagged-but-benign rather than dropped.

**Account for every flagged session.** A session the triage flagged and this phase didn't read is a fact the report owes you, so there is no silent cap: name by path each session in `flagged` whose probe returned neither a finding nor a `benign` verdict — one that failed, degraded, or never came back — and name the beyond-top sessions from the script's `remainderPaths`, with `remainder` as their count: flagged is flagged, whether or not a probe read it.

**Gate — write the findings file.** The gate carries its own preview, as every gate here does: the per-session findings the probes returned — class, session, sanitized evidence, suggested fix — so the decision is made against what would be written rather than against a tally. Refuse the write until every excerpt passes the parent redaction check above. Then offer exactly one write: `~/.local/state/agents-kit/session-findings-YYYY-MM-DD.md`, dated today, carrying the window used, the per-session findings with their sanitized evidence, and the benign and remainder counts. Check the destination first: if the file already exists — a second run today — the gate says so and the confirmation is explicitly an overwrite, so consent is to replacing that file, never just to writing one. On confirmation write that one file and nothing else, creating `~/.local/state/agents-kit/` if it isn't there; declining writes nothing at all, and the findings still reach you — at this gate, and again in the Output's **Sessions** block. Never write it unasked: the findings are this phase's product either way, and whether they become a store artifact is yours to decide.

**Marker.** Once the phase has finished — findings rendered and the gate answered either way — write today's ISO date as the single line of `~/.local/state/agents-kit/.maintain-last-run`. This is the **only** change this ritual applies without a prompt: derived run metadata owned by this skill, not task content. Write it on a declined gate too — the sweep happened, and the marker records the sweep, not the artifact. Skip it in exactly two cases, each for the same reason — a marker advanced past a window that was never read blinds the next run to exactly the sessions this one missed: when the phase itself was skipped, and when the triage JSON's `unreadable` is non-zero — the transcripts in `unreadablePaths` and every transcript under a directory in `unreadableDirs` alike, since each keeps an mtime the next `--since` would exclude. `skippedUnrecognized` does **not** hold the marker: a file whose host cannot be sniffed would not sniff on a later run either, so gating on it would freeze the window permanently on one stray non-session file — report it and move the marker. On a partial read say so in the Output's *marker* line and leave the file at its previous date, so the next run re-covers the window rather than stepping over it.
