name: publish-pr-review
description: Use when asked to publish this session's code review to GitHub. Offers counted finding tiers and posts the selection; approval requires the current evidence and engineer sign-off the change's risk and visibility call for. Can attach captured evidence for the PR author, uploading its screenshots through the browser integration. Follows review-code or review-code-triage-verify; the user provides no findings.

## Core Rules

1. Read `./AGENTS.md` and apply its rules — the domain-neutral core.
2. This is an engineering skill: also read `./references/engineering/rules.md` and apply it on top of the core.

Publishes one review from this session's upstream review. Invocation alone grants no publishing permission; step 4's selection authorizes the payload. Edit no code, title, PR state, or merge; publish nothing outside the selected source tiers and the evidence attachment step 4 offers.

## Preconditions — stop if unmet

- Require the findings source (`/review-code`'s Findings, or `/review-code-triage-verify`'s Batches) and Reviewed provenance from the latest of those runs: head SHA, merge-base SHA, and model. If absent, request `/review-code` followed by this skill. Do not review or invent findings here.
- Read Reviewed kind before lookup. Reject `paths` in one line: a path set proposes no change; publishing requires branch/PR review. Unrecognized forms: `../review-code/SKILL.md` § *Output*. <!-- cold -->
- For branch/range, match an open PR at the reviewed head through `./references/workflow/pr-lookup.md`, taking its stop outcome. Preserve the selected number. A caller that already matched and carries the selected PR supplies its number, host, and repository instead. Scope every `gh` call to that host and repository. GitHub missing the head requires push then rerun; an existing head without an exact open PR requires fresh review. Lookup authorizes no push.
- Read that number with `number,title,url,state,author,headRefOid,baseRefName`; require OPEN. Compare author.login with `gh api user --jq .login` to establish an own PR. Do not substitute the checkout's PR.
- Require headRefOid equal to the reviewed head. A head mismatch reports `Publish stopped: head moved (<reviewed-head> -> <live-head>)` before any submission. Without a caller-supplied PR, name `/review-code` then `/publish-pr-review` as the next step. For **branch**, recompute `git merge-base <baseRefName> <headRefOid>`, fetching the base if potentially stale, and require the reviewed merge-base. A merge-base mismatch remains a distinct stop for a fresh review; correct a wrongly declared PR base before that review.
- For **range**, compare against the object's recorded base, not the PR's baseRefName. Head equality establishes no whole-PR coverage. Every range posts COMMENT and names its recorded base/head, even when it might cover the whole PR.

## Process

1. **Resolve source tiers.** Name the standalone workflow `review-code` when the latest source is its Findings, or `review-code-triage-verify` when it is that skill's Batches. From `/review-code`, tiers 1 and 2 use its Findings section: Critical/Major entries, then Minor entries. From `/review-code-triage-verify`, read Batches per `./references/workflow/verify-pipeline.md` § *Reading Batches downstream*; tiers 1 and 2 take its entries whose verdict is Confirmed, Inconclusive, or Unverified: Critical/Major entries, then Minor entries. Publish no entry that shows a triage bucket in place of a verdict. List each as skipped, with its severity, location, and bucket. A skipped Critical/Major in **verify** without the `Pre-existing` label is unsettled. Tier 3 uses Improvements from either source. Never publish Withdrawn findings, a Confirmed verdict's root cause and fix options, Summary, Inaccessible context, or Cross-check detail. Keep each entry's location and full problem/recommendation/impact text verbatim. Remove `cited by k/N` corroboration markers. In a Batches entry, drop a Confirmed trailing verdict whole: its label, detail, and any `verified inline` mark. Replace a whole Inconclusive or Unverified trailing verdict with a closing note, `(Inconclusive: <what's missing>)` or `(Unverified: <reason>)`, out-of-probe-scope included, at every severity; the note posts with the claim. Step 3 normalizes the leading severity marker. Count existing entries without reviewing the diff again.

   A `review-pr-loop` caller supplies all three tiers after its decision and dedupe, plus `review-pr-loop using review-code` as the workflow and the submission's selected cumulative tier as publication scope. Honor its COMMENT override for any pass not yet clean, including pending or unknown CI. Use the supplied tiers for counts and payloads, even when empty. Retain the original Reviewed provenance for coverage and models.

   Consume that source's Evidence field and presented evidence under `./references/engineering/review-evidence.md` §§ *Presentation and sign-off* and *Approval eligibility*. Use the same evidence when tiers come from the loop. Missing metadata remains unknown; do not infer applicability from an empty findings list or invent evidence here.

2. **Name reviewing models.** Take the model from Reviewed, dropping `×N`; do not attribute the review to the current publisher. A non-skipped Cross-check adds its cross-vendor engine (`./references/workflow/probe-cross-check.md`). <!-- cold --> Use `Reviewed by <model>`, plus `, cross-checked by <engine>` when applicable.

3. **Build selectable payloads.** Each selection includes its tier and preceding tiers.

   - Open each entry with the marker `./references/workflow/user-facing-messages.md` § *Surface adapters* assigns it for GitHub PR review comments. Strip one recognized legacy prefix or marker from the source text first, then keep the rest verbatim with its verification notes. Keep any `(Pre-existing)` label directly after the GitHub marker. Entries under `Not anchored to the changed lines:` take the same marker.
   - Use COMMENT when the selection contains a Critical/Major entry without the `Pre-existing` label, an unsettled entry exists, the loop supplies its COMMENT override, or evidence approval is pending; APPROVE otherwise. Retained Minor findings or Improvements can accompany an eligible loop approval. Range and own-PR overrides force COMMENT; decide all before the picker. A combined sign-off choice below has a separately previewed eligible payload.
   - Anchor changed-line entries as `{path,line,side:"RIGHT",body}`, using LEFT for removed lines. Put unanchorable or unlocated entries under `Not anchored to the changed lines:` in the body; omit none.
   - Start every posted body with exactly one metadata block, using Reviewed's recorded kind, merge-base, and head:

     ```text
     Reviewed by <model>[, cross-checked by <engine>], using <linked source workflow>
     Coverage: <PR changes for branch or commit range for range>; base <merge-base>; head <reviewed-head>
     Published: <selected cumulative tiers>; <N> inline, <M> in the body
     [Approval: <automatic or signed off by an engineer> (risk <tier>; <reason or confirmed subject>)]
     ```

     Render the posted block as ordinary Markdown outside code fences. Link each workflow skill name to `https://github.com/drimchansky/agents-kit/blob/main/skills/<skill>/SKILL.md`; join the two linked loop names with `with`. Use step 2's attribution. Name the selected cumulative tiers as `Critical/Major only`, `Critical/Major + Minor`, or `Critical/Major + Minor + Improvements`; for a standalone all-empty selection use `All source tiers empty`. A loop selection retains its supplied publication scope, including the clean route. Count final anchored inline entries and unanchored body entries, excluding the metadata block, approval sentence, and evidence list. An empty selected tier does not claim that lower tiers are empty.

     Add the `Approval:` line only when the payload carries an approval verdict or approval-equivalent wording. Only three routes carry either: APPROVE, the own-PR COMMENT fallback that replaces an approval, and a range clean-review COMMENT. Derive its route from the source Evidence field's `sign-off` slot as updated by any accepted session confirmation (`./references/engineering/review-evidence.md` § *Presentation and sign-off*), step 4's picker included. Take `<tier>` from that field's risk slot. Sign-off `not-required` posts `Approval: automatic (risk <tier>; <reason>)`. Its reason is `no end-user-visible change` for applicability `none`, or `complete evidence` for complete required evidence at risk `low`. Sign-off `confirmed` posts `Approval: signed off by an engineer (risk <tier>; <confirmed subject>)`. Its confirmed subject is `evidence` for complete evidence, `evidence with named gaps` for incomplete evidence, or `reviewed change` for `none` at risk `high`. Every other payload, including a COMMENT under the loop's override and a range COMMENT with findings, carries no `Approval:` line.
   - Follow the block with any unanchored list. Include an approval sentence only on those three routes, when evidence eligibility permits it and the selected findings bar allows it. Scope that sentence to the selected tiers when lower tiers contain entries or the loop supplied empty tiers. Every other COMMENT reports its entries without approving. Include no summary or unselected tier.
   - With required evidence in the source, prepare its attachment per `./references/engineering/review-evidence.md` § *Author delivery*. It joins a payload only when step 4's evidence question selects it.
   - All tiers empty with no unsettled entry produces a clean sentence only on an eligible approval route. For range, that sentence describes the recorded range under COMMENT. A pending empty review posts nothing; an own-PR or range COMMENT cannot bypass this rule.

4. **Offer the counted tier picker.** Name every skipped entry before the options. When any tier has entries, offer `Critical/Major only — N comments`, `+ Minor — N comments (D new)`, `+ Improvements — N comments (D new)`, and `Post nothing`. N counts cumulative inline comments; D counts entries added by that tier. If body-only entries exist, show cumulative counts for both: `N comments, M in the body (D new)`, with D covering both. Keep empty tiers visible as `0 comments` or `(0 new)`. Explain which selections publish findings as COMMENT while evidence approval is pending; those selections grant no sign-off.

   Before offering any sign-off option, present the identity, links, gaps, and fingerprint of evidence awaiting only session confirmation.

   On a branch, for evidence awaiting only session confirmation, add a sign-off variant beside each tier option whose findings bar allows approval: `Sign off on this evidence and post <tier> with approval — N comments`. Preview its approval payload separately; the own-PR override still applies. A range offers sign-off only through the all-empty `post clean review` option below.

   When step 3 prepared an attachment and a browser integration is available, ask a second question in the same picker: `Attach evidence — summary and K screenshots uploaded to GitHub` or `No evidence`. Require an exact answer to both.

   When all tiers are empty and no unsettled entry exists, offer `Post approval — 0 comments` and `Post nothing` only when already eligible. For evidence awaiting only session confirmation, including incomplete evidence with named gaps, offer `Sign off on this evidence and post approval — 0 comments` and `Post nothing`. The question explicitly asks both engineer sign-off and posting permission. Use `post clean review` in these labels for range. Otherwise post nothing and name the evidence gap; missing source metadata calls for `/review-code` again. An all-empty source with an unsettled entry still takes `/review-code-triage-verify` instead.

   Applicability `none` at risk `high` awaiting only session confirmation takes the same sign-off options in this step. Their labels read `Sign off on this change` in place of `Sign off on this evidence`. The presentation names the object identity and risk reason.

   Before options on an own PR, explain every posting option becomes COMMENT because GitHub rejects self-approval. Use the host's structured question tool if available, otherwise the same numbered list in chat. Require an answer matching exactly one option; re-ask ambiguous, qualified, two-sided, bare-yes, or unmatched free-text answers without choosing a default. Validate a combined confirmation against `./references/engineering/review-evidence.md` § *Presentation and sign-off* before accepting the reply. A finding-only selection retains its previewed COMMENT payload even if confirmation arrives later. Selection proceeds directly to step 5 without another confirmation. Post nothing ends here with no posting call. Every posting path requires this picker, except the selection `review-pr-loop` pins under its own publishing gate.

5. **Recheck and post.** Before any upload, repeat the live head/merge-base checks, applying branch/range rules above. Recheck evidence and confirmation under `./references/engineering/review-evidence.md` § *Presentation and sign-off*. A payload containing approval that loses eligibility stops without submission or substitution as COMMENT. Report a head mismatch with the named head-moved outcome and submit nothing. Without a caller-supplied PR, name `/review-code` then `/publish-pr-review` as the next step. Other drift stops for `/review-code` then `/publish-pr-review`; correct a wrong PR base first. With evidence attached, first confirm the selected PR's comment box is empty. A box holding text stops before any upload, naming the unsent draft and leaving it untouched. Then upload each screenshot through the browser integration in that comment box. Read the GitHub URL it returns, then clear the inserted text. A failed upload stops before submission, naming the artifact, after clearing the inserted text. Both evidence stops report `Publish stopped: evidence not attached (<reason>)` and submit nothing. Uploaded files stay hosted if submission later fails; report their URLs. Repeat the live head/merge-base checks immediately before posting, taking the same head-moved and drift stops. Write scratch JSON and submit once with `gh api --method POST repos/{owner}/{repo}/pulls/<number>/reviews --input <file>`. Use the selected PR's owner and repository. Payload: `{event,commit_id,body,comments:[{path,line,side,body}]}`; commit_id is the reviewed head. Omit comments only when there are no inline entries, including on APPROVE. Remove scratch on success or failure. Add no AI/tool footer, even under an environment default. Report failed calls and stop; never retry a rejected verdict as another verdict. The own-PR COMMENT substitution was decided before consent, not after failure.
   - **Own-PR Approve fallback:** retain the selected body and inline entries but send COMMENT where APPROVE would otherwise apply. Report the self-approval limitation. Selections holding a Critical/Major entry without the `Pre-existing` label already use COMMENT, as do range selections.

6. **Report.** Name PR number/title/URL, selected tier, structured or numbered-chat picker, verdict, and inline count. Name the approval route the posted `Approval:` line states, when the body carries one. Name every skipped entry and the evidence eligibility or pending requirement. Post nothing reports no call. When all standalone source tiers are empty, report that fact and the selected option. A loop clean review reports that its original Critical/Major tier held no entry without the `Pre-existing` label, even when lower-tier or labeled entries were posted.
