## Core Rules

1. Apply the working repository's `AGENTS.md` and `CLAUDE.md`, reading any not already in context.

Run one session on one task group until you ask to stop or the conversation ends. Load no domain pack; each child task keeps its own Domain. `./references/workflow/task-store.md` § *Shared group context* owns the group file's sections, `GQ<n>` ids, and `GROUP_LOG.md`. Keep no group state outside the files; rebuild it from disk each time.

Write only the selected group's `GROUP_CONTEXT.md` and `GROUP_LOG.md` and the `CONTEXT.md`, `ticket.md`, `plan.md`, `goals.md`, and `result.md` of each task below it, outside Archive and Backlog. Those tasks include tasks in nested groups (§ *Change sets* step 1). In a `plan.md`, `goals.md`, or `result.md`, make only § *Change sets* step 4's edits. § *Init* also creates the group's directory. § *Change sets* step 3 may create such a task's missing `CONTEXT.md`. Never write ancestor or nested group files, `DECISIONS.md`, or a task's other files. Never write through a `GROUP_CONTEXT.md`, `GROUP_LOG.md`, task folder, directory between a task and the group, or task `CONTEXT.md`, `ticket.md`, `plan.md`, `goals.md`, or `result.md` that is a symlink or other non-regular entry. While the group's `GROUP_CONTEXT.md` or `GROUP_LOG.md` is such an entry, a change set writes nothing and names that entry as unsupported. A skill the session runs under § *Lifecycle* writes under its own rules.

## When to Use

**Use when** you want to see or steer a group's direction, scope, decisions, and open questions across its child tasks, or to create a group.

**Skip when** the work concerns one task: `resume-task` briefs it, `reconcile-task` records session findings, and `plan-task` changes its plan.

## Resolve the group

1. A token with a path separator is a path, used anywhere on disk. Expand `~`, then resolve a relative path against the working directory to an absolute one. Any other token is a name.
2. A path to a folder holding a role file (`./references/workflow/task-layout.md` § *One task, one flat folder*) is a task. Refuse it and name `resume-task`.
3. A name matches group directories in registered roots by whole basename, case-insensitively, outside Archive and Backlog. Walk each root under `./references/workflow/task-store.md` § *The root registry*. A group directory holds no role file, and holds a `GROUP_CONTEXT.md` entry of any kind or a task below it. List several matches with their root labels for the user to pick. With no match, ask for a path.
4. Select the root as `task-store.md` § *Shared group context* selects one for a task, and cite group files by root-relative path. Outside every registered root, read only the group's own files, skip ancestors, and cite the group by its absolute path from step 1. The brief says so and warns, as § *New group file* does, that child tasks inherit nothing from this group file. It names `init-config` to register a root.
5. Refuse a path, writing nothing, when an ancestor directory holds a role file. The path lies inside that task folder; name the task. Also refuse a path that is or lies inside an Archive or Backlog container, matched case-insensitively. Both tests check only components below the store root (`./references/workflow/task-archiving.md`). The store root is the registered root step 4 selects, else the canonical `.agents/tasks` root containing the path. With neither, both tests check the whole path.
6. Route the path. A directory holding a `GROUP_CONTEXT.md` entry of any kind, or a task below it, opens with § *Brief*. A missing directory, or one holding neither, goes to § *Init*. A path naming a file is not a group; ask for another.

## Brief

Print the brief at start, when you ask what's next, and when the session continues after context compaction. Build it from disk each time.

1. **Group files.** Read the group's `GROUP_CONTEXT.md` in full. Report a `GROUP_CONTEXT.md` or `GROUP_LOG.md` that is a symlink or other non-regular entry as unsupported instead of following it (`task-store.md` § *Shared group context*). Measure a `GROUP_CONTEXT.md` that is a regular file by its size on disk in bytes, for example with `wc -c`. When that size exceeds the budget in `task-store.md` § *Shared group context*, print the **Size:** line with the size and the budget. Inside a registered root, also read the ancestor group files from the root down, without writing them. Report material contradictions with the group's file under `task-store.md` § *Shared group context*.
2. **Children.** Take the group's direct subdirectories under the walk's prunes (`task-store.md` § *The root registry*), skipping Archive and Backlog containers case-insensitively. Report each symlink, and each entry that is neither a file nor a directory, as unsupported (`task-store.md` § *Shared group context*). A subdirectory holding a role file as a regular file is a child task. Another that holds `GROUP_CONTEXT.md` or a task below it is a nested group, listed by name only.
3. **Plan status.** Before the first run, check that `<kit-root>/scripts/task-state.ts` exists. Run `node <kit-root>/scripts/task-state.ts <child-dir>` for each child, never with `--repair` (`./references/scripts/task-state.md`; `<kit-root>`: `task-store.md` § *Resolving `<kit-root>`*).
    - Exit 0: take `plan.status`, each step's number, title and checkbox, `nextPendingStep`, `checkpoints`, `currentState`, and each `structure.diagnostics` entry.
    - Exit 1 with a stderr line starting `[task-state]`: check the child's `plan.md` entry without following links, for example with `ls -ld`. An existing entry is an unreadable plan; report it with its path. Without one, check the child for legacy `*.plan.md` entries the same way. Report each one's path as a legacy plan file (`./references/workflow/task-layout.md` § *One task, one flat folder*). For a child under `<kit-root>/.agents/tasks/`, name `maintain` to rename it; `maintain` renames legacy files nowhere else. For any other child, tell the user to rename the file to `plan.md` by hand. Also tell them to repoint links in that folder that name the old file. A child with neither entry has no plan.
    - Exit 2: report the child's state as unavailable, with the stderr line.
    - Helper unavailable: the script is missing, an exit 1 has no stderr line starting `[task-state]`, or the exit is not 0, 1, or 2. Stop running the helper. Show every child's state as unavailable, citing the missing path, or the exit code and the stderr line naming the error.
4. **Questions.** Read only the `## Open Questions` section of each child's `CONTEXT.md` and `plan.md`, where each exists. Skip only fully answered entries, and show a partly answered entry by its open part. Add the group file's `## Open Questions`. Group all of them by the addressee each entry states. List under **You** each group question addressed `ask you`. Also list there each entry, or open part, marked "Awaiting decision" or recording a held choice with its options and their trade-offs, when it states no other addressee (`reconciliation.md` § *Consent model: findings apply, the record carries them*). List the other entries without an addressee under **No addressee**. Apply § *Change sets* step 5's citation test to each child entry in either citation form of `task-store.md` § *Shared group context*. For an entry that cites this group's file, look up its id in the group file step 1 read. The lookup has the four outcomes of `task-store.md` § *Shared group context* and reads no other file. An answered-form entry whose id the lookup finds answered is fully answered. Show an open part of its own as that child's question. Each id answered this way gets one line under Answered in Decisions. That line shows the id as answered for every child citing it, and repeats no Decisions line text. An entry of either form that the lookup finds unresolvable appears under Unresolvable, with its child and file. Any other child entry that cites one of this group's questions under § *Change sets* step 5 appears once, under that question. Those include an answered-form entry whose id the lookup finds open or waiting. When the id instead starts a `## Decisions` line, the entry appears beside that line under Answered in Decisions. The brief leaves the entry unchanged. An open part of its own shows beside its child there. Any other child entry citing a `GQ<n>` id of another file, in either citation form, appears apart with that file's path.
5. **Older group files.** For each of the four sections the group file lacks, print "none recorded". List the file's other `##` headings by name. A group with no `GROUP_CONTEXT.md` entry is reported as having none.
6. **Scope drift.** When the group file read in step 1 holds a `## Scope` section, compare its lines with the step 2 child tasks. A Scope line names a child when it names the child's directory. Report each child task no Scope line names, and each Scope line that names no child task.
7. **Offers.** Offer § *Restructure* when `GROUP_CONTEXT.md` holds text outside the four sections, apart from its title. Otherwise, offer § *Compact* when the step 1 size exceeds the budget. Offer § *New group file* for a group with no `GROUP_CONTEXT.md` entry. Make no offer while `GROUP_CONTEXT.md` or `GROUP_LOG.md` is unsupported.
8. **Child lines.** Give each child task its owner. Treat a `done` or `skipped` plan as having no pending step, even when it has an unchecked step. A `done` child awaits reopening as `./references/workflow/task-siblings.md` defines it for a `done` sibling. Its child line shows that state and its route in place of `no pending step`. Choose that route under `./references/workflow/task-siblings.md` § *Reopening marker*. An `in-review` child awaits repair when its Current state **Next:** begins with the repair marker of `./references/workflow/task-siblings.md` § *Repair marker*. Its child line shows that state and its route in place of its next step or `no pending step`. Choose that route under `./references/workflow/task-siblings.md` § *Repair marker*. Give any other child with a pending step its next step and that step's blockers. Give a child without a plan its planning blockers.
    - **Owner:** take it from the group's `## Scope` line that names the child's directory (step 6). Print `owner <name>`, else `owner not stated`.
    - **Next step:** take the earliest unchecked step, in plan order, of the child's own plan that Current state's **Next:** names. When Next names no unchecked step of that plan, take `nextPendingStep`. When Next names steps of that plan and all are checked, mark Current state out of date.
    - **Depends on:** also read the `**Depends on:**` line under the next step's `### Step` heading in the child's `plan.md`. Never take it from task-state's `steps[].dependsOn`. A line that starts with `none` cites nothing. The line, or a Current state item, cites a task when it names that task's directory. A `Step <n>` directly after that name cites that step of the task.
    - **Blockers** of the next step come from five sources:
        - Current state: each item it says the next step waits on. When it holds the step without naming an item, the hold itself. The Depends on line's checks below also apply to an item that cites another step 2 child, a task in the group's Archive container, or a step of either. A done-record line in the group file's § Decisions also clears any other Current state item it records done, under the Other item check below (`./references/workflow/task-store.md` § *Shared group context*). For a `blocked` child, this source also gives each item that the most recent `**Blocked:**` section of its `result.md` records as needed or awaited. For an `in-review` child, it also gives each item that the most recent `**In review:**` section lists (`./references/workflow/task-lifecycle.md` § *Companion result file*). Each such item blocks under the Depends on line's checks below, even when Current state omits it. The In review items do not block a next step that is unexecuted under `./references/workflow/status-transitions.md` § *Downward reconciliation and upward advances*, such as one a change set added. When a `blocked` child has no `**Blocked:**` section in `result.md`, this source gives the item `Blocked section missing from result.md`. When an `in-review` child has no `**In review:**` section there, it gives `In review section missing from result.md`. No check below clears either item.
        - The Depends on line: each item it cites, under the checks below.
            - Own step or group question: a step of the child's own plan while unchecked, and a group question while open.
            - Another child: one the line cites, or a cited step of it, blocks until the citation is met under `./references/workflow/task-siblings.md`. Ask any repository question that rule raises under `./references/workflow/task-delivery.md` § *Branch and worktree creation* → **Which repository** before printing the brief. Reuse your answer in this session's later briefs.
            - Archived task: when the line cites a task that is not a step 2 child, look for its folder in the group's Archive container, matched case-insensitively. Run task-state on a folder found there as step 3 runs it, never with `--repair`. When the run exits 0, the check for another child applies to that archived task and its cited steps. A run that exits non-zero keeps the cited task or step blocking. Either way, a blocking archived task or step is named as that task.
            - Other item: any other item, such as a PR, a ticket, or a review, blocks unless Current state, an answered Open Questions entry, or a done-record line in the group file's § Decisions records it done (`./references/workflow/task-store.md` § *Shared group context*). A cited task that is neither a child nor in the group's Archive container, such as one inside a nested group, is such an item.
        - Open Questions from step 4: an open entry, or its open part, blocks only when the Depends on line cites it, it names the next step, or Current state names it as what the step waits on. A group entry names a child's step only beside that child's directory.
        - Approach choice: the child's pending comparison and each of its open approach-wait entries, as **Planning blockers** below defines and checks them. Their route follows `./references/workflow/task-approaches.md` § *Other readers and writers*.
        - Approach citation: the child's approach-citation stop under `./references/workflow/task-approaches.md` § *Other readers and writers*. Check the child's `approaches.md` as **Planning blockers** below checks it. When its `**Decision:**` line reads `selected`, read the dated decision anchor its `## Current decision` cites. Also read each `approaches.md` anchor that the `## Approach` section of the child's `plan.md` cites.
    - **Planning blockers:** only three kinds of item block a child without a plan. One is an open Open Questions entry that says the child's planning waits on it. Another is the child's pending comparison: an `approaches.md` whose `**Decision:**` line reads `pending`. Read that comparison's deciding questions from its `## Current decision`. The third is each open approach-wait entry in the child's `CONTEXT.md` `## Open Questions`, tested against its `approaches.md` under `./references/workflow/task-approaches.md` § *Approach-wait entries*. Their route follows `task-approaches.md` § *Other readers and writers*. Check the child's `approaches.md` entry without following links, and read it only when it is a regular file. Report a symlink or other non-regular `approaches.md` as unsupported (`task-store.md` § *Shared group context*).
    - **Kinds:** name each blocker once, as a group question `GQ<n>` with its addressee, an own step, a person, a PR, another child task, a pending comparison, an open approach-wait entry, an approach-citation stop, or another item the task files record, such as a ticket. Name an own step as `<child> Step <n>`, with the child's directory and the step's number. Name a pending comparison as `<child> approach comparison pending (<deciding question>; …)`, with the child's directory and the comparison's deciding questions. Name an open approach-wait entry as `<child> approach decision awaits record (<decision>)`, with the child's directory and the entry's decision. Name an approach-citation stop as `<child> plan approach citation needs update (<anchor>)`, with the child's directory and the anchor that the comparison's `## Current decision` cites. When `./references/workflow/task-siblings.md` leaves a citation of another task unmet awaiting merge of its branch, name that blocker as `<task> (branch <branch> awaiting merge)`, with the task's directory. When that rule awaits merge of a commit, name the blocker as `<task> (commit <sha> awaiting merge)`. Include the cited task's directory. When that rule instead awaits update of the local default branch, name the blocker as `<task> (default branch <default-branch> needs update)`, with the task's directory. When it awaits update of the local base branch `<base>` instead, name the blocker as `<task> (base branch <base> needs update)`, with the task's directory. When that rule instead awaits a PR head that is not available locally, name the blocker as `<task> (PR head <short-sha> not available locally)`. Include the cited task's directory and the PR head's short SHA. Beside it, tell the user to fetch `refs/pull/<n>/head` under `./references/workflow/task-siblings.md`. When that rule instead awaits updating the child's branch, name the blocker as `<task> (branch <child-branch> needs update)`. Include the cited task's directory. When that rule leaves a citation unmet awaiting the sibling task's final commit, name the blocker as `<task> (awaiting commit)`, with the task's directory. When it leaves a citation unmet awaiting commit of the cited step, name the blocker as `<task> Step <n> (awaiting commit)`, with the task's directory and the cited step's number. Beside either awaiting-commit blocker, tell the user to append the applicable record to the sibling's `result.md` if the work was committed by hand. Name the record and `**Commit:**` line under `./references/workflow/task-siblings.md`. When an awaiting-commit blocker's qualifying record reads `none — no task changes` and no earlier record names a commit, also tell the user to revise the child's `**Depends on:**` line through `plan-task` if the cited work produced no commit. When that rule leaves a step citation unmet because the cited step is missing from the sibling's `done` plan, name the blocker as `<task> Step <n> (missing from done plan)`. Include the cited task's directory and the cited step's number. When that rule leaves a citation of the sibling unmet awaiting reopening of the sibling task, name the blocker as `<task> (awaiting reopening)`, with the task's directory. When it leaves a step citation unmet awaiting reopening of the sibling task, name the blocker as `<task> Step <n> (awaiting reopening)`. Include the cited task's directory and the cited step's number. When the **Archived task** check found the task of either awaiting-reopening blocker in the group's Archive container, name two actions beside the blocker: un-archiving that task, then its route. Un-archiving is the user's own move of the folder from `<group>/Archive/<task>/` back to `<group>/<task>/` (`./references/workflow/status-transitions.md` § *Terminal vs. live states*). Choose `resume-task-reconcile` or `review-task-reconcile` under `./references/workflow/task-siblings.md` § *Reopening marker*. Read the task's **Next:** from the `currentState` of that check's task-state run. Name a child's own question by its addressee, else by its subject. Print `nothing` when no blocker remains.
    - The blockers of an `in-review` or `blocked` child with no pending step, other than one awaiting repair, are the items its Current state says it waits on. They also include each item the Current state source above takes from the child's `**Blocked:**` or `**In review:**` section, or gives for a missing section. The Depends on line's checks apply to these items as the Current state source above applies them. Such a child shows `nothing` when none of them blocks. A child awaiting repair shows no blockers, whatever its `**In review:**` section lists. Any other child whose plan has no pending step shows no blockers. A child with an unreadable plan, a legacy plan file, or unavailable state also shows no blockers.
9. **Ready.** List each child that has work left and nothing blocking it:
    - A child without a plan whose planning shows `nothing`. A child without a plan that is recorded done under `./references/workflow/task-siblings.md` is left out instead. Its line shows `no plan; recorded done` and one file that records it, preferring the group file.
    - A child whose only planning blockers, or whose next step's only blockers, are its pending comparison, its open approach-wait entries, or both. Its work left is the approach choice; show it as `choose an approach`.
    - A child whose next step's only blocker is its approach-citation stop. Its work left is the plan revision; show it as `revise the plan`.
    - A child whose plan is `to-do`, `executing`, `blocked`, or `in-review` and whose next step shows `nothing`.
    - An `executing`, `blocked`, or `in-review` child with no pending step, other than one awaiting repair. A `blocked` or `in-review` one qualifies only when its child line shows `waits on: nothing`. Show an `in-review` one as `next: verification`, and the others as `next: acceptance`.
    - A `done` child awaiting reopening under step 8. Show it as `next: reopening`.
    - An `in-review` child awaiting repair under step 8. Show it as `next: repair`.
    - For each ready child shown as `choose an approach`, print `/choose-approach <token>`. For each shown as `revise the plan`, print `/plan-task <token>`. `task-approaches.md` § *Other readers and writers* routes both. Print `/plan-task <token>` for another ready child without a plan. For a child awaiting reopening or repair, print `/resume-task-reconcile <token>` or `/review-task-reconcile <token>`, following its step 8 route. For any other ready child, print `/implement-task <token>`. The token follows `./references/workflow/task-layout.md` § *One task, one flat folder*: the bare slug where discovery resolves it, the folder path otherwise.
10. **Blockers list.** Name each distinct blocker from the child lines once, with the children it holds. Two lines name the same blocker when they name the same group question, own step, person, PR, child task, or item. Order the list from the most children held to the fewest, and break ties by Children order.
11. **Decisions summary.** Print the number of Decisions lines and how many of them hold no log citation. Then print at most 8 lines that cite one of three kept change sets. A Decisions line is a list item of the group file's `## Decisions` section. A list item is a line that starts with `- `, `* `, `+ `, or a number followed by `. `, such as `1. `.
    - When the section holds non-blank lines but no Decisions line, print how many non-blank lines it holds in place of the counts.
    - A line holds no log citation when it names no `GROUP_LOG.md § <heading>`, such as a line citing another writer's record (`task-store.md` § *Shared group context*, § *Change sets* step 6). Leave that count out when it is 0.
    - Read only the `## Change set` headings of `GROUP_LOG.md`, for example with `grep '^## Change set' GROUP_LOG.md`, and no other line of the log. A later heading is a more recent change set.
    - A line cites a change set when it names `GROUP_LOG.md § <heading>` with that heading's full text (§ *Group file entries*). Take the change sets that any Decisions line cites.
    - Skip each change set whose topic is `restructure` or `compaction`, alone or followed by a space and a number, such as `restructure 2` (§ *Change sets* step 8). Keep the three most recent of the rest.
    - Rank each line that cites a kept change set by the most recent kept change set it cites. Order those lines from the newest rank to the oldest, in section order within a rank.
    - Print the first 8 of them as written, and state how many of them are left out.
    - Print the counts alone when `GROUP_LOG.md` is missing or unsupported, or when no change set is kept.
    - When you ask for the full Decisions section, read `GROUP_CONTEXT.md` again and print that section as it stands on disk.

## Team status

When you ask for a team status, draft in chat a progress update for the group's discussion thread. Never post or send it, and write no file or Slack draft for it.

1. **Period.** Cover today, or the period you name.

## Lifecycle

Hand a request to create, park, or archive a child to its skill, under that skill's own invocation and confirmation rules. The session itself creates and moves no task folder.

- **Create:** `prepare-ticket` for one child, given a new folder inside the group's directory, or `decompose-task` for several, given the group's directory as the parent.
- **Park:** `backlog-task`. **Archive:** `archive-task`.
- Hand `archive-task` a request to archive a `done` child awaiting reopening under § *Brief* step 8 with no confirmation of the session's own. Before the move, its step 1 names that state, the remaining work, and the route (`../archive-task/SKILL.md` § *1. Resolve the target task folder*).
- A run the session starts on your request is model-invoked (`./references/workflow/skill-conventions.md` § *The invocation gate*). A confirm-gated skill on that section's roster proposes its run, and nothing moves before your confirmation.
- Report the skill's output as printed, including a refusal.
- When the run adds or removes a direct child task, rebuild the Scope drift from disk as § *Brief* step 6 does. For each added or removed child that drift names, offer a change set that adds or removes its Scope line. Apply an accepted offer as an instruction under § *Change sets*.
- Moving an existing task into the group is a manual move, outside the session (`./references/workflow/task-relocation.md` § *3. Report*).
