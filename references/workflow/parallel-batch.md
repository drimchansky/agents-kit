# Coordinator-Side Parallel Batch

The mechanics of running write-mode units concurrently — split out of `./executor-contract.md` § *Write-mode routing*, which keeps the intake; the posture is `./write-mode-posture.md`, and the registry and the engines are `./executor-routing.md`. Read this file when a parallel batch qualifies, and whenever a unit runs on `cross` — its worktree-always placement routes a serially delegated unit's seeding, surface check, and removal through this file too — before launching.

## Coordinator-side parallel batch

This is the single home for the mechanics of running units concurrently. It is written in terms of *units* and *the consumer's declared unit order*, so every registered consumer cites it and none restates it.

**Eligibility — all conditions required.** Two units may share a batch only when:

- no dependency path connects them, directly or transitively;
- each declares an edit surface and the declared sets are pairwise disjoint — the core rule "do not parallelize sequential edits to the same artifact" (`CORE_RULES.md`), made checkable;
- each unit's verify can run in an isolated copy.

A unit with no declared surface (or a surface of `none`) runs serially — an absent declaration is a serial default, not an invitation to infer one. When in doubt about disjointness, run the doubtful unit serially: a wrongly-serial unit costs minutes, a wrongly-parallel one costs the merge. Each consumer adds its own eligibility bounds on top — `implement-task`'s checkpoint-bounded batches and `**Touches:**` lines, for instance — and those stay in that skill.

**Run.** Launch one executor per eligible unit, each with a self-contained launch packet per `./executor-contract.md`, on the engine and defaults `./executor-routing.md` § *Write-mode engine registry* names — `native` through its host adapter, `cross` through the launch recipes that entry points at, since no adapter loads there. Each executor's effective root is its own **coordinator-managed worktree**, seeded to the **batch baseline** — the shared tree's state at launch, uncommitted work included (staged, unstaged, and untracked), since a worktree created bare from a commit hands the executor stale code; executors never create, switch, or seed worktrees themselves. **Capture that baseline as a manifest before the first worktree diverges** — the merge script's `baseline` on the shared tree — and hand that one file to every unit's `check` and `apply` below: a manifest taken later, against a tree already carrying an earlier unit's incorporation, reads that unit's work as this one's. Seeding also **pins the unit's tool state inside the worktree** — every cache, daemon, and workspace-metadata directory the unit's commands write, redirected into it by whatever environment variable or flag the tool takes. Each pinned directory is named to that capture as `--prune <path>`, root-relative — the manifest carries its prunes into `check` and `apply` — or its contents read as an added tree escaping every unit's surface; `.git` and `node_modules` need no naming, the script prunes them by name at any depth, whatever their type, and **a git-ignored path outside every declared surface needs no naming either** — on a Git checkout the walk drops every untracked path the repository ignores, on both sides of the comparison (`<kit-root>/SCRIPTS.md` § *`scripts/worktree-merge.ts`*), because `git worktree add` carries no ignored file into a seeded worktree and measuring them reads each of the shared tree's own (`.DS_Store`, local agent settings) as a deletion escaping every unit's surface. **Do not route a unit's output to a git-ignored path**: a dropped path is not incorporated, so a unit told to write one produces nothing the merge can carry. Inside the unit's declared surface that is caught rather than lost — the script reports the path as `NOT MEASURED`, counts it in the `ignored-divergent` trailer, and refuses the `apply` before it writes anything — but the unit's work still has to be redone somewhere the merge measures. **Inside a declared surface a git-ignored path still takes a `--prune`**, which is where the no-naming rule above stops: a unit's own build output under its surface directory — the ordinary shape when the surface is a package root, since the verify criterion is proved inside the worktree — is not routed output, but it diverges from the shared tree just the same, so name it at seeding or every `apply` for that unit refuses and the completed work goes to a serial re-run. Outside the surface nothing is examined and nothing is reported, which is what keeps a worktree's build output out of every change set. **Name only paths the project does not track**: a prune filters the baseline as well as the current walk (`<kit-root>/SCRIPTS.md` § *`scripts/worktree-merge.ts`*), so pruning a tracked directory a unit legitimately edits — a zero-installs `.yarn/cache`, a committed bundle — drops that edit out of its change set and it is never incorporated, silently. Pin such a directory somewhere untracked instead of pruning it. Left to its own defaults a build tool resolves those to the shared checkout, where two concurrent units contend over one directory and a sandboxed unit fails outright on a write outside its root; both surface as a broken toolchain rather than as unpinned state, which is why the pinning is part of seeding rather than a repair applied once it bites. A unit's **change set** is everything in its worktree that differs from that baseline — every path whose content, presence, or absence differs from the seed, tracked or untracked, never git-ignored — and is what the merge gates below operate on. While a batch is in flight the **shared tree is frozen**: the coordinator runs no unit of its own, including a serial fallback, until every executor has returned or its worktree has been discarded, waiting on the launches as `./delegated-waiting.md` § *How to wait* directs.

**Merge — in the consumer's declared unit order.** Each binding in `./executor-contract.md` names its consumer's order (plan order, frame order, severity order). Once every executor has returned or its worktree has been discarded, process each unit in that order. An unavailable or hung executor enters its owning consumer's declared serial fallback with no raw worktree delta. The mechanical gates below — the delta against the baseline, the surface check that bounds it, and the incorporation with its verification — are `node <kit-root>/scripts/worktree-merge.ts` (`./task-store.md` § *Resolving `<kit-root>`*), which performs them in this order and refuses to remove a worktree until the change set it applied is verifiably present in the shared tree. `<kit-root>/SCRIPTS.md` § *`scripts/worktree-merge.ts`* owns the CLI forms and the stdout contract — the subcommands this section names, the options each one takes, and the `0`/`1`/`2` exit statuses that carry a gate's outcome — so read that section, not the whole file, before the first invocation rather than assembling a command from the flags this section happens to name. Its captures are hash manifests: it detects and verifies and never reconstructs, so the exact pre-unit capture a conflicting incorporation restores from is bytes the coordinator takes itself, beside the manifest, before that unit's incorporation. Run by hand they are shell re-authored on every run, and a merge whose ordering holds only as well as the shell it was written in is the one that removes a worktree before proving the copy landed. With no kit root available, the gates below are the hand equivalent and are run exactly as written — the ordering then holding only as well as the shell it is written in, which is the cost of the hand form and the reason the script is the default. For every unit:

1. **Returned-worktree surface check** (the script's `check`) — inspect a returned worktree's raw, complete content/presence delta against the batch baseline, including new and deleted paths, and confirm it stays inside that unit's declared surface. A surface escape discards that worktree and enters the serial fallback.
2. **Capture, incorporate, or fall back** — at the unit's ordered position, capture the exact shared content/presence state immediately before it: the script's `baseline` for the manifest, beside the coordinator's own copy of the bytes. Incorporate a worktree that passed the surface check atomically, through the script's `apply`: modify files, copy new files, and mirror deletions. Its `--baseline` is the **batch baseline** step 1 checked against, never the pre-unit capture just taken — that capture is restore material alone, and a change set measured against a tree already carrying earlier units' incorporations reads their work as this unit's escapes. Never commit in a worktree or merge branches. If incorporation conflicts, restore that exact capture, discard the worktree, and enter the serial fallback; never hand-resolve a batch conflict inside an executor worktree. An incorporation that **failed to verify** takes that same path and needs the restore more than a conflict does: a conflict is refused before anything is written, while a failed verification leaves part of the change set on the shared tree — restore from the pre-unit capture, using the script's landed/did-not-land split to say what was there to undo. An unavailable, hung, surface-escaping, ignored-divergent, conflicting, or unverified unit executes only that unit serially, at the placement its engine then defines — for a unit still on `cross`, the worktree-always rule in `./executor-engines-cross-vendor.md` § *Cross-run rules*; for one the ladder there has degraded to `native`, the current integrated tree. Check its complete actual content/presence delta against the immediate pre-unit capture and its declared surface; if it escapes, restore that exact capture, discard the unit's work, and stop under the owning consumer's **Blocked** binding (`./execution-bindings.md`) — except `fix-findings`, whose units are independent, which buckets the finding and continues. A serial fallback that escapes is never re-executed serially again.
3. **Re-prove the unit outcome** — after either a successful incorporation or its serial fallback, run that unit's full outcome tier on the integrated tree as `./execution-loop.md` § *Two verification tiers* defines it: its stated criterion plus the per-unit checks the resolved domain's `verification.md` adds. Not the health recipe, and not the criterion alone. Executor-reported success is provisional; this is the pass that counts. On failure, remove every remaining batch worktree before the owning consumer applies its Stop-the-Line or recovery behavior; do not record the failed outcome. A unit whose worktree is removed that way has not itself failed and is not one of the fallback triggers above: where the owning consumer's units are independent (`fix-findings`) it enters that consumer's declared serial fallback, and where they are not it is left unstarted under the consumer's **Blocked** binding. Neither case silently drops it.
4. **Expose and record** — only after the integrated outcome passes, expose the ordered incorporated content/presence change set: the actual delta from the exact shared state immediately before that unit to the state it left behind, together with the consumer order and declared dependencies. The raw worktree delta is merge input; this incorporated set is recovery evidence, not Git state. Then record per the consumer's own binding (`./execution-bindings.md`), exactly as in serial execution.

Integrated health is not owed by any individual merge. Once every batch unit has incorporated or completed its declared serial fallback, remove every executor worktree before continuing — a merged one through the script's `remove`, a discarded, failed, or hung one through its `discard` — then hand the accumulated shared tree to the owning consumer's declared health boundary. That consumer runs the boundary's recipe once at it, not once per merge. Coordinator-managed **executor** worktrees sit inside the Git-discipline rule, not against it: they are transient scratch — created for the batch with nothing committed and no branch made, merged by diff-apply, removed — not the Git-state mutation the consumers' invariants forbid. That is a statement about these worktrees alone. **The shared tree they are seeded from and merged back into is the run's own task worktree wherever the run has one** (`./task-delivery-edges.md` § *The task worktree is the run's shared tree*), and the checkout itself where it does not — durable, branch-carrying, and sanctioned by the invoking skill's contract rather than by this paragraph. Every mechanic above takes a tree and is indifferent to which.

*Where* in a run a batch merges and where its one health pass lands are the consumer's business, not this file's. A checkpoint-bounded `implement-task` batch, for example, shares the checkpoint's health boundary rather than creating another one.
