# Locating the PR a Follow-Up Acts On

How a skill that acts on a pull request finds the one its object sits on, and every way that lookup comes up short. **This file is the single source of truth for that lookup**, so a consumer names what it does with the outcome and never its own copy of the query; a second copy drifts silently, because the wordings differ and `dup-check` groups only on exact matches. § *Coming up short has two outcomes* names each consumer and the outcome it takes, and carries the standing exceptions to that no-second-copy rule.

**Find the PR the reviewed object sits on, not merely the current branch's.** Ask GitHub which PRs have the reviewed head as their own head — `gh api --paginate repos/{owner}/{repo}/commits/<head-sha>/pulls --jq '.[] | select(.state == "open") | select(.head.sha == "<head-sha>") | .number'` — and take the one it names; a review of a range or of another branch's head has a PR of its own, and resolving to the checkout's PR instead would act on a diff nobody reviewed. The `.head.sha` filter is load-bearing: the endpoint answers by *association*, returning every PR whose head branch contains the commit, so an open PR whose head has advanced past the reviewed head still matches it and a stacked PR containing the commit matches beside its parent. Filtering on the head itself is what makes the match the object's own PR rather than one that merely contains it — without it a mutating follow-up resolves an advanced PR from a stale SHA and writes against a diff nobody reviewed. **Exactly one match is required**: none is a coming-up-short way below, and several stop with the candidate numbers named rather than picking one. Key the lookup on the SHA rather than scanning a listing: `gh pr list` returns one capped page — 30 by default — so on a busy repository a scan silently misses the match and reports that no PR exists. `--paginate` is what keeps that same cap off the SHA lookup — the endpoint pages at 30 too and takes no state filter, so without it closed and merged PRs fill the page ahead of the open match and hide it, or hide the second match that should have stopped the run. Read that PR by number: `gh pr view <number> --json <fields>`. Either call requires the `gh` CLI. Every follow-up reads four fields, `number`, `title`, `url`, and `state`; a skill that needs more names them beside those.

**Carry the PR forward once it is found.** A caller that already selected a PR by reviewed head passes that number here rather than re-deriving one — re-deriving is what silently swaps the object's PR for the checkout's, and the currency check downstream then reports a branch that advanced when nothing did.

**Coming up short has two outcomes, and the consumer's own kind picks which.** The ways are the same either way: `gh` is missing, the repository has no GitHub remote, the command errors on auth or network, the PR it returns is not in state `OPEN`, several open PRs match and none can be singled out, or no open PR carries the object — and that last way is two, told apart by the lookup's own outcome, because each has a remedy of its own and a stopping consumer names it. **GitHub does not have the head**: the `commits/<head-sha>/pulls` call errors on a commit the remote never received (`No commit found for SHA`), which is what an unpushed local tip looks like from here; `git push` clears it, and the same lookup then finds the PR. **GitHub has the head, but no open PR has it as its own head**: the call answers and nothing passes the `.head.sha` filter — every PR containing the commit has advanced past it or is closed; only a fresh review at the head you mean to act on clears it, since no push changes which commit was reviewed.

- **The follow-ups stop**, noting which way it was and, where the object is uncarried, which of its two ways — naming that way's remedy, since the two look alike from the stop and only one is cleared by a push. `publish-pr-review` and `update-pr-description` have nothing to act on without a PR, so none of these degrades to a guess at one.
- **`review-code` does not.** It looks a PR up for *context*, not to act on one, so coming up short costs it the PR's title, body, threads, and links and nothing more: it records that there is no PR context and reviews on the object's commits alone. A stop there would refuse a review the object fully supports.
- **`review-code`'s branch-keyed context lookup is one of two standing exceptions to the no-second-copy rule.** It resolves its declared base and its PR context from the current branch's PR (`gh pr view` with no positional argument, at `../../skills/review-code/SKILL.md` § *Setup*), not from the reviewed head, because the branch it reviews routinely has a local HEAD ahead of the pushed PR head — keying that lookup on the head would find no PR and cost the review both its context and the declared base its `publish-pr-review` follow-up re-checks against. The head-keyed form above is what it uses for a range ending anywhere but the current branch's HEAD, and both of its branch-keyed calls take `state` as the follow-ups do, treating anything but `OPEN` as no PR. **`triage-findings`' PR-mode lookup is the other.** It has no reviewed object at all — it triages a PR's own review threads, so the current branch's PR *is* the object it acts on and there is no reviewed head to key on (`gh pr view --json number,url,title,state` with no positional argument, at `../../skills/triage-findings/SKILL.md` § *Fetch*), and it takes `state` like the others; `triage-findings-verify` and `fix-findings` run that same Fetch section rather than carrying copies of their own.
