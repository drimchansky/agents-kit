# Task Delivery: Branch and Worktree Creation

How a task's work reaches the repository it belongs to — which repository that is, the branch and worktree a run executes in, and where their names come from. **This file and its satellite `./task-delivery-edges.md` are together the single source of truth for task delivery**, split at the load boundary: every engineering task in a checkout passes through the creation gate here, while re-entry, removal, and the live-verification gate are reached only on their own conditions and live there. The skills that deliver a task cite the section they need rather than restating it: `implement-task` creates here and re-enters and removes there; `plan-task` reads the gate there; `maintain` runs the backstop sweep against that file's § *Removal*. Delivery stops at branch and worktree lifecycle — staging, committing, pushing, and opening a pull request stay with the user and their own commands.

## Repo delivery declarations

A repository states its delivery conventions in prose, in the `AGENTS.md` / `CLAUDE.md` every run already reads before starting work (`../../CORE_RULES.md` § *Workflow*). There is no config file and no schema: project consistency already takes precedence over kit defaults by core rule, and a machine-readable second home would drift from the prose agents actually follow. Two declarations are read from there:

- **Branch pattern** — the shape a task branch's name takes, with `<slug>` and `<name>` as the only tokens the kit substitutes — any other placeholder a pattern carries, `<initials>` say, is the team's own to fill. `<slug>` is the task's slug (`./task-layout.md`) — the task folder's name as it stands; `<name>` is that folder name minus a leading `NN-` ordering prefix — its shape and its occasion both `./decomposition.md` § *Ordering and numbering*'s; that file's § *The proposal* writes the prefixed folder as `NN-<slug>`, and its `<slug>` is this section's `<name>` — and is `<slug>` itself where the folder carries none. The strip is syntactic — a slug that itself opens with two digits and a hyphen loses them too — so a repository declaring `<name>` keeps its slugs clear of that shape. So folder `50-contacts-be-book-crud` resolves `feat/<name>` to `feat/contacts-be-book-crud`, and folder `contacts-adr` to `feat/contacts-adr`. Patterns look like `feature/<slug>`, `<initials>/<slug>`, `feat/<name>` — whatever the team uses. No declaration → the kit default **`task/<slug>`**. Both substitutions name the **branch only** — § *Branch and worktree creation*'s worktree path is built from `<slug>` whichever the pattern uses, so the directory keeps the folder's full name. `<name>` carries no uniqueness of its own — `01-api` and `05-api` are a legal pair under `./decomposition.md` § *Ordering and numbering*, and both resolve `feat/<name>` to `feat/api` — so a repository declaring it owns that uniqueness: two task folders resolving to one branch name — across the canonical root and every registered one, `Archive/` and `Backlog/` included since a finished task's branch routinely outlives it; the roots are the ones `./task-layout.md` § *Discovery rules for skills* gives a slug — are a layout error the run surfaces before creation — ask, never guess between them — rather than a collision met at `git worktree add`. The mapping runs both ways: a `<name>` token names the folder called that token or that token behind an `NN-` prefix.
- **Live verification** — whether a task in this repository reaches `done` only once its change is observed live. A repository that declares it says so and says *how*: which environment, which surface to check, who confirms. No declaration → no gate, and `./task-delivery-edges.md` § *The live-verification gate* never fires.

Read both once, at the start of the run that needs them. A declaration absent from both files is **absent** — never inferred from the repository's existing branch names, its history, or its remote, since a guessed convention is indistinguishable from a declared one after the fact.

## Branch and worktree creation

**Which repository.** The one `./reconciliation-commits.md` § *The scan* already resolves — this kit's rule for exactly this question, cited rather than restated: a task folder under a project-local `.agents/tasks/` acts on the git root containing it; a folder in a task store or a registered root elsewhere (`./task-store.md`) acts on the session's git root. **The task folder's own location is never the answer by itself**: a folder in a git-backed store would otherwise take the branch and `<root>.worktrees/<slug>/` into the store rather than into the repository the plan touches, and `./context-schema.md` carries no repository field to correct it with. Where more than one root answers and nothing separates them, ask — the same treatment **Resolving `<default-branch>`** below gives its own ambiguity.

**When it fires.** Both conditions, checked at execution start:

- the task's resolved `**Domain:**` (`./context-schema.md`) is `engineering` — a documentation or bureaucratic task delivers no code and gets no branch;
- **the resolved repository exists and is this task's** — the resolution above returns a root, `git rev-parse --git-dir` succeeds from it, and at least one path a plan step names **exists on disk** inside it. That is the same existence test `./reconciliation-commits.md` § *The scan* gates itself with, and for the same reason: a repo-relative path lies inside *any* root, so containment would never discriminate a wrong one. A root holding none of them is not this task's, and neither is no root at all.

**A failure skips creation — but the two failures skip differently.** What separates them is whether the run says so.

- **The domain condition fails, or there is no root at all** — the resolution returns nothing, or `git rev-parse --git-dir` fails → **skip creation silently.** No announcement, no degrade note, no pointer: the run proceeds on the checkout or the folder it was invoked against, exactly as it did before this contract existed. Silence is deliberate here — a doc task announcing what it declined to create would report the absence of a thing it never had, and a run that resolved no repository has none to name in an announcement anyway.
- **A root resolved but holds none of the plan's paths** → **skip creation and say so**: the run names the root it resolved and states that none of the plan's paths exist in it yet, then proceeds on that root exactly as the silent skip does. The doc-task reasoning above does not reach this case. The gate is checked at execution start, before any step runs, so a greenfield engineering task whose plan steps name only files the run will create fails the existence test necessarily — were this skip silent too, exactly the tasks most likely to want their own branch would get none and nothing would say so. What is announced is a **skip, not a degrade**: nothing was attempted and nothing failed, so it creates nothing, records no degrade note, and leaves `**Pointers:**` carrying no branch. **When creation is unavailable** below owns the case that did attempt creation.

**What is created.** From the **resolved repository's main checkout root** — the first entry of `git worktree list --porcelain` run inside it, which lists the main checkout ahead of every linked worktree, so a run invoked from inside a linked worktree behaves identically to one invoked from the main checkout:

- the **branch**, named by § *Repo delivery declarations*' pattern, based on `<base>` — **the default branch's current head**, unless the user directs otherwise at the start of the run;
- the **worktree** at `<main-checkout-path>.worktrees/<slug>/` — a sibling directory suffixed onto the main checkout path, outside the project itself, named by the task's slug.

**Resolving `<default-branch>`**, needed for `<base>` here and for the merged check in `./task-delivery-edges.md` § *Removal*: `git symbolic-ref --short refs/remotes/origin/HEAD`, minus its `origin/` prefix. That ref goes unset in plenty of correctly wired repos and the command then fails outright, so fall back to the `HEAD branch` line of `git remote show origin`, and with no remote at all take the main checkout's current branch — asking the user where even that is ambiguous.

One command does both:

```
git worktree add -b <branch> <main-checkout-path>.worktrees/<slug> <base>
```

**Announce it, record the branch, derive the path.** Creation is announced in chat as it happens — the branch, the worktree path, the base — because a run that silently moved where the work lands is a surprise the user pays for later. The branch name then goes into the result file's `## Current state` `**Pointers:**` line, the home for the task's own delivery vehicle (`./one-home.md` § *One home per fact*), written `` branch `<branch>` `` — that line is free prose, so the entry is additive to whatever is already there and machine-findable inside it by every reader that resolves the branch back off it, exactly as the watermark entry beside it is (`./reconciliation-commits.md` § *The watermark*). `scripts/commit-scan.ts` carries the machine-readable copy of that shape, since it cannot read this prose at run time — a sanctioned copy per `AGENTS.md` § *Consumer lists*: reword the entry here and change the pattern there in the same edit, or every scan of a task with its own branch walks `HEAD` instead. **The worktree path gets no pointer entry of its own**: it derives from the slug and the convention above, and a derivable fact given a second home is drift waiting to happen.

**The sanction.** Creating a branch and a worktree mutates Git state, which the engineering Git-discipline rule (`../engineering/rules.md` § *Code & Git discipline*) otherwise reserves for an explicit ask. The permission is **the invoking skill's own contract**: a skill whose CRITICAL block names task branch-and-worktree lifecycle among its sanctioned writes carries the user's explicit ask the moment they invoke it. **The ask is the *user's* invocation, not the model's.** A skill carrying this sanction may still be model-invocable — `implement-task` is — so a run the user did not ask for carries no such permission and makes no Git write under it at all: announce the skip, create nothing, recreate nothing, remove nothing, and proceed on the current checkout. That skip is **announced** rather than silent, unlike the domain-and-root skip above — an unrequested run resolved a repository it could have delivered into, so saying nothing would hide a Git write it declined to make. Which door a run came through is `./skill-conventions.md` § *The invocation gate*'s test, and stating the split here is what that file requires of any skill reading its own invocation as consent. That sanction is **scoped to this lifecycle alone** — the creation above, and the re-entry and removal in `./task-delivery-edges.md`. Nothing here stages, commits, pushes, or opens a pull request, and no ref outside the task's own branch is created, moved, or deleted — with one named exception: the branch-scoped `git fetch origin <default-branch>` the **merged** predicate of `./task-delivery-edges.md` § *Removal* runs — at removal, and at a § *Re-entry on resume* check that reaches it — which moves the default branch's remote-tracking ref and no other.

**When creation is unavailable.** A sandbox or permission layer refusing a write beside the checkout, or a `git worktree add` that fails for any other reason: **announce the degrade and continue on the current checkout**, which is how every run behaved before this contract — the shared tree is then the checkout itself, and nothing downstream changes. Record the degrade in the run's own record. Never retry with `--force`, never relocate the worktree somewhere writable, and never stop the run over it: a delivery convenience is not worth stranding the work.
