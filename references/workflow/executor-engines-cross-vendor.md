# Executor Engines: Cross-Vendor

The cross-vendor engines a write-mode `-x` run launches its executor on — each one's launch recipe, the preflight and policies that bound it, how the model pin reaches a launch that loads no adapter, and, in § *Cross-run rules* below, everything a cross run holds to whichever engine it lands on. This is the write-mode counterpart of `./probe-engines-cross-vendor.md`, which keeps the read-only probe recipes. The contract binding every executor is `./executor-contract.md`; its § *Write-mode engine registry* registers `cross` and points here for all of the above, restating none of it — what stays there is the packet shape, which § *Launch packet* owns for both engines alike. Read this file only when a cross launch is imminent.

**These are the write-mode recipes.** The read-only twin is `./probe-engines-cross-vendor.md`, a near-homographic filename whose `codex exec` recipe differs from the one below in several places — the twin carries no model pin, roots at a working root rather than a worktree, and writes to a flat scratch layout instead of a per-unit one — of which the permission-and-sandbox pair for each engine is security-critical: `--sandbox workspace-write` here against `--sandbox read-only` there, and `--permission-mode acceptEdits` plus the hard-fail sandbox settings here against `--permission-mode plan` there. Those are the controls to check first, and a write-capable probe launched on a read-only skill reads as a perfectly ordinary command; the others are why a recipe cannot be derived from the twin by swapping it. So take a recipe from the path the skill in hand cites, never from whichever of the two files you happen to have read most recently: a skill whose fan-out is read-only never takes a recipe from this file.

- **`codex`** — OpenAI Codex CLI, headless. The cross-vendor executor when the host is Claude Code. Requires `codex` on PATH, an active login, and a readable pin source, all checked **before** the once-per-run consent statement below — `command -v codex` checks presence, `codex login status` checks auth, and a read of `~/.codex/agents/executor.toml` confirms the `model` and `model_reasoning_effort` keys the launch line carries; a non-zero exit or an absent or keyless pin source degrades by the ladder below with nothing yet announced. A login that lapses between the preflight and the launch still surfaces at run time and degrades the same way; the preflight narrows that window, it does not close it.

  ```bash
  codex exec --ephemeral --sandbox workspace-write --skip-git-repo-check \
    -m <model> -c model_reasoning_effort=<effort> \
    -C <worktree> -o <scratch>/<unit>/evidence.md - < <scratch>/<unit>/packet.md
  ```

  The packet goes in on stdin, never as a command-line argument: the coordinator writes it to `<scratch>/<unit>/packet.md` with its file tool, and the trailing `-` makes `codex exec` read it from stdin — so a `$`, backtick, or apostrophe in the packet is data, not shell syntax to expand or execute (`<scratch>` is an absolute path). The probe file gives the same reason for a prompt; it binds harder here, because a write-mode packet quotes finding text, diffs, and file contents verbatim. The per-unit subdirectory is what keeps a run's second unit from overwriting the first's packet and evidence: one run shares one `<scratch>`, and an earlier unit's evidence is still the coordinator's to read after a later one has launched. `<worktree>` sits **outside** that subdirectory — a sibling such as `<scratch>/worktrees/<unit>`, never `<scratch>/<unit>/` itself, whose symmetry is a trap: a worktree rooted there holds `packet.md` and `evidence.md` at its root, which the returned-worktree surface check then reports as new untracked paths and fails as a scope escape on every unit.

  `--sandbox workspace-write` is the engine-side write ceiling; `-C <worktree>` is the coordinator-managed worktree the registry requires as the unit's effective root; `-o` captures the final message — the contract's six-heading evidence report — for the coordinator to read; `--ephemeral` leaves no session files; `--skip-git-repo-check` drops Codex's own repository precondition, so the launch turns on the coordinator's placement rather than on whether that check recognizes the seeded root — a linked worktree's `.git` is a file pointing into the parent repository, not a directory.

  `-m` and `-c model_reasoning_effort=` carry the pin, **read at launch time from the installed `~/.codex/agents/executor.toml`** — its `model` and `model_reasoning_effort` keys. `codex exec` has no agent selector, so that adapter never loads and its values have to travel on the launch line; reading them instead of copying them keeps the installed adapter as the pin's authoritative owner (`./executor-contract.md` § *Write-mode engine registry* → **Adapter defaults**) and keeps the registry's retune affordance working — retuning the installed definition retunes the cross launch with it. (`-c` takes a dotted config path whose value is parsed as TOML, falling back to a literal string.) The adapter's `sandbox_mode` is deliberately *not* read through: the sandbox is stated on the launch line, so a retuned adapter cannot widen it.

- **`claude`** — Claude Code, headless. The cross-vendor executor when the host is Codex — the mirror of the above, written as the mirror and **not yet exercised from a real Codex host**. Treat it as unconfirmed until that run happens. Its preflight mirrors the codex one and runs at the same point, before the consent statement: `command -v claude` for presence; `claude auth status` for auth — it prints JSON whose `loggedIn` field is the answer; `claude --version` for compatibility; and a read of `~/.claude/agents/executor.md` for the pin — the frontmatter `model:` and `effort:` keys the launch line carries. A false login, a non-zero exit, a version below `2.1.241`, an unparseable version, or an absent or keyless pin source degrades by the ladder below with nothing yet announced. `2.1.241` is the minimum version this recipe's sandbox schema and validation behavior have been checked against; the floor may move when those controls change.

  ```bash
  cd <worktree> && claude -p --permission-mode acceptEdits --no-session-persistence \
    --setting-sources "" \
    --settings <scratch>/<unit>/claude-settings.json \
    --model <model> --effort <effort> \
    < <scratch>/<unit>/packet.md > <scratch>/<unit>/evidence.md
  ```

  Before launch, the coordinator writes `<scratch>/<unit>/claude-settings.json` with its file tool, substituting the shared repository's absolute path for `<shared-root>`:

  ```json
  {
    "sandbox": {
      "enabled": true,
      "failIfUnavailable": true,
      "autoAllowBashIfSandboxed": true,
      "allowUnsandboxedCommands": false,
      "filesystem": {
        "denyWrite": ["<shared-root>"]
      }
    }
  }
  ```

  Validate that exact file before launching:

  ```bash
  CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 \
    claude --setting-sources "" \
      --settings <scratch>/<unit>/claude-settings.json doctor \
      > <scratch>/<unit>/claude-doctor.txt 2>&1
  ```

  The launch gate passes only when that command exits zero and the coordinator's read of `claude-doctor.txt` finds no `Invalid settings` block for any loaded source. A missing report, a rejected file, a validation error, or an unsupported CLI version degrades the unit without launching `claude -p`. Claude's print mode silently ignores settings that fail validation, so the print launch is never used as its own validation probe; `doctor` is, and its report is checked because it can describe invalid settings while still exiting zero. `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` keeps this local validation pass from making update, telemetry, or feature-flag calls; it applies to `doctor` only, not to the executor launch.

  The empty `--setting-sources` value suppresses the user, project, and local settings sources, so none can merge an ambient `sandbox.excludedCommands` entry into the generated policy. Managed settings remain authoritative and load independently of that flag, so the coordinator preflights their effective sandbox policy before launch: a nonempty `excludedCommands`, an unreadable or otherwise unresolved managed source, or a CLI that cannot honor the empty source list degrades the unit without launching Claude. An excluded command runs outside the sandbox even when `allowUnsandboxedCommands` is false, so this is a fail-closed containment gate, not a compatibility check.

  For a launch that passes that gate, the leading `cd` pins the working root (`claude` has no `-C` equivalent), so every `<scratch>` path is absolute. `--permission-mode acceptEdits` authorizes built-in edits inside that root; the generated settings separately put Bash and every child process behind Claude's OS sandbox, auto-approve commands that stay inside it so the executor can run its criterion headlessly, fail the launch when the sandbox is unavailable, disable its unsandboxed retry escape hatch, and deny writes to the shared tree explicitly. A managed policy may still tighten or deny the launch. `--no-session-persistence` is the mirror of `--ephemeral`. Packet on stdin and evidence to a file work exactly as above. The pin is read from the YAML frontmatter of the installed `~/.claude/agents/executor.md` — its `model:` and `effort:` keys — for the same reason: `claude -p` loads no agent definition of its own.

- **No sandbox bypass.** No recipe here passes `--dangerously-bypass-approvals-and-sandbox`, `--dangerously-skip-permissions`, or any other flag that weakens a sandbox or approval layer, and none is added to one at run time. `--sandbox workspace-write` and Claude's generated hard-fail sandbox policy are the engine-side write ceilings; `acceptEdits` authorizes in-root built-in edits but substitutes for neither. `./executor-contract.md` § *Execution boundaries* already makes the live parent sandbox, approval setting, and managed security policy authoritative over any adapter or recipe: a launch that cannot write, or a verify command the sandbox blocks, is a blocker to report, never a flag to widen.

- **Profile fallback for the pin.** Should `-c model_reasoning_effort=<effort>` turn out not to compose with `--sandbox workspace-write` on some host, `codex exec` also accepts `-p <name>`, which layers `$CODEX_HOME/<name>.config.toml` over the base user config and can carry `model` and `model_reasoning_effort` instead. It is a fallback, not the recipe: it buys a second installed file that duplicates the adapter-owned pin and must be kept in step. Take it only where the `-c` route is demonstrably rejected.

## Cross-run rules

These bind every `-x` run on either engine above, and `./executor-contract.md` § *Write-mode engine registry* restates none of them.

**Worktree always.** A cross executor never touches the shared tree. Every `-x` unit that runs on `cross` — a serially delegated one included — gets a coordinator-managed worktree as its effective root and comes back through the returned-worktree surface check; `./parallel-batch.md` owns the seeding, that check, and the removal, and they apply here unchanged. Its seeding rule is **per unit, not batch-only**: a serial `-x` unit's worktree is seeded to the shared tree as that tree stands **at that unit's launch**, uncommitted work included, so a unit depending on an earlier one sees the earlier one's incorporated work instead of a bare copy of `HEAD`. This is stricter than the native path because a foreign engine's containment is its own CLI sandbox policy rather than the host's permission layer, and the surface check catches any returned change outside the unit's declared surface before incorporation. Serial `-x` therefore means at most one worktree **live at any moment** — a fresh one per unit, never one reused across units, since each unit's baseline has to have advanced past the one before it — and never the shared tree. The flag adds no batch-width cap: `./parallel-batch.md`'s eligibility conditions bound a cross batch exactly as they bound a native one.

**The verify criterion is retargeted, not rewritten.** A unit's criterion is often written against the shared tree — an absolute repository path, an explicit `cd`. Run verbatim inside a worktree, such a criterion `cd`s straight back into the shared tree and verifies there, defeating worktree-always while still reporting a pass, so nothing surfaces the escape. When a criterion names a path outside the unit's worktree the coordinator therefore **retargets it at that worktree**, and the packet carries both forms: the criterion verbatim, and the retargeted form the executor runs. Only the root moves — what is asserted and what counts as passing are never changed by a retarget. The coordinator's own post-incorporation re-proof then runs the criterion **as written**, on the integrated tree.

**Content leaves the machine.** What ships to the other vendor is a working copy of the repository, not a prompt — `./agent-fanout.md` § *Probe contract*'s rule at the exposure a whole tree carries. `-x` is itself the consent, held to that rule's own standard: use the cross engine only on work the user already uses that vendor's CLI on, and ask first when in doubt. Once per run, before its first cross launch, the coordinator states in chat which vendor receives the work and that what it receives is a working copy of the repository — once per run, not once per unit and not once per session. Each engine's presence-and-auth preflight above runs **before** that statement, so an unavailable or logged-out CLI degrades without the coordinator having announced a working copy leaving a machine it never left. And the containment bounds writing, not reading: the recipes' sandbox policies ceiling what an executor *writes*, while what it can *read* is whatever the user can. The statement is exact about what ships and understates what is reachable: `-x` is consent to that wider exposure, not to the shipped copy alone.

**Cleanup.** An `-x` run leaves nothing of itself on disk. The recipes' session flags write no engine session files; the coordinator removes every unit's scratch packet, scratch evidence, generated engine-settings file, and Claude doctor report — they quote or encode repository constraints and local paths, and one run's units each keep their own set — along with the worktrees `./parallel-batch.md` already requires removing, whether the run finished, degraded, or failed. The coordinator's own scratch goes the same way once the evidence it carries has been recorded — content baselines, per-unit pre-fix captures, change-set ledgers — since it quotes the same repository content the packets do, and clearing the packets while leaving it behind clears nothing.

**Degradation — `cross`, then `native`, then the binding.** An absent or unauthenticated CLI, or a failure mid-unit, degrades that unit to `native`; a `native` failure then enters the consumer's own **Fallback** in `./executor-contract.md` § *Bindings*, which is the ladder's last rung. Consumers name that rung as their binding's **Fallback** rather than spelling out what it resolves to — it is per-binding and, in two of the three, per unit kind, so a spelled-out rung would be wrong for a batch unit. A degraded run **stays on `native` for its remaining units** rather than retrying `cross` unit by unit. A degraded unit takes **the placement its new engine defines**: a serially degraded unit moves to the shared tree, and any worktree already seeded for it is discarded with its partial work before the native re-run — the mid-unit degrade being the case that needs saying, since a half-finished cross attempt is not the re-run's baseline. The degrade is **announced in chat** — once, with its reason — as well as recorded in the consumer's report: degrading silently spends the quota `-x` was chosen to save, so it owes more than the probe contract's recorded `skipped (<reason>)`. The announcement carries the engine the run is now on, that staying there is settled for the remaining units so no per-unit retry is coming, and whether any work had already left the machine — a degrade before the first launch means none had, the most reassuring fact available at that point. A degrade changes the engine and the placement that engine defines; it is never cover for widening scope or relaxing a gate.
