# Executor Engines: Cross-Vendor

The cross-vendor engines a write-mode `-x` run launches its executor on — each one's launch recipe, the presence-and-auth preflight and policies that bound it, how the model pin reaches a launch that loads no adapter, and, in § *Cross-run rules* below, everything a cross run holds to whichever engine it lands on — the second preflight that asks whether the engine's sandbox can run a unit's criterion at all among them. This is the write-mode counterpart of `./probe-engines-cross-vendor.md`, which keeps the read-only probe recipes. The contract binding every executor is `./executor-contract.md`; its § *Write-mode engine registry* registers `cross` and points here for all of the above, restating none of it — what stays there is the packet shape, which § *Launch packet* owns for both engines alike. Read this file only when a cross launch is imminent.

**These are the write-mode recipes.** The read-only twin is `./probe-engines-cross-vendor.md`, a near-homographic filename whose `codex exec` recipe differs from the one below in several places — the twin carries no model pin, roots at a working root rather than a worktree, and writes to a flat scratch layout instead of a per-unit one — of which the permission-and-sandbox pair for each engine is security-critical: `--sandbox workspace-write` here against `--sandbox read-only` there, and `--permission-mode acceptEdits` plus the hard-fail sandbox settings here against `--permission-mode plan` there. Those are the controls to check first, and a write-capable probe launched on a read-only skill reads as a perfectly ordinary command; the others are why a recipe cannot be derived from the twin by swapping it. So take a recipe from the path the skill in hand cites, never from whichever of the two files you happen to have read most recently: a skill whose fan-out is read-only never takes a recipe from this file.

- **`codex`** — OpenAI Codex CLI, headless. The cross-vendor executor when the host is Claude Code. Requires `codex` on PATH, an active login, and a readable pin source, all checked **before** the once-per-run consent statement below — `command -v codex` checks presence, `codex login status` checks auth, and a read of `~/.codex/agents/executor.toml` confirms the `model` and `model_reasoning_effort` keys the launch line carries; a non-zero exit or an absent or keyless pin source degrades by the ladder below with nothing yet announced. A login that lapses between the preflight and the launch still surfaces at run time and degrades the same way; the preflight narrows that window, it does not close it.

  ```bash
  codex exec --ephemeral --sandbox workspace-write --skip-git-repo-check \
    -m <model> -c model_reasoning_effort=<effort> \
    -C <worktree> -o <scratch>/<unit>/evidence.md - < <scratch>/<unit>/packet.md
  ```

  The packet goes in on stdin, never as a command-line argument: the coordinator writes it to `<scratch>/<unit>/packet.md` with its file tool, and the trailing `-` makes `codex exec` read it from stdin — so a `$`, backtick, or apostrophe in the packet is data, not shell syntax to expand or execute (`<scratch>` is an absolute path). The probe file gives the same reason for a prompt; it binds harder here, because a write-mode packet quotes finding text, diffs, and file contents verbatim. The per-unit subdirectory is what keeps a run's second unit from overwriting the first's packet and evidence: one run shares one `<scratch>`, and an earlier unit's evidence is still the coordinator's to read after a later one has launched. `<worktree>` sits **outside** that subdirectory — a sibling such as `<scratch>/worktrees/<unit>`, never `<scratch>/<unit>/` itself, whose symmetry is a trap: a worktree rooted there holds `packet.md` and `evidence.md` at its root, which the returned-worktree surface check then reports as new untracked paths and fails as a scope escape on every unit.

  `--sandbox workspace-write` is the engine-side write ceiling; `-C <worktree>` is the coordinator-managed worktree the registry requires as the unit's effective root; `-o` captures the final message — the contract's six-heading evidence report — for the coordinator to read; `--ephemeral` leaves no session files; `--skip-git-repo-check` drops Codex's own repository precondition, so the launch turns on the coordinator's placement rather than on whether that check recognizes the seeded root — a linked worktree's `.git` is a file pointing into the parent repository, not a directory.

  `-m` and `-c model_reasoning_effort=` carry the pin, **read at launch time from the installed `~/.codex/agents/executor.toml`** — its `model` and `model_reasoning_effort` keys. `codex exec` has no agent selector, so that adapter never loads and its values have to travel on the launch line; reading them instead of copying them keeps the installed adapter as the pin's authoritative owner (`./executor-contract.md` § *Write-mode engine registry* → **Adapter defaults**) and keeps the registry's retune affordance working — retuning the installed definition retunes the cross launch with it. (`-c` takes a dotted config path whose value is parsed as TOML, falling back to a literal string.) The adapter's `sandbox_mode` is deliberately *not* read through: the sandbox is stated on the launch line, so a retuned adapter cannot widen it.

- **`claude`** — Claude Code, headless. The cross-vendor executor when the host is Codex — the mirror of the above, written as the mirror and **not yet exercised from a real Codex host**. Treat it as unconfirmed until that run happens. Its preflight mirrors the codex one and runs at the same point, before the consent statement: `command -v claude` for presence; `claude auth status` for auth — it prints JSON whose `loggedIn` field is the answer; `claude --version` for compatibility; and a read of `~/.claude/agents/executor.md` for the pin — the frontmatter `model:` and `effort:` keys the launch line carries. A false login, a non-zero exit, a version below `2.1.241`, an unparseable version, or an absent or keyless pin source degrades by the ladder below with nothing yet announced. `2.1.241` is the minimum version this recipe's sandbox schema and validation behavior have been checked against; the floor may move when those controls change.

  ```bash
  cd <worktree> && claude -p --permission-mode acceptEdits --no-session-persistence \
    --setting-sources "" \
    --settings <scratch>/<unit>/claude-settings.json \
    --model <model> --effort <effort> \
    < <scratch>/<unit>/packet.md > <scratch>/<unit>/evidence.md
  ```

  Before launch, the coordinator writes `<scratch>/<unit>/claude-settings.json` with its file tool, substituting the shared repository's absolute path for `<shared-root>`:

  ```json
  {
    "sandbox": {
      "enabled": true,
      "failIfUnavailable": true,
      "autoAllowBashIfSandboxed": true,
      "allowUnsandboxedCommands": false,
      "filesystem": {
        "denyWrite": ["<shared-root>"]
      }
    }
  }
  ```

  Validate that exact file before launching:

  ```bash
  CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 \
    claude --setting-sources "" \
      --settings <scratch>/<unit>/claude-settings.json doctor \
      > <scratch>/<unit>/claude-doctor.txt 2>&1
  ```

  The launch gate passes only when that command exits zero and the coordinator's read of `claude-doctor.txt` finds no `Invalid settings` block for any loaded source. A missing report, a rejected file, a validation error, or an unsupported CLI version degrades the unit without launching `claude -p`. Claude's print mode silently ignores settings that fail validation, so the print launch is never used as its own validation probe; `doctor` is, and its report is checked because it can describe invalid settings while still exiting zero. `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` keeps this local validation pass from making update, telemetry, or feature-flag calls; it applies to `doctor` only, not to the executor launch.

  The empty `--setting-sources` value suppresses the user, project, and local settings sources, so none can merge an ambient `sandbox.excludedCommands` entry into the generated policy. Managed settings remain authoritative and load independently of that flag, so the coordinator preflights their effective sandbox policy before launch: a nonempty `excludedCommands`, an unreadable or otherwise unresolved managed source, or a CLI that cannot honor the empty source list degrades the unit without launching Claude. An excluded command runs outside the sandbox even when `allowUnsandboxedCommands` is false, so this is a fail-closed containment gate, not a compatibility check.

  For a launch that passes that gate, the leading `cd` pins the working root (`claude` has no `-C` equivalent), so every `<scratch>` path is absolute. `--permission-mode acceptEdits` authorizes built-in edits inside that root; the generated settings separately put Bash and every child process behind Claude's OS sandbox, auto-approve commands that stay inside it so the executor can run its criterion headlessly, fail the launch when the sandbox is unavailable, disable its unsandboxed retry escape hatch, and deny writes to the shared tree explicitly. A managed policy may still tighten or deny the launch. `--no-session-persistence` is the mirror of `--ephemeral`. Packet on stdin and evidence to a file work exactly as above. The pin is read from the YAML frontmatter of the installed `~/.claude/agents/executor.md` — its `model:` and `effort:` keys — for the same reason: `claude -p` loads no agent definition of its own.

- **No sandbox bypass.** No recipe here passes `--dangerously-bypass-approvals-and-sandbox`, `--dangerously-skip-permissions`, or any other flag that weakens a sandbox or approval layer, and none is added to one at run time. `--sandbox workspace-write` and Claude's generated hard-fail sandbox policy are the engine-side write ceilings; `acceptEdits` authorizes in-root built-in edits but substitutes for neither. `./executor-contract.md` § *Execution boundaries* already makes the live parent sandbox, approval setting, and managed security policy authoritative over any adapter or recipe: a launch that cannot write, or a verify command the sandbox blocks, is a blocker to report, never a flag to widen.

- **Profile fallback for the pin.** Should `-c model_reasoning_effort=<effort>` turn out not to compose with `--sandbox workspace-write` on some host, `codex exec` also accepts `-p <name>`, which layers `$CODEX_HOME/<name>.config.toml` over the base user config and can carry `model` and `model_reasoning_effort` instead. It is a fallback, not the recipe: it buys a second installed file that duplicates the adapter-owned pin and must be kept in step. Take it only where the `-c` route is demonstrably rejected.

## Cross-run rules

These bind every `-x` run on either engine above, and `./executor-contract.md` § *Write-mode engine registry* restates none of them.

**Capability preflight — can the sandbox run the criterion?** Each engine bullet's presence-and-auth preflight establishes that the CLI is there and usable. It establishes nothing about whether that engine's sandbox can execute the unit's **verify criterion**, and the two failures cost differently: an absent CLI is known before anything moves, while a criterion the sandbox cannot run is invisible until a working copy has shipped, an executor has read the whole tree, and the work is done — `./executor-contract.md` § *Verification and fallback* has the executor report a capability it lacks, but that report is the end of a launch, not a gate before one. So after the criterion has been retargeted (below), the coordinator probes the capabilities that criterion needs, under the sandbox rather than beside it: an unsandboxed rehearsal proves nothing, since it is the sandbox that denies. The probe runs **in that unit's worktree**, so seeding — pins included, since the tool-state class below asks precisely whether the pinning took — comes before the probe rather than at the launch the probe gates; a denied unit's worktree is discarded with the degrade, as **Degradation** below already requires. **What a probe wrote is the coordinator's to clear before the launch it gates.** These probes execute real commands in a worktree already seeded from the batch baseline, and the closure rule below turns one criterion into every leg the manager runs for that name, so a leg that emits a file the project tracks — a `prebuild` code generator, a formatter, a lockfile refresh — leaves the worktree diverged from that baseline before the executor has started. `./parallel-batch.md` § *Coordinator-side parallel batch*'s returned-worktree surface check then reads that divergence as the unit's own change: incorporated as work the executor never did where it sits inside the declared surface, and a scope escape that discards the worktree and drops the unit into the serial fallback where it does not. Prove the clearing with that same gate — `check <worktree> --baseline <batch baseline> --surface <the unit's>` run after the probes and before the launch, whose whole trailer is the evidence: `delta 0`, and no third segment. A nonzero `ignored-divergent` counts a git-ignored path a probe left inside the surface — `check` reports it at exit 0 and `apply` later refuses it, so exit status is not the signal here. Clear what the trailer names, `--prune` the path at the baseline capture (`./parallel-batch.md` § *Coordinator-side parallel batch*), or re-seed the worktree, before the executor goes. Where the probe runs relative to the consent statement follows from what it ships: `codex sandbox` runs one local command under the engine's sandbox and launches no model, so it runs **before** the statement like the presence-and-auth preflight; the `claude` probe is itself a `claude -p` launch, so it runs only **after** the statement — a probe that sends a criterion-shaped command to a vendor cannot precede the sentence that says content is leaving. On `codex` the vehicle is `codex sandbox`, which surfaces the denial directly — with the policy stated on its line exactly as the launch line states it, `cd <worktree> && codex sandbox -c 'sandbox_mode="workspace-write"' -- <command>`, since the subcommand otherwise takes whatever `~/.codex/config.toml` says. The root is pinned with `cd`, not `-C`: on codex-cli 0.149 passing `-C` makes `--permission-profile <name>` — backed by a `[permissions]` table in the config — mandatory, and the command exits 2 without it, while the same command run from inside the worktree needs neither. Its writable roots are the working directory, `/tmp`, and `$TMPDIR`, which is what makes an unpinned lock under the shared checkout fail here as it fails in the launch. The subcommand's interface moves between releases, so a usage or configuration error from the probe is **preflight unavailable**, not a denial: the unit launches unprobed with that recorded, and only a denial the command itself reports degrades it; `claude` has no separate subcommand, so its probe is a `claude -p` launch under the already-generated settings file carrying a criterion-shaped command and no edit surface — unconfirmed, like the rest of that entry.

**Probe the classes the criterion actually needs, never a fixed list:**

- **The package manager's own network egress.** A criterion written as a package-manager script reaches the wrapper binary before it reaches any project command, and a modern wrapper goes to the network on its own account — resolving the version the repository pins it to, verifying that release's signature — before it has run a line of the script. Under a sandbox that denies that egress — one with no network, or one whose proxy refuses the host — that reach does not fail fast: it stalls until the wrapper's own timeout and only then refuses, so every probe written as a wrapper invocation pays minutes to learn one thing, and the criterion underneath is never reached at all. Probe it with a **sentinel** — `<wrapper> --version` under the engine's sandbox — and run that sentinel **before any full-criterion probe**. It is the cheapest question the wrapper answers, and its answer reroutes everything after it: a denied wrapper means each command in the closure below is probed as the **direct binary** the script resolves to rather than as a script name, and the launched executor's retargeted criterion runs the same way. Environment switches and offline flags that promise to skip the resolution are not a second sentinel — they are the same egress under another name, they stall identically, and probing them spends the bound below once per switch to re-learn one denial. One sentinel answers for the wrapper.
- **Tool state written outside the invocation root.** A build tool that keeps cache, daemon, or workspace-metadata directories resolves them from its own notion of the workspace, not from where it was invoked, and a workspace-write sandbox denies the write. It surfaces as a permission error from the *tool*, which reads as a broken toolchain rather than as a sandbox denial and costs the diagnosis. Pinning those directories into the worktree is the fix and belongs to seeding (`./parallel-batch.md` § *Coordinator-side parallel batch* → **Run**); what this probe establishes is whether the pinning took.
- **External daemons and ports.** A criterion reaching a container runtime, a Unix socket outside the root, or a loopback TCP listener is denied structurally: nothing inside the recipes' ceilings opens it, and widening one is exactly what **No sandbox bypass** above forbids. A criterion of this shape is not merely slower on `cross` — it cannot run there, and no retry changes that.

**Probe the criterion's whole closure, not its first leg.** A criterion is rarely one command. A workspace script that recurses over packages expands to one command per package, and a package's own script may be several commands joined together, each a separate shell command with its own capability profile. Expand the criterion to that closure before probing anything, and account for **every** command in it — which of them a probe actually runs is the cache check below.

The stopping condition is **everything the package manager executes for that name** — not everything reachable by reading the named script's definition, which is the narrower thing and the one that misses legs. Concretely: read the script's definition and split every join whose legs the manager runs unconditionally — `&&`, `;`, and `run-s`/`npm-run-all`-style composites, which name further scripts rather than commands and expand again; leave a `||` alternative and a pipeline whole, one probe unit each, because a probe executes what it is handed: a right-hand alternative does not run in a passing run, so probing it alone performs an action the criterion never would, and a pipeline's stages are one command the manager never runs as two, so probing a consumer stage alone asks it for input nothing is producing and buys a stall that `hung` cannot tell from a denial; follow each recursive invocation to the per-package scripts it reaches and split those the same way; drop the packages that do not define the script at all; and include the manager's **implicit lifecycle hooks**, `pre<name>` and `post<name>`, wherever a script name is reached, ordered around it and split like any other leg. The hooks are the legs no reading of the named script can reach — they are resolved from the package's script table by name, so a `pretest` of `docker compose up -d` is invisible to an expansion that reads `test` — and whether they run is a property of the manager, not the repository: npm, Yarn classic, and bun run them automatically, pnpm only under `enable-pre-post-scripts`, and Yarn 2+ not at all. Resolve that from the wrapper the sentinel above already identified. What comes out is the candidate list — the `--command` set the cache check below reduces to the commands actually probed. The recursive invocation itself is not on it — it is the wrapper the sentinel already answered for; its leaves are. Probing the first package's command alone answers for one package and silently asserts the rest, and it is the leg nobody expanded — a deploy dry-run reached through `build`, a code generator reached through `test` — that carries the class the sandbox denies, because the legs a coordinator thinks of are the ones that look like the criterion's name.

**A `codex sandbox` probe runs under a bound.** Default **60 s** per probe, enforced by the **coordinator's own tool-call timeout**: the `codex sandbox` subcommand takes no timeout option, so the tool call wrapping it is the only place a bound can live, and a bound nobody enforces is a preference. 60 s because it clears the slowest green answer by about half again — in the run this bound comes from, direct-binary criterion commands answered in 33–41 s of wall clock under that timeout; a later run's answered in 3 s — while sitting far below the stalls that motivated it, sentinels still running at 45 s and at 120 s and resolving to a refusal either way. Deviate upward for a criterion whose own runtime is known to exceed the bound, and state the deviation with the answer; deviating because a probe *might* be about to finish is how a preflight costs more than the launch it protects. This bound does not touch `./agent-fanout.md` § *Probe contract*'s "a probe has no fixed time budget", and is not an exception to it: that rule governs a **delegated model probe**, whose elapsed time is work being done for the session and whose progress no timeout can judge, while this is one local command run under a sandbox to ask a single yes-or-no question the sandbox answers immediately or not at all — a command still running at a minute is answering with a stall. A probe that reaches the bound records the command it exercised as `hung` and degrades it **exactly as a denial**: same degrade path, same announcement, same cache answer, because a capability the sandbox will not let the criterion reach in bounded time is a capability the unit does not have, and the distinction between a refusal and a stall is a diagnosis the run is not owed.

**The `claude` vehicle's probe takes no bound**, and the paragraph above does not reach it. That probe is a `claude -p` launch (above), not a local command run under a sandbox, so it is a **delegated model probe** — the class the bound's own justification names as belonging to the other rule. What governs it is that section's **no fixed time budget** clause — `./agent-fanout.md` § *Probe contract (every engine)*, that one clause and the waiting rule it carries: waited on and reported per `./delegated-waiting.md` § *How to wait*, and called off by the user rather than by a timeout. The clause is cited rather than the section because the section's read-only clause forbids a probe from running the project's build or suite, which is exactly what a capability probe exists to attempt: its whole question is whether the sandbox will let a criterion-shaped command run, and it is answerable no other way. That clause therefore does not reach a capability probe on either vehicle — the one exemption, named here rather than left to be inferred from a citation that would otherwise forbid the probe's purpose. Bounding it at 60 s would time out an ordinary model launch, record it `hung`, and degrade every unit off `cross` at preflight on a Codex host — a preflight that denies every unit is not gating anything. `./delegated-waiting.md` § *How to wait* already resolves a timed-out delegated call the other way, by re-entering it or leaving it to the notification, and an empty return there is not a finished agent; the two rules would otherwise contradict each other on the same call.

A denied capability degrades that unit before its launch, per **Degradation** below. What was probed and what it answered is recorded with the degrade: a reader of the record cannot re-derive a denial from the criterion alone, and the next run would otherwise pay the same investigation again.

**A launch packet never pre-exempts a foreseen sandbox denial.** When the coordinator can foresee that a unit's criterion will hit a denial, the packet is the one place that cannot absorb it. Writing *the sandbox will refuse this, file it and carry on* into a packet launches an executor against a criterion already known not to pass, hands it a standing instruction to record the failure under the heading reserved for exactly that, and then asks intake to read past the heading the packet itself filled — spending a whole launch and a shipped working copy to reach the answer the preflight already had. A foreseen denial has two dispositions and no third: **pinned away at seeding**, so the command runs, or **degraded before launch**, so the unit moves off `cross` under **Degradation** below; both are settled before anything leaves the machine. `./executor-contract.md` § *Write-mode routing* keeps its intake meaning unweakened here — an entry under `Blockers or attempted scope escapes` means what that section says it means, and a blocker the packet invited is no exception to it. A coordinator that would have to override its own intake rule to accept a report has already decided the unit wrong.

**The probe answer is cached per repository; the cache is never the authority.** A capability answer is per-machine derived state — the same class as `maintain`'s markers — so it belongs in the machine's run-state directory and never in the task folder or the repository (`./task-store.md` § *The root registry* → **Run state is not config**). `node <kit-root>/scripts/cross-capability.ts` owns that cache — `<kit-root>` per `./task-store.md` § *Resolving `<kit-root>`* — and `<kit-root>/SCRIPTS.md` § *`scripts/cross-capability.ts`* owns its three subcommands' CLI forms, the entry shape, the state-directory override, the fingerprints that decide staleness, the exit statuses, and the `sweep` that retires the per-engine files predating the cache: read that section, not the whole file, before assembling a command from the flags this one happens to name. Absence is the normal state and never a gap — it means no run has probed this repository on this machine yet. The cache saves the investigation, not the check: a probe that runs takes tens of seconds, and the run it protects is measured in minutes.

**`check` runs before any probe, and its verdicts are the probe list.** Once the closure above is expanded and before a single command is probed, run `check <repo>` with the engine facts this run knows — `--engine`, `--cli-version`, `--model`, `--effort`, `--network-access`, `--network-proxy` — and one `--command "<package dir>: <shell command>"` per unit of that closure. Each key is written in the form the last recorded sentinel answer dictates — the direct binary where that answer is `denied` or `hung`, the wrapper form where it is `allowed` or unrecorded — and a fresh sentinel answer that flips it re-keys the closure and re-runs `check`, since the verdicts were answering for commands the criterion no longer runs. The two network flags are read from the engine's configuration at probe time rather than assumed — on codex, `sandbox_workspace_write.network_access` and whether `features.network_proxy` is enabled — because a workspace-write sandbox with network on behind a proxy that refuses a host stalls the wrapper exactly as no network does, and only the policy recorded beside the answer tells the next run whether a widened allowlist has moved it. The report that comes back **is** the input to everything after it. A command it verdicts `match` is believed and never probed: its stored `answer`, `binary`, and `statePins` seed the run, the pins going to seeding so a denial already pinned away is not re-derived from a failure this run will no longer see. A command it verdicts `stale` or `absent` is probed, and no other command is — probing a `match` spends the bound above to re-learn what the entry already says, and skipping a `stale` trusts an answer whose fingerprints have moved. `check` always exits 0 once it has written its report, so the verdicts are read out of that JSON and never inferred from a status. Every probe that runs then goes back through `record <repo>` — one invocation per answer, since `record` takes exactly one `--command` — carrying the `--classes` that execution exercised, the `--answer`, the `--binary` it resolved where the probe ran one, the `--state-pins` that made a denial pass, and the `--config-files` that answer read. What counts as those config files is resolved per answer from what was actually probed — the tool configs the pins address, the compose files an external-daemon answer read, the wrapper pin — the never-a-fixed-list rule of § *Probe the classes the criterion actually needs* applied to the cache. At close-out, quote `check`'s `summary` line verbatim instead of hand-writing a claim about what the next run will cost.

**An answer claims exactly the classes its own execution exercised** — no more, and never fewer. One execution answers for as many classes as it touched: a suite whose global setup opens a container while its runner writes cache outside the invocation root is probed once and recorded under both. A class no command exercised is never recorded, because an unprobed class is not the answer "none observed" — recording one asserts about the legs nobody expanded exactly what the closure rule above exists to stop, and the unexpanded leg is where the denial was. Silence about a class re-probes; a line saying it came back clear is a claim no probe supports, and it survives into the runs it misleads. Two consequences bind. A command probed as the **direct binary** the sentinel above rerouted it to never answers for `package-manager wrapper egress` — that execution made no wrapper call — so `record` refuses that pairing outright, and the executor's retargeted criterion has to run the same direct form the probe ran. And a `match` is matched on the command key and the fingerprints, not on classes, so an answer `check` calls `match` is still re-probed when the criterion in hand needs a class its recorded `classes` do not carry.

**A probe's record carries the bound it ran under**, in that answer's `--note`, with any deviation from the 60 s default stated there beside the answer. A `hung` is worth only as much as the bound that produced it: `hung` at 60 s is the stall the paragraph above describes, while `hung` under a deviation raised for a criterion whose own runtime exceeds the default may be measuring the criterion rather than the sandbox — and nothing in the answer itself tells the next run which it read.

**The answer is the probed command's own exit status**, captured before any consumer can overwrite it: send the probe's output to a file and echo the status by itself — `<probe> > <scratch>/probe.txt 2>&1; echo EXIT=$?` — then read the output from that file. A pipe reports its **last** stage, so `<probe> | tail -20; echo EXIT=$?` files `tail`'s success as the probe's and records a denial as `allowed` — a wrong answer the next `check` then verdicts `match` and no probe revisits.

**Worktree always.** A cross executor never touches the shared tree. Every `-x` unit that runs on `cross` — a serially delegated one included — gets a coordinator-managed worktree as its effective root and comes back through the returned-worktree surface check; `./parallel-batch.md` owns the seeding, that check, and the removal, and they apply here unchanged. Its seeding rule is **per launch, not batch-only** — a segment launch (`./executor-contract.md` § *Segment launches*) is one launch, one worktree, its units merging back together through that same surface check: a serial `-x` unit's worktree is seeded to the shared tree as that tree stands **at that unit's launch**, uncommitted work included, so a unit depending on an earlier one sees the earlier one's incorporated work instead of a bare copy of `HEAD`. This is stricter than the native path because a foreign engine's containment is its own CLI sandbox policy rather than the host's permission layer, and the surface check catches any returned change outside the unit's declared surface before incorporation. Serial `-x` therefore means at most one worktree **live at any moment** — a fresh one per launch, never one reused across launches, since each launch's baseline has to have advanced past the one before it — and never the shared tree. The flag adds no batch-width cap: `./parallel-batch.md`'s eligibility conditions bound a cross batch exactly as they bound a native one.

**The verify criterion is retargeted, not rewritten.** A unit's criterion is often written against the shared tree — an absolute repository path, an explicit `cd`. Run verbatim inside a worktree, such a criterion `cd`s straight back into the shared tree and verifies there, defeating worktree-always while still reporting a pass, so nothing surfaces the escape. When a criterion names a path outside the unit's worktree the coordinator therefore **retargets it at that worktree**, and the packet carries both forms: the criterion verbatim, and the retargeted form the executor runs. Only the root moves — what is asserted and what counts as passing are never changed by a retarget. The coordinator's own post-incorporation re-proof then runs the criterion **as written**, on the integrated tree. A retarget cannot reach a leg **no engine can execute** — a criterion half needing a browser, a device, or a person's eyes. Such a leg is named at the capability preflight above, beside the classes the sandbox denies, and it travels in the packet as an **explicitly open leg**: the executor proves the executable half and reports the open one untouched. It is never split off to leave a smaller criterion the run can pass — that records the step proved against something the plan did not write, the same substitution *only the root moves* forbids at the other end. Until the open leg is verified — in-session where the coordinator can run it, otherwise against the user's reported best-available proxy — the step stays **unproved**, and what that costs the run is the consumer's: for `implement-task`, `./implement-task-edges.md` § *An open criterion leg*.

**Content leaves the machine.** What ships to the other vendor is a working copy of the repository, not a prompt — `./agent-fanout.md` § *Probe contract*'s rule at the exposure a whole tree carries. `-x` is itself the consent, held to that rule's own standard: use the cross engine only on work the user already uses that vendor's CLI on, and ask first when in doubt. Once per run, before its first cross launch, the coordinator states which vendor receives the work and that what it receives is a working copy of the repository — once per run, not once per unit and not once per session. That statement has to land in the coordinator's **user-visible reply**, the prose the user actually reads: a reasoning block, a thinking trace, a tool preamble, or any other narration the host may collapse, summarize, or drop is not the reply and does not satisfy this, however plainly the sentence is written there. Consent the user never saw is not consent, and the failure is invisible from the inside — the coordinator has composed the sentence, so nothing about the run looks unannounced while the working copy ships. Each engine's presence-and-auth preflight above runs **before** that statement, so an unavailable or logged-out CLI degrades without the coordinator having announced a working copy leaving a machine it never left. And the containment bounds writing, not reading: the recipes' sandbox policies ceiling what an executor *writes*, while what it can *read* is whatever the user can. The statement is exact about what ships and understates what is reachable: `-x` is consent to that wider exposure, not to the shipped copy alone.

**Cleanup.** An `-x` run leaves nothing of itself on disk but the capability answers above, which are derived per-machine state rather than run scratch and are kept deliberately — clearing them would buy nothing and cost the next run the same investigation. The recipes' session flags write no engine session files; the coordinator removes every unit's scratch packet, scratch evidence, generated engine-settings file, and Claude doctor report — they quote or encode repository constraints and local paths, and one run's units each keep their own set — along with the worktrees `./parallel-batch.md` already requires removing, whether the run finished, degraded, or failed. The coordinator's own scratch goes the same way once the evidence it carries has been recorded — content baselines, per-unit pre-fix captures, change-set ledgers — since it quotes the same repository content the packets do, and clearing the packets while leaving it behind clears nothing.

**Degradation — `cross`, then `native`, then the binding.** An absent or unauthenticated CLI, or a failure mid-unit, degrades that unit to `native`; a `native` failure then enters the consumer's own **Fallback** in `./executor-contract.md` § *Bindings*, which is the ladder's last rung. Consumers name that rung as their binding's **Fallback** rather than spelling out what it resolves to — it is per-binding and, in two of the three, per unit kind, so a spelled-out rung would be wrong for a batch unit. A degraded run **stays on `native` for its remaining units** rather than retrying `cross` unit by unit. **A capability degrade is the one exception, and it moves the unit alone.** An engine whose sandbox cannot run *this* criterion has not failed — it serves the next unit exactly as well — so the run stays on `cross` and only the units the preflight denied move across. That is why the triggers are named apart: an absent, unauthenticated, or failed CLI says nothing more is delegable there, while a denied capability says one criterion is not, and collapsing the second into the first spends the quota `-x` was chosen to save on every remaining unit of the run. It is announced on the same terms, naming the criterion and what the probe denied, and — coming before that unit's launch — it carries the reassurance every pre-launch degrade carries: no working copy of that unit left the machine (on `claude`, the probe's own command did, after the statement that said so). A degraded unit takes **the placement its new engine defines**: a serially degraded unit moves to the shared tree, and any worktree already seeded for it is discarded with its partial work before the native re-run — the mid-unit degrade being the case that needs saying, since a half-finished cross attempt is not the re-run's baseline. The degrade is **announced in chat** — once, with its reason — as well as recorded in the consumer's report: degrading silently spends the quota `-x` was chosen to save, so it owes more than the probe contract's recorded `skipped (<reason>)`. For an absent, unauthenticated, or failed CLI the announcement carries the engine the run is now on, that staying there is settled for the remaining units so no per-unit retry is coming, and whether any work had already left the machine — a degrade before the first launch means none had, the most reassuring fact available at that point. A capability degrade carries the one unit that moved and the criterion the probe denied, the run staying on `cross` for everything else. A degrade changes the engine and the placement that engine defines; it is never cover for widening scope or relaxing a gate.
