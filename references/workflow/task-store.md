# Store-Level Artifacts and the Root Registry

The two optional things that sit *outside* any one task folder — the files a task **store** may carry, and the machine registry that names this machine's task roots — split out of `./task-layout.md`, which keeps the folder shape and the discovery rules. **This file is the single source of truth for both.** Read it when a store carries store-level artifacts — the shared group context of § *Shared group context* among them — or a root registry (`~/.config/agents-kit/config.json`), or when registering one.

## Store-level artifacts (optional)

A directory tree that groups many task folders — a task **store**, like a central `Tasks/` repo with area subdirectories — may carry store-level files. Every kind below is optional; skills detect them by existence and degrade silently when absent. There is deliberately **no standing listing artifact** — "what is in the store" is derived on demand by walking the registered roots (`./task-layout.md` § *Discovery rules for skills*), never kept on disk, because a derived enumeration goes stale silently and duplicates the walk that would have found the truth.

- **`DECISIONS.md` — the home for project-scoped decisions.** A registered root, or an area within it, may carry a `DECISIONS.md`: the single home for decisions that outlive any one task, each entry numbered and dated. Tasks cite an entry as `Decision #N — <root-relative path>` (plain text, per the cross-folder citation rule in `./one-home.md` — a store-level doc has no slug, so it keeps the path form). Task-local decisions stay in the task's own files; a task that inlines a copy of a project decision for self-sufficiency must name `DECISIONS.md` as the source.
- **`DOC_CONVENTIONS.md` — org documentation conventions.** A registered root, or an area within it, may carry a `DOC_CONVENTIONS.md`: the single home for the org-specific documentation conventions the kit's format checklists deliberately exclude — people/mention tables, house style, page-handling conventions for published docs. Discovered by **walk-up**: from the task folder, check each ancestor directory up to the registered root that contains it — the root is the bound, and an unregistered task folder walks up to its project root instead; the nearest file wins (an area-level file overrides a root-level one). Absent → only the kit's generic format bars apply. Consumed by documentation-domain work — the pack checklists cite this role rather than hardcoding a path.
- **`GROUP_CONTEXT.md` — shared grounding for the tasks below one directory.** § *Shared group context* owns it: which files a task inherits, in what order, and what bounds the chain. It differs from the two above in who reads it — ordinary task work, on every invocation — and in how much of it applies: the whole ancestor chain rather than the nearest file alone.

## The root registry (optional)

An optional JSON file at the fixed path `~/.config/agents-kit/config.json` names this machine's task roots. It carries exactly one class of fact: **machine-variant paths the kit cannot derive.** **Absent is the normal state**, and means the canonical-root-only behavior each rule below names as its fallback — no install ships one, and nothing writes one unasked. The `init-config` skill proposes one from what is on disk and writes it only on confirmation; hand-authoring it is equally valid.

```json
{
  "taskRoots": [
    { "path": "~/Documents/Tasks", "label": "personal" },
    { "path": "~/Work/tasks", "label": "work" },
    { "path": "~/Documents/Repositories/agents-kit/.agents/tasks", "label": "kit" }
  ],
  "kitRoot": "~/Documents/Repositories/agents-kit"
}
```

- **Registration grants discovery.** A registered root is **listed** and **slug-resolvable** — that is what registration widens: what skills can *find*. Registration alone never makes a root somewhere they *write*: which root a new task folder lands in is decided by the creation precedence whose single home is `./task-destinations.md`. It does bound one thing besides discovery: registering a directory makes it a candidate for the selected root, and so for where an inherited chain starts — § *Shared group context* owns what that costs when one registered root sits inside another.
- **A missing path is skipped, and reported in one line per run** — never an error either way. Skipping is what lets one file describe the union of several machines; reporting is because nothing syncs this file today, which makes an unresolvable path likelier a typo than another device's layout.
- **`~` expands before a path is used, and whatever reads this file is what expands it.** The schema takes `~` precisely so an absolute `/Users/<name>/…` path cannot fail silently under the skip rule the moment the file reaches another machine — but the expansion happens where the file is read. A `scripts/*.ts` walker **handed a root as an argument** takes absolute paths only and does no expansion of its own, so a skill that forwards a registry entry to one must expand it first; handed a literal `~/…` it resolves that against the process directory and reports the root as unreadable. A script that reads this file **itself** expands its own entries, for the same reason a skill does — `scripts/task-move.ts` is the one that does today, resolving a bare slug against the roots it reads here.
- **Labels group listings.** A "which task?" prompt groups its options by `label`. The label is display grouping, not a selector: there is no filtering syntax and no new skill argument.
- **Walking a registered root is recursive, and a task folder is identified by its contents, not its position.** A registered root may nest tasks under area directories, and registration is what buys the depth: the canonical root is read one level deep unless it is itself registered (`./task-layout.md` § *Discovery rules for skills*, the home of that read rule). Walk to unbounded depth, treat any folder matching the **recognition set** (`./task-layout.md` § *One task, one flat folder*) as a task folder and never descend into one, and descend through everything else except `node_modules`, dotted names other than `.agents`, and every entry that is not a real directory — the walk `scripts/health-check.ts` already performs, prunes included. An `Archive` or `Backlog` container (each matched case-insensitively, per `./task-archiving.md` and `./task-backlog.md`) is tested before that recognition set rather than against it: whatever such a container holds, it is walked through and never itself claimed as a task folder, so a role file misfiled into one cannot turn the container into a match and hide every real folder beneath it. `.agents` is the one dotted name entered, because a canonical root sits inside it: that is what lets a project directory be registered as a root and still resolve the tasks under its `.agents/tasks`, rather than walking clean and reporting a zero indistinguishable from an empty root. A symlink fails that last test however directory-like its target, so it is neither entered nor recognized as a task folder: a linked twin is never scanned a second time, and a cycle of links can never trap the walk. **`scripts/lifecycle-constants.ts` carries the machine-readable copy of these prunes and of the ordering they open** — `WALK_SKIP_DIRS`, `TASK_STORE_DIR`, and `classifyWalkEntry` — because the walkers that enforce them cannot read prose at run time; change the prune list or the ordering here and change that module in the same edit.
- **Run state is not config, and lives apart.** `~/.config/agents-kit/` holds this file and nothing else. Per-machine state a skill derives — `maintain`'s `.maintain-last-run` marker and its session-findings files — belongs in `~/.local/state/agents-kit/`, so a config directory never accumulates mutable run data.
- **`kitRoot` names the agents-kit source checkout** — the directory holding `setup.ts`, `CORE_RULES.md`, and `references/`, not a deployed install home. It is the one entry that is not a place tasks live; skills that operate on the kit itself read it.
- **Every key is optional, and each absence has one meaning.** No `taskRoots` (or an empty one) is the canonical-root-only behavior above — the same as no file. No `kitRoot` means this machine has no source checkout registered: a skill that needs one asks for it or takes it as an argument, and never derives it from the deployed `~/.claude` copy it is running out of, which is an install home rather than a checkout. A file carrying neither key is valid and inert.

Nothing else belongs in this file. A path the kit cannot derive is a fact; a default the kit can already reason about is a preference, and preferences stay out — a threshold copied here would manufacture the second home *One home per fact* (`./one-home.md`) exists to prevent.

## Shared group context (optional)

A registered root may nest its task folders under **grouping directories** — a project, an area, a feature — and any of those may carry an optional `GROUP_CONTEXT.md`: the grounding every task beneath it inherits, maintained at one home instead of copied into each folder. **This section is the single source of truth for that contract.** Carrying none is the ordinary state, exactly as carrying no registry is, and a store without these files behaves as it always has.

**A group is not a task, and a group file never makes it one.** The recognition set (`./task-layout.md` § *One task, one flat folder*) names the role files alone, so a directory holding only a `GROUP_CONTEXT.md` and whatever sits below it is walked through — never listed, planned, executed, archived, or counted as a task. **The name is `GROUP_CONTEXT.md` exactly**, and that exactness is load-bearing: any *other* recognition-set file appearing in a group — a `CONTEXT.md`, one prefix away from the file this section invites — makes that directory a task folder in every walk that reads the set, which then stops there and never descends. The group is counted as the task and every real task beneath it disappears from slug resolution, from the health walk, and from every listing derived from either, with no diagnostic naming the cause. The health walk names the shape after the fact — `scripts/health-check.ts`'s `nested-task` finding lists the task folders a claimed one hides (`../scripts/health-check.md`) — but nothing prevents it, so at write time the spelling is the whole of the guard. It has no status, no lifecycle, no plan, no goal IDs, no `**Domain:**`, and no acceptance criteria; the tasks under it keep their own, and a progress rollup of them is precisely what this file is not. What it holds is prose — constraints, conventions, and standing facts that hold for everything beneath it — and that prose is grounding rather than instruction precedence: it informs the work as `CONTEXT.md` does, and outranks neither the kit's rules nor the task's own contract.

**What applies to a task is its ancestor chain, read root-to-task.** The sources are every `GROUP_CONTEXT.md` that exists from the containing registered root down through the task's immediate parent, in that order, and then the task's own `CONTEXT.md`. Nothing else joins them: a sibling group's file, a file below the task, and anything above the selected root are all outside the chain. Each source stays **identifiable** through the work that uses it — name the selected root, and cite each file by its path from that root in the plain-text form § *Store-level artifacts* uses, so an inherited constraint is never mistaken for a task-local one.

**The selected root is the most specific registered directory that physically contains the task**, its own `GROUP_CONTEXT.md` included and everything above it excluded, whether the task was reached by its slug or by an explicit path. Expand `~` first, compare resolved directory identities over whole path components — a root that merely shares a textual prefix is a different root — and treat the aliases of one root as that one root. A canonical root someone registers explicitly participates like any other registered directory; an **unregistered** location inherits nothing at all, which is the behavior every task outside a registered root keeps. A configured root absent from this machine is skipped under § *The root registry*'s rule and selects nothing.

**Registering a root inside another shortens the chain, silently.** The registry supports it deliberately — § *The root registry* searches an inner root on its own account, since the outer walk's prunes can leave it unreachable from above — but selection takes the most specific of the two, so every `GROUP_CONTEXT.md` between the outer root and the inner one stops applying to the tasks below. Nothing reports it: the file stays on disk, readable and unread, and the inheritance simply carries less. Register the inner directory when its tasks should ground on it alone, and leave it unregistered when they should still inherit from above.

**Lifecycle containers are transparent to inheritance.** An `Archive` or `Backlog` directory below the selected root — matched case-insensitively, per `./task-archiving.md` and `./task-backlog.md` — marks a lifecycle position rather than a group, so a `GROUP_CONTEXT.md` placed directly inside one contributes nothing while the ordinary groups on both sides of it still apply. Archiving or parking a task in place therefore leaves what it inherits unchanged; only a move between groups changes it. The selected root's own file is read whatever that root happens to be named.

**Absence is silent, unreadable is not.** A group carrying no file contributes nothing and is worth no mention. An applicable file that exists but cannot be read is an incomplete grounding read: say which file and why, rather than proceeding as though that group had nothing to say. An applicable `GROUP_CONTEXT.md` that is a symlink, or any other non-regular entry, is reported as unsupported rather than read through — grounding arriving from outside the chain is exactly what the bound above exists to prevent.

**A contradiction is surfaced, never quietly resolved by reading order.** Where an applicable group file materially contradicts the task's own artifacts, report both statements with their sources before the dependent work proceeds, under the clarification and write rules the running skill already carries. Two skill families may then correct the group file itself: `implement-task`, where execution disproves what it states (that skill's § *Correcting Grounding Where It's Wrong*), and the reconcilers — a correction whose home is an applicable group file is written there, on the extra terms `./reconciliation.md` § *The upstream ask is writable, and never rewritten quietly* sets for an external surface.

**No machinery is added for any of this.** No CLI, no registry key, no generated manifest, no cache: the files are read from disk on each invocation, so a group edited after a plan was written is seen by the next run rather than by a refresh someone has to remember. Group prose is never bulk-copied into a task, a link found in a group file does not enter the reference sweep a task performs, and the nearest-file `DOC_CONVENTIONS.md` lookup above keeps its own separate semantics.

## Resolving `<kit-root>`

Several skills run a helper out of the kit's `scripts/` directory, written as `node <kit-root>/scripts/<name>.ts`. **This section is the single home for what that placeholder resolves to**, so a skill that invokes a script cites it rather than restating the rule.

`<kit-root>` is the agents-kit **source checkout** — the directory holding `setup.ts`, `CORE_RULES.md`, and `references/`. Read it from the `kitRoot` key of `~/.config/agents-kit/config.json` (§ *The root registry* above). It is never the deployed `~/.claude` or `~/.codex` home the skill is running out of: `setup.ts` installs skills, `references/`, `CORE_RULES.md`, and the agent definitions, and **no `scripts/` directory**, so an install home cannot answer the path however plausible it looks. Deriving one from the install home is the failure this paragraph exists to stop — it produces a path that does not exist and an error that reads like a missing script rather than a missing checkout.

- **No config file, or no `kitRoot` in it** → ask for the checkout path rather than inferring one. Only when the lookup itself is in question is § *The root registry* worth reading; the key's absence already means what it means.
- **No kit root available at all** → say the script cannot be run here and stop, or fall back to whatever the citing skill names in its place. Which of the two applies is the skill's own call and each states it: a skill whose script produces a report it could reconstruct by hand says so, while one whose script performs a guarded mutation usually has none worth offering — and where the work cannot simply stop, the skill that offers one anyway says what the hand form gives up.
- **A script's own contract is `references/scripts/<name>.md`.** That file owns the script's CLI form and its stdout contract, and it is installed beside every other reference, so a skill cites it as `./references/scripts/<name>.md` and any other reference as `../scripts/<name>.md`. The design rationale behind the script is maintainer material in the checkout's `AGENTS.md` § *Source contracts*, under *`scripts/<name>.ts`*, which no run loads. This bullet is that idiom's home as well, so a skill names its script's contract without spelling the rule out again.
- **The path is used verbatim.** `kitRoot` is joined into the `node` command rather than handed to a script, and a walker given a root as an argument expands no `~` of its own (§ *The root registry*), so a `kitRoot` written with a `~` is expanded before it is joined to `scripts/`.
