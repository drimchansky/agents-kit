# CONTEXT.md Schema

The section layout of a task's `CONTEXT.md`, the static grounding beside `goals.md`, `plan.md`, `result.md`, and the optional `ticket.md`, `approaches.md`, `observations.md`, and `history.md`. When a section name or optionality changes, check the readers of these sections: `review-task`, `implement-task`, `resume-task`, and `scripts/sweep-scope.ts`, which uses References and Open Questions to bound a source check.

## The schema

Copy `../templates/CONTEXT.md`. Keep the title, `**Domain:**`, and a filled `## Problem Statement`. Add other sections only when they contain task-specific grounding; omit empty headings and literal template prompts. Readers treat absent optional sections as empty.

## Field notes

- **No `**Status:**` field.** The plan owns the task's lifecycle; a legacy line here reads as none (`./task-lifecycle.md`).
- **`**Domain:**`** names the domain pack every skill in the task loads (default `engineering`). Default to `engineering` for code or ambiguity within a coding context. When the task is clearly non-code and the domain is unclear, ask rather than stamp a wrong label.
- **Optional sections.** Add `## Recommended Direction`, `## Key Assumptions to Validate`, `## MVP Scope`, `## Not Doing (and Why)`, `## Open Questions`, and `## References` only when each has content. Key Assumptions entries are `- [ ] <assumption> — <how to test it>` checkboxes; MVP Scope carries `- **In:**` and `- **Out:**` bullets. `refine-idea` writes the conclusions its pass established; `plan-task` without a prior idea step records known assumptions only; `choose-approach` scaffolds only missing context from the problem or ticket before research; `decompose-task` records its source pointer and any settled part direction or open items. Add no `## Goals` mirror.
- **Decision history.** For a task decision settled in a group change set, write its current rule and reason in the owning context section. Append its full decision record to [`history.md`](./task-history.md). Approach comparisons follow `./task-approaches.md`.
- **Static grounding, not a scratchpad.** The user enriches it over time. Task writers apply `./task-writes.md` when correcting grounding, references, or answers. Within its change set, `start-group` may do so in every affected task below the group outside Archive and Backlog, including nested groups. Before those edits, it may scaffold a missing `CONTEXT.md` under § *The schema*. `implement-task` corrects a section its own execution disproved (its § *Correcting Grounding Where It's Wrong*). `plan-task` records the context answers it settles under `./task-writes.md`. The sole exception is the task loader's identifier repair, which may rewrite proven goal identifiers here without changing meaning (`./task-authorship.md`). Per-step notes and verify criteria belong in the plan or its result; goals belong in `goals.md`. Retained approach rationale follows `./task-approaches.md`; approach rationale that `approaches.md` does not retain belongs in task history. Downstream artifacts cite these sections rather than restating them (`./one-home.md` § *One home per fact*). A fact a sibling task needs is duplicated here, unless a `GROUP_CONTEXT.md` above both tasks holds it; then `## References` cites that file (`./task-store.md` § *Shared group context*).
- **Project-level decisions** live in the store's `DECISIONS.md` when one exists (`./task-store.md` § *Store-level artifacts*). Cite them as `Decision #N — <root-relative path>` in `## References`; an inlined copy names `DECISIONS.md` as its source.
- **With a `ticket.md` present, `## Problem Statement` cites `./ticket.md`** rather than restating it (`./ticket-format.md`). `## References` carries links surfaced during refinement or planning; the requester's own links stay in the ticket. Without a ticket, `## Problem Statement` holds the one-sentence framing.
