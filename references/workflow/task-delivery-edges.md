# Task Delivery: Re-entry, Removal, and the Live-Verification Gate

The later half of `./task-delivery.md` — the parts a run reaches only on a condition, split out of it so the creation gate every engineering task in a checkout passes through stays hot and these do not. That file owns the declarations and creation; this one owns what a **resume**, a **finalization**, and a **declaring repository** reach for. Read it from the citation that names the section you need, never as background.

## The task worktree is the run's shared tree

Where a run has a task worktree, that worktree **is** the shared tree the write-mode contracts already speak of — the effective root a serially delegated executor edits, the tree a parallel batch's worktrees are seeded from and merged back into, the tree each health boundary runs on. Nothing in `./executor-contract.md`, `./parallel-batch.md`, or a domain's verification recipe changes: they take a tree, and this file only decides which one. Where a run has none — creation skipped or degraded — the checkout itself is the shared tree, as before.

**The task folder is not among them.** Its `<task-dir>` stays where the run resolved it, under the main checkout (`./task-layout.md` § *One task, one flat folder*), whichever tree the work lands in. A repository that tracks its `.agents/tasks/` carries a second copy of the folder inside every worktree, so a run writing `**Pointers:**` and the plan's status into that copy would strand the task's own records on an unmerged branch while the main checkout's copy — the one every later run and every sweep reads — went stale.

The batch's **coordinator-managed worktrees are a different thing at a different layer**: transient scratch, seeded from the shared tree, carrying no branch, removed at merge (`./parallel-batch.md` § *Coordinator-side parallel batch*). A task worktree is durable, carries the task's branch, and outlives the run that made it.

## Re-entry on resume

A later run on the same task reads the branch from the result's `**Pointers:**` line and resolves the worktree by **matching that branch** against `git worktree list --porcelain` from the main checkout root — a `branch refs/heads/<branch>` line. Matching on the branch rather than on the derived path is what lets a run adopt a worktree the user moved or renamed; the branch is the identity, the directory is replaceable. Then, taking the **first** case that matches:

- **Branch merged — by § *Removal*'s predicate, which owns what that word means here — or gone** → **report it and create nothing.** The work has landed, or the branch was deleted deliberately; recreating it silently would open a second divergent line of work off a stale base under the same name. It is checked first because a merged branch whose worktree still stands — the pair § *Removal*'s refusal path leaves in place by design — would otherwise read as the re-entry below, and resuming onto an already-merged branch silently extends a delivered line. Ask the user which they want — a fresh branch for follow-up work, or the task treated as delivered — and take their direction.
- **Branch live, worktree matched** → re-enter it. It is this run's shared tree; nothing is created and nothing is announced beyond naming where the run is working.
- **Branch live, no worktree matches** → recreate it on the existing branch, announced, with no `-b`: `git worktree add <main-checkout-path>.worktrees/<slug> <branch>`.
- **No branch in `**Pointers:**`** → the task has no delivery vehicle yet; treat this as a first run and apply `./task-delivery.md` § *Branch and worktree creation*.

## Removal

Removal fires at **finalization** — the run that takes the task terminal and observes its pull request merged. **This section is the one home for the predicates, the resolution step, the command sequence, and what a refusal does.** Both actors below cite it and restate none of it: two copies of a removal rule drift into two different rules, which is precisely how a criterion the finalization run refuses on came to qualify an entry for the sweep.

**Resolve the worktree from the branch, never from the slug.** `git worktree list --porcelain` from the main checkout root, matched on the `branch refs/heads/<branch>` line, returns the worktree's real path — the same branch-as-identity match § *Re-entry on resume* above makes, and for the same reason. Do not reconstruct `<main-checkout-path>.worktrees/<slug>/` here: `git worktree remove` resolves its argument by real-path equality and then by unique path-suffix match, so a derived path matches neither once the user has moved or renamed the directory. The reconstructed form fails, `git branch -d` then fails behind it because the branch is still checked out, and the run records a removal that removed nothing. No branch line matches → there is no worktree to remove and the **clean** predicate has no tree to run in; the branch half below still applies.

Both predicates are required:

- **merged** — the task's work is contained in the default branch. Three proofs, taken in order, and any one suffices: the pull request the trigger above names is observed merged (`gh pr view <branch> --json state` returns `MERGED`); or the branch is an ancestor of a **freshly fetched** `origin/<default-branch>` (`git fetch origin <default-branch>`, then `git merge-base --is-ancestor <branch> origin/<default-branch>`, resolved per `./task-delivery.md` § *Branch and worktree creation*); or every commit on the branch has a patch-equivalent already in `origin/<default-branch>` (`git cherry origin/<default-branch> <branch>` prints no `+` line), which is what a rebase merge and a single-commit squash leave behind. `git branch --merged` is **not** the test, and neither is the **local** `<default-branch>`: a squash or rebase merge lands the work as a new commit, so the branch is never listed, and the fetch above moves the default branch's remote-tracking ref and not the local branch that placeholder resolves to, which stays where it was until an actual pull — which is why both proofs read `origin/<default-branch>`. Scoping the fetch to that one branch is what keeps it to that single ref, and is the exception `./task-delivery.md` § *Branch and worktree creation* → **The sanction** names. A multi-commit squash whose pull-request state cannot be read reaches none of the three — that is **unproved, not merged**, and takes the refusal path below.
- **clean** — run **in the resolved worktree**, not the main checkout: `git status --porcelain` returns nothing, and `git log --oneline <branch> --not --remotes` returns nothing, so no staged, unstaged, untracked, or unpushed work is about to be discarded.

Both hold → **preflight the branch deletion before removing the worktree.** `git branch -d` applies a containment test of its own, and it is not the **merged** predicate above: it judges the branch against that branch's upstream, or against the main checkout's current `HEAD` where there is none, and `git worktree add -b` sets no upstream under the default `branch.autoSetupMerge`. So run that same test first, from the main checkout root — `git merge-base --is-ancestor <branch> <upstream, else HEAD>` — while running it still costs nothing: the test needs no worktree, and the removal that follows spends the one thing that keeps an undeletable branch collectable as the task's whole vehicle. **The preflight failing refuses the whole removal**, not just its second command: take the refusal path below, naming the containment the branch lacks, and leave worktree and branch standing together rather than spending the worktree on a deletion that was never going to succeed.

The preflight passing → remove from the main checkout root, in this order — `git branch -d` fails outright while a worktree still has the branch checked out, so the worktree goes first:

```
git worktree remove <resolved worktree path>
git branch -d <branch>
```

**`git worktree remove` never takes `--force`, and `git branch -d` never becomes `-D`.** Both forms are chosen precisely because they refuse when something would be lost; that refusal is the safety property, not an obstacle to route around. Record the removal in the run's own record, and at the Current-state rewrite that follows, rewrite the `**Pointers:**` branch entry to `` branch `<branch>` (removed YYYY-MM-DD) `` — the identity stays citable while every reader that resolves the entry as a ref reads it as gone rather than live. `scripts/commit-scan.ts` matches that marker to take its `HEAD` fallback, and cannot read this prose at run time — a sanctioned copy per `AGENTS.md` § *Consumer lists*: reword the marker here and change the pattern there in the same edit.

**A refusal between the two commands is still a partial cleanup, and is recorded as one.** The preflight narrows that window; it cannot close it, because the two commands are not one atomic operation and the `HEAD` the preflight judged against can move under them. So a branch the **merged** predicate proved contained can still be refused here, checked against the main checkout's `HEAD` rather than against anything that predicate examined, and by then the worktree is already gone. Record that the worktree was removed, **name the surviving branch** so the backstop and the user both know what is still standing, and finalize anyway. Never reach for `-D` to tidy the record: deleting the branch once its containment is confirmed by hand is the user's call, not this run's.

Either predicate fails, or the preflight refuses → **refuse, name the reason, and finalize anyway.** A dirty or unpushed worktree holds work nothing else has a copy of, an unmerged branch is still the task's delivery vehicle, and a branch `git branch -d` would refuse is one whose removal cannot finish; none of the three is a reason to hold the task open, and none is a reason to force. Record what was refused and why, leave both in place, and let the backstop collect them.

**Who removes:**

- **The finalization run is the actor** — the `implement-task` pass reaching `done`, whether directly or from `in-review`.
- **`maintain`'s worktree-husk sweep is the backstop**, kit-scoped: it lists the leftover worktrees beside the main checkout together with the recorded task branches that no longer have one, applies the predicates above unchanged, and removes only on per-item confirmation. **A terminal task whose branch is not merged qualifies for the report and never for removal.** Terminal status is not a merged proxy: `git branch -d` on such a branch either refuses — stranding exactly the partial cleanup above — or, where an upstream happens to be set, succeeds and deletes an undelivered task's only local vehicle, after which § *Re-entry on resume* reads the missing branch as delivered.
- **A reconciler never touches Git.** `reconcile-task` and the reconcile composites may advance a task `in-review → done` from what the user reports (`./reconciliation.md`), and that advance leaves the worktree and branch standing. This is a **known, accepted gap**, not an oversight: the next `implement-task` pass or the sweep above collects them, and buying the alternative would mean putting Git mutation inside skills whose whole contract is that they write task documents only.

## The live-verification gate

Where `./task-delivery.md` § *Repo delivery declarations* declares live verification, a task in that repository reaches `done` **only through the `(external)` goal `plan-task` emits**. The gate rides on that goal; it is not a second check standing behind it:

- **`plan-task` emits the goal.** The goals draft carries a `G<n> (external)` goal naming the live outcome and the yardstick that confirms it, held to the same quality bar as any other goal (`./acceptance-criteria.md`). A hand-authored `goals.md` that lacks one in a declaring repository is **surfaced to the user**, never silently amended — the goals are the user's contract.
- **`implement-task` parks on that goal.** The acceptance gate tags it `pending external` while the live check is outstanding, and the task parks at `in-review` (`./task-lifecycle.md`). It reaches `done` only on a later run, once the user reports the live state and the gate re-runs against that best-available proxy.

**What the mechanism does not do is catch a goal that was never written.** The acceptance gate runs `goals.md` as written, so it fires on a goal that *is* marked `(external)` and never on the absence of one: a goals file that is hand-authored, predates this contract, or had the surfacing above declined finalizes to `done` with no live check and no complaint. Closing that would mean `implement-task` re-reading the declaration at its own gate and refusing there; until it does, the mandate below reaches the goals **draft** alone, and a declaring repository's real guarantee is the surfacing in the first bullet.

The machinery is entirely the existing one — the `(external)` marker, the `pending external` verdict, the `in-review` state — so this gate adds no status value and no new vocabulary. What it adds is that the goal is **mandatory in the draft** where the repository declares the gate, rather than remembered. Where no repository declares it, none of this fires and a task reaches `done` at its acceptance gate exactly as it always has.
