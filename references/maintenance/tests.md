# Test maintenance

Maintainer-only testing strategy, suite commands, dependencies, rationale, and live procedures. Read § *Testing strategy* before adding or retaining a check. Read the relevant suite paragraphs before changing its tests; read the live procedure only when live model calls are requested. Surface-to-suite routing is in `references/maintenance/repository.md` § *Change routing*.

Suites use zero dependencies and Node type stripping, like their sources.

```
node --test tests/<name>.test.ts
node --test "tests/*.test.ts"
```

Quote the glob for the runner to expand it. A bare directory would be resolved as a module path.

## Testing strategy

Apply `references/engineering/testing.md` for generic test practice. This section adds the project's check kinds, limits, and retention rules.

Suites use four kinds of checks:

- **Behavioral checks** run a helper, its exported functions, or `setup.ts` against temporary fixtures. They assert outputs, exit codes, written and preserved files, Git state, and process lifecycle.
- **Structural checks** read corpus files for formats that helpers, installers, or other sources consume mechanically. They check citations, cited headings, registries, markers, and adapter fields. They assert no instruction wording.
- **Template and snippet checks** fill the task templates or extract a skill's embedded shell program. They run real helpers or that program over the result.
- **CLI integration checks** spawn a helper and assert its status, stdout, stderr, and process behavior. Run input-validation variants through the exported API. Keep representative CLI cases for refusal status, diagnostics, and the absence of a launched child.

The default suite proves neither agent compliance with instructions nor real vendor CLI behavior. Review instruction-following behavior manually. Fake vendor CLIs prove the helper's transport only.

**Isolation.** Default runs read no credentials, launch no real vendor CLI, and reach no network. Cases that write files work under temporary stores and checkouts. The `secretary-state`, `start-secretary`, `meeting-sync-state`, `task-move`, `task-state`, and `setup-install` suites give every helper and installer launch a temporary `HOME`. Helper launches in other suites keep the user's `HOME`. The `commit-scan`, `task-state`, and `worktree-merge` suites also run Git, directly and through helpers, with the user's environment; `task-state` helper launches replace only `HOME`. Git therefore reads the user's system configuration and, wherever `HOME` is the user's, their global configuration. Its commits run any hooks that configuration sets through `core.hooksPath`. Those suites set Git identity and signing locally. Cases that differ in input, permissions, clock, or process behavior get separate executions.

**Scenario reuse.** When several tests assert on one unchanged argument set, run it once in a `describe` scenario's `before` hook. Freeze the captured result so a test that mutates it fails. Selecting one test then runs only its scenario, and a failed setup cancels only that scenario's tests. The suite paragraphs below name the cases kept separate.

**Fault-based retention.** Keep an assertion when a plausible fault in the covered code or source makes it fail. Remove assertions that only confirm the test's own fixture or construction. Name each test for the behavior it exercises, including the limits of fixtures that stand in for agent or vendor actions.

**Routine verification.** `node --test "tests/*.test.ts"` runs offline and makes no model calls. The live Codex doctor probe and the live executor smoke stay opt-in under their own procedures below.

## Suite notes

**The `pr-comments` suite never reaches the real CLI or the network.** Cases use fixture pages, arguments rejected before fetching, or a fake `gh` first on PATH. Cases requiring live CLI or network access do not belong here.

**The `executor-run` suite uses isolated fake vendor CLIs.** Its PATH contains only fixture executables with an absolute Node interpreter. Missing-command cases use that same isolated PATH. Literal transport, process receipts, large logs, failure after edits, and owned cancellation need local temporary files and POSIX subprocesses; no credentials or live model calls are used. The fake CLI writes each polled sentinel under a temporary name and renames it into place. Otherwise a concurrent poll can read a created but still empty file. The fake CLI records the argv, stdin, cwd, and effort variable it receives, then replays scripted help output and events. These cases prove adapter transport: what the helper sends and how it reads replies and process state. They prove no real vendor compatibility, configuration precedence, or permission enforcement. Only the opt-in live executor smoke runs real CLIs. Request-validation variants call the exported `readRequest` directly. One CLI case checks the allowance refusal receipt: status 2, the named entry, no probe, and no vendor call.

**The `review-evidence` suite checks citations across review and publication sources.** Each approval producer must cite `references/engineering/review-evidence.md`. Every relative file citation in the listed sources must exist. Section citations among those sources, or into `references/workflow/skill-conventions.md`, must name an existing heading in their owner. `references/workflow/skill-conventions.md` must register `fix-findings-reconcile` as a composite, and its confirm-gated roster entry must name an existing proposal section. The suite checks no instruction wording and proves no approval behavior, screenshot contents, or human judgment.

**The `setup-install` suite pins a rule about `references/` that reaches past its own assertions.** `setup.ts` copies references with `dereference`, materializing links. Health-check's `--installs` pass reports one-sided links as drift. A references symlink would therefore produce permanent installation drift; keep the tree symlink-free. Both secretary duties must install as regular files in both homes. The secretary case also reads installed bytes for contract and helper-path citations, the Claude adapter's `disallowedTools` line, and absent Codex permission keys. It finds no installed `scripts/` directory. These checks prove no agent permission behavior. The hook case runs the installed `SubagentStart` command through `sh` with `HOME` set to the test home. It puts the running Node first on `PATH`, because the command calls `node` by name.

Each installation scenario is a `describe` block with its own directory under the suite's temporary root. Its `before` hook runs every `setup.ts` launch the scenario needs; its `after` hook removes the directory. Scenarios that need an installed home run their own clean install first. The hook-merge and linked-file scenarios read the expected kit hook entry from a separate reference home. Selecting one test therefore launches only its scenario's installs. A failed scenario setup cancels only that scenario's tests. Captured observations are frozen.

**The live Codex doctor probe is opt-in.** Its environment diagnostics contact external services and can abort sandboxed suite runs. Run `AGENTS_KIT_LIVE_CODEX_DOCTOR=1 node --test tests/setup-install.test.ts` when live diagnostics are intended. Its test runs against the clean-install scenario's Codex home. Default runs retain installation and TOML checks and report the doctor probe as skipped.

**The installed Codex TOML probe checks for permission overrides.** It rejects sandbox, approval, permission-profile, and network-proxy overrides in parsed agent definitions. Its test parses the clean-install scenario's agent TOML files. It proves those keys are absent, not how Codex applies permissions at runtime. The probe requires Python with `tomllib`; without it, the suite reports the check as skipped.

**The `secretary-state` suite never touches the real home.** Every case passes a temporary home to the CLI or to `openStore`. No run reads the user's configuration or writes their secretary records. Large histories are built in-process through the exported `append`; CLI runs check stdout bounds and exit codes. Due-state cases pass `now` to `append` and `status`. Configured-cadence cases cover defaults, malformed known settings, and complete/partial deadlines, comparing event/body digests and pending identifiers across cadence changes. Wake-boundary cases pin UTC and mock the validation clock, covering due rounding, minute shifts, minimum lead, and neighboring valid slots. Stored-review cases retain immutable-history digests. CLI cases that read the real clock place their instants relative to it, and the local-time cron case pins `TZ` for each run. Apply cases write only their temporary runbook and compare it and a sibling file before and after. Interruption cases pass `applyProposal` hooks that throw just before or just after the replacement. Recovery cases pass `recover` a small batch to page short histories; one CLI case builds more than two fixed batches. CLI apply cases check exit 0 with the printed event for an applied result and exit 1 naming the recorded seq for a held one. Changed-evidence cases edit a cited source and author the revision as fixture actions; the helper does not read cited sources.

Identity cases switch configuration between temporary runbooks with colliding proposal IDs. Explicit-mode cases exercise every command family after retargeted, malformed, and deleted configuration, preserving the other store. Legacy guards refuse drift and accept physical aliases. Interrupted explicit applies retain the accepted revision through recovery.

Permission cases observe record protection and apply permissions during writes and after publication. They restore the process umask and filesystem observers.

**The `start-secretary` suite checks secretary structure and runs documented helper commands.** It reads the skill, init-config, the secretary contract, the runbook duty, both adapters, `README.md` § *Secretary*, and the skill registrations in `references/workflow/skill-conventions.md` and `references/workflow/domain-packs.md`. A structural edit to any of them can fail it. Structural cases check the skill name, its shared-references link, its registrations, and the sections and files the skill, init-config, contract, and duty cite. The confirm-gated roster entries for start-secretary and init-config must name existing proposal sections. Both adapters must carry the role name and contract citation that the launch checks read; the Codex adapter must set no provider or permission override keys, and the Claude adapter must set no tool allowlist. The runbook report may render only the duty's reply headings and its unavailable-evidence class. Each section that matches automatic wakes must use the owner tag that opens the wake prompt. These cases check no instruction wording and prove no agent compliance or native host execution. Its helper cases run the skill's command and payload shapes under temporary homes, as the `secretary-state` suite does. A status case covers store reselection after retargeting and the exit statuses for malformed, missing, and unreadable configuration. Retained lifecycle cases follow review, proposal reads, accepted interrupted apply, recovery, stop after config deletion, and a fresh start on the new runbook. A startup-status case calls the exported helper functions: an undecided proposal stays pending while an interrupted accepted apply settles, and the next review stays scheduled. Meeting CLI traces cover meetings-only startup without runbook records, configuration retargeting and deletion, snapshot serialization, explicit follow-up, stop and fresh start. Combined-duty traces compare accepted proposal identifiers and complete history before and after sync, including two sync passes with unchanged history and approval digests, then apply the accepted revision through the runbook helper. Runbook-only and no-duty cases leave meeting stores absent. Fixed-clock combined-duty traces cover different deadlines, partial completion, failure retries, leases, missed intervals, and explicit retry.

**The `start-group` suite checks start-group structure.** It reads the skill, each file it cites, and the skill registrations in `references/workflow/skill-conventions.md` and `references/workflow/domain-packs.md`. A structural edit to any of them can fail it. Cases check the skill name and description, its shared-references link, and its standalone and pack-free registrations. A fixture case proves that the frontmatter reader reads `description: ""` and `description: ''` as empty, so the description check can fail. The skill must ship no `AGENTS.md` link and cite no domain pack. Every cited file must exist, and every cited section must name a heading in its owner. A basename-only citation resolves to the file of that name that the skill cites by full path with a section. A section cited without an owner names a skill heading, or a heading of the nearest owner cited before it on the same line. The skill must cite sections of the task-store, context-schema, reconciliation, and skill-conventions references. These cases check no instruction wording and prove no agent compliance.

**The `invocation-gate` suite pins prose.** Its `MARKER_LINE` is read from the code span `references/workflow/skill-conventions.md` § *The invocation gate* renders after "this exact line:", so an owner edit fails the suite until every gated skill follows; the roster block there holds one `` - `<skill>` `` entry per line up to the first blank line. The live tree holds no closed door, so the door-detector fixture case is the only proof that the absence check can fail.

**The `meeting-sync-state` suite isolates every folder and state store in disposable homes.** No test reads personal notes or configuration. Retained configuration, cadence, leases, physical containment, physical-folder replacement, no-overwrite publication, receipt reconciliation, failed retries, and conditional deletion use fixed clocks and deterministic hooks. In-process publication hooks supply deterministic filesystem races. Stop and supersession interleavings use before-lock hooks on real helper attempts before create, archive, and delete. They prove refusal after revocation wins the lock. A CLI stop sent while create, archive, or remove holds the lock reports busy, and the mutation finishes first. Planted owner records prove dead-owner reclamation and live-owner busy reports. An after-publication interruption retains the archive across stop. Archive hooks interrupt before publication, after linking, before deletion, and after deletion; reconcile settles the removal and preserves a new incoming file. Retries assert one archive, retained newer incoming text, unchanged collision files, and refusal of changed observations or incomplete deletion authorization. Stage and archive replacements with identical bytes prove that recovery checks identity as well as content. These filesystem checks do not establish arbitrary concurrent-writer isolation or native agent behavior.

**The `sync-meeting-notes` suite traces the documented procedure's helper calls with disposable fixtures.** Explicit helper traces show calls leaving unnamed notes untouched and refusing removal or publication without the required receipt, attestation, or matching hash. These traces encode source and matching decisions as fixtures; they do not execute a model, fetch connectors, or prove native scheduling. Relative-link checks cover the new duty and shared procedure.

**The `commit-scan` suite builds real checkouts.** Branch existence and watermark ancestry require Git repositories, not text fixtures. Each temporary checkout sets local `user.email`, `user.name`, and `commit.gpgsign`, then stages with `git add -f`. This isolates tests from global identity, signing, and ignore settings. Keep the project-local task folder untracked and unstaged so it stays outside the ranges under test.

**The `health-check` suite's fixture ages are load-bearing.** Four folders exceed the default 30 days. `done-unarchived` is excluded from stale by terminal status; `unknown-status` by vocabulary; `parked-todo` by backlog placement. `no-status-plan` has no exemption: the live-status guard checks only non-null status. Its unparseable header therefore yields the second stale finding, labeled `no-status`. Regressing any exclusion changes the count.

Each health-check `describe` scenario runs its argument sets once, in its `before` hook. These cover the store, anchor, citation, pre-delivery install, duplicate-slug, group, and near-miss fixtures. A separate group runs each single-home `--installs` fixture once for both its own test and the user-action matrix. Selecting one single-home test therefore runs every single-home fixture. Shared results are frozen, so a test that mutates one fails. Flag variants, permission and mutation cases, and the file, pipe-buffer, and early-reader runs keep separate executions.

**The `session-triage` suite launches each `describe` scenario's argument set once.** The main corpus and its `--top`, `--since`, retry, and absent-directory variants each spawn the helper in their scenario's `before` hook. Each test reads status, stdout, and stderr from that frozen capture and parses its own report. Selecting one test launches only its own scenario. Built fixture scenarios, the locked-directory and locked-file cases, and the file, pipe-buffer, and early-close runs keep separate executions. The determinism cases run their arguments twice on purpose.

**The `silence-watch` suite drives the watch loop with a fake clock.** Loop cases call the exported `watch` with a clock whose sleep advances time, edits fixture files, and stops the loop by throwing. Fixture modification times fall on whole seconds, so the silence arithmetic is exact. Usage variants call the exported `parseArgs`; one CLI case checks the refusal status and message. One CLI case runs the real clock with a one-second interval for about two seconds. It reads the first notice, closes stdout, and expects status 0.

## Opt-in live executor smoke

Run this procedure only when live model calls are requested. Use disposable fixture repositories and existing authenticated CLIs. Preserve installed payloads, authentication files, and user configuration. Fingerprint protected configuration, auth files, and installed definitions before calls; retain hashes without copying credential contents.

1. Name one absolute `<candidate-kit>` checkout. Record `git -C "<candidate-kit>" rev-parse HEAD`, its tracked delta, and any untracked candidate inputs. Record host and child CLI versions.
2. Explicitly load the candidate `skills/implement/SKILL.md` in each fresh host session. Bind the test's source, helper, and contract roots to `<candidate-kit>`. For external launches, invoke that checkout's helper directly with request `contractRoot` pointing there, following [cross-vendor preparation](../workflow/executor-engines-cross-vendor.md) and the [launcher contract](../scripts/executor-run.md). A registered `kitRoot` pointing elsewhere does not identify this candidate; do not rewrite machine configuration to select it.
3. Derive native test adapters from the candidate Claude definition `agents/executor.md` or Codex definition `agents/executor.toml`. Preserve role instructions, model, effort, and permission inheritance; expand only install-root references to the candidate's absolute root. Supply Claude's named `executor` through invocation-local `--agents`; place Codex's definition at the fixture's `.codex/agents/executor.toml`. If Codex selects another role file, restart with invocation-only `-c 'agents.executor.config_file="/absolute/fixture/.codex/agents/executor.toml"'` ([role setting](https://learn.chatgpt.com/docs/config-file/config-reference), [one-off overrides](https://learn.chatgpt.com/docs/config-file/config-advanced#one-off-overrides-from-the-cli)). Retain the source-to-test definition diff.
4. In each host, exercise a fresh run with omitted `-e`. Verify the native route, selected candidate definition, and actual candidate-contract read in the trace. An installed definition or missing contract-read evidence leaves the check pending.
5. From Claude Code, invoke candidate `implement -e codex` on a bounded file change. Repeat from Codex with `implement -e claude`. Verify the requested diff at the supplied fixture root. Trace Codex's executor bootstrap and contract read; for Claude, trace the per-run `agents-kit-executor-*` role, candidate `roleSource`, and contract read.
6. Include two ordered units in the Codex-host exercise. Assign Unit 1 a coordinator-owned required check under [executor intake](../workflow/executor-contract.md#write-mode-routing). Its report retains that check as pending, and its packet excludes Unit 2. Run the original check before acceptance and the successor launch. Failure or unavailable access keeps the unit and its dependent work unadvanced.
7. Use a separate fixture with an intentionally unavailable required capability. Confirm an explicit blocker and held coordinator disposition, preserving the selected engine and permission policy. Record unavailable host, login, model, policy, or verification access as pending.
8. For each attempt, retain invocation, root, model/effort/policy provenance, receipt, raw diagnostics, available final report, and coordinator disposition. Compare requested model, effort, and policy with exposed runtime trace settings. A mismatch fails the check; a receipt alone does not prove application. Include selected-role and contract-read trace locations, plus proof ownership for every required check. Finish the repository checks under [Change routing](./repository.md#change-routing), including inspection of the unchanged native permission-inheritance fixture `tests/setup-install.test.ts`.
9. After all CLI calls exit, identify trust entries created by this run for disposable roots. Remove only proven task-owned entries, preserving unrelated user changes. Recheck protected fingerprints and account for remaining differences. Whole-configuration rollback and home-wide cleanup are outside this procedure.
